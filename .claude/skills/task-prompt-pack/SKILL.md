# 작업별 AI 지시문 묶음 만들기 (WhyMath판)

계획(작업 목록과 의존 관계)을 받아, 작업 하나당 파일 하나인 지시문 묶음을 만든다. 각 파일은 다른 맥락 없이 그것만 붙여 넣어도 새 AI 세션이 작업을 끝까지 할 수 있어야 한다. 받는 AI는 이 대화를 모르기 때문이다.

이 스킬은 원본 `task-prompt-pack`(PED-17에서 처음 썼다)에 WhyMath에서 골든 패스 묶음을 만들며 보강한 것이다. 보강점 4가지는 §"원본과 다른 점"에 있다. 실제 완성 예 = `golden/prompts_src/`(원본 spec·config)와 그 산출물 `golden/prompts/`·`golden/prompts_no_students/`.

결과물 모양:

```
<프로젝트>_AI지시문/   (WhyMath에서는 golden/prompts/ 처럼 그 작업이 사는 폴더 아래)
├── README.md                      ← 사용법, 단계별 실행표, 작업별 여유, 관문, 사람이 할 일
├── 단계01_병렬_2개/
│   ├── <접두어>-단계01-T0-<짧은이름>.md   ← 파일 이름 = 세션 이름 = 첫 줄 "세션 이름:"
│   └── ...
├── 단계06_순차/
└── ...
```

## 순서

### 1. 작업 목록과 의존 관계 확정

작업마다 번호(T0, A1, S3처럼 레인 글자+숫자), 짧은 이름, 레인, 선행 작업을 정한다. 아직 없다면 사용자와 먼저 만든다: 기간이 아니라 "무엇이 끝나야 다음을 시작할 수 있는가"로 정렬하고, 병렬 가능한 묶음과 크리티컬 패스(늦어지면 전체가 늦어지는 줄)를 보여준다. 공개·배포처럼 안전에 닿는 순서(관문 → 감사 → 소수 공개 → 전체)는 병렬로 만들지 않는다.

계획서가 "세션 1~15"처럼 달력 순서로 쓰여 있어도 그대로 옮기지 않는다. 선행 관계만 적으면 생성기가 병렬 묶음을 찾아낸다(골든 패스에서는 달력상 순차였던 15세션에서 병렬 3곳이 나왔다).

### 2. 작업 지시서 작성

`references/spec-format.md`의 형식으로 작업 지시서를 쓴다(공통 규칙, 용어 표, **공유 계약**, 작업별 목적·선행 산출물·할 일·산출물·완료 기준·하지 말 것). 작은 예시는 `assets/example-ped17-spec.md`, 큰 예시는 `golden/prompts_src/spec.md`.

- **먼저 저장소를 실측한다.** 지시서에 들어갈 경로·패키지 이름·CI 잡 이름·데이터 건수는 `grep`·`ls`·`git log`로 직접 확인하고, "사전 실측(날짜 · 기준 커밋)"이라고 표시해 적는다. 받는 AI가 재확인하도록 공통 규칙에 "사전 실측 값도 다시 확인한다"를 넣는다.
- 여러 작업이 같은 모양(API 응답·JSON 스키마·표·환경변수)을 써야 하면 작업 본문마다 복사하지 말고 **공유 계약** 절에 한 번 쓴다. 생성기가 모든 파일에 싣는다.
- 사용자가 문서 도구(Claude Docs, Notion 등)를 쓰고 있으면 지시서를 그 문서의 탭으로 만들고, **그 문서를 원본으로 삼는다.** 지시문 파일은 원본에서 생성하는 결과물일 뿐이다.
- 정해지지 않은 숫자·정의는 "(제안값)"으로 표시하고 사용자에게 확정받는다. 확정되면 표시를 지우고 승인 기록에 한 줄 남긴다.
- 저장소 경로·테이블 이름처럼 모르는 정보는 지어내지 않는다. "먼저 찾고, 못 찾으면 미확인으로 보고"라고 쓴다.
- 사람만 할 수 있는 일(섭외·승인·권한 조작)은 번호를 주되(예: H1) 레인을 "사람이 하는 일"로 두고, 설정의 `human_tasks`에도 적는다.

### 3. 설정 파일 작성

`assets/example-ped17-config.json`(작은 예) 또는 `golden/prompts_src/config.json`(큰 예)을 복사해 고친다. 항목 설명은 `references/spec-format.md` 5절. 특히:

- `tasks`의 `deps`는 계획서의 선행 작업 표와 지시서의 "선행 산출물"을 합친 것이다. 둘이 다르면 사용자에게 확인한다.
- `background`는 모든 지시문 맨 앞에 들어가는 5~7줄이다. 문제, 결정, 예외 권한, 관문 순서, 목표 기한을 담는다.
- `short`는 세션 이름이 되므로 공백 없이 짧게 쓴다.
- `repo_location`에 저장소 위치를 **채워서** 준다(GitHub 경로 · 사용자 머신 경로 · 클라우드 세션 경로). 자리표시자를 남기지 않는다 — Kiki는 파일을 통째로 붙여 넣는다.
- `output_root`(보고 폴더)와 `branch_prefix`는 묶음마다 다르게 둔다. 같은 계획의 변형 묶음(예: 학생 없는 변형)을 만들 때 보고가 섞이지 않게 하기 위해서다.

### 4. 생성

생성기는 저장소에 한 벌만 둔다: `scripts/golden_prompts/build_prompts.py`(린트가 배선된 `scripts/` 아래 — `tests/infra/test_lint_coverage.py`가 어떤 CI 린트에도 안 걸리는 `.py`를 막으므로 다른 곳에 복사하지 않는다).

```bash
python3 scripts/golden_prompts/build_prompts.py <작업지시서.md> <설정.json> <출력 폴더>
```

스크립트가 하는 일:
- 선행 관계로 **실행 단계**를 계산한다(가장 빨리 시작할 수 있는 순서). 같은 단계에 작업이 2개 이상이면 `단계NN_병렬_K개`, 1개면 `단계NN_순차` 폴더에 넣는다.
- 작업마다 **여유**(늦어도 되는 단계)와 크리티컬 패스를 계산해 파일과 README에 적는다.
- 파일 이름과 첫 줄을 `<접두어>-단계NN-<번호>-<짧은이름>`으로 맞춘다. 세션 목록에서 이름순으로 정렬하면 실행 순서가 된다.
- 공통 규칙 1·2번을 "이 지시문만 읽는다", "선행 작업의 `<산출물 폴더>/<번호>/보고.md`가 완료(관문은 go)인지 확인한다"로 바꾼다. 세션끼리는 이 산출물 폴더와 `보고.md`로만 결과를 넘겨받는다.
- 지시서의 `**공유 계약**` 절을 모든 파일의 "용어" 다음에 통째로 싣는다.
- "너의 역할"에 **0단계: 세션 제목 등록**을 넣는다 — 클라우드 세션이면 `claude-code-remote`의 `set_session_title`을 호출하고, 터미널이면 사용자에게 `/rename <이름>`을 안내한다. 저장소 훅 `.claude/hooks/golden_session_register.py`(UserPromptSubmit)가 첫 줄 `세션 이름:`을 읽어 `golden/SESSIONS.md`에도 자동 기록한다. 이 훅은 접두 `GP`·`GPN`만 인식하므로 새 프로젝트 접두를 쓰면 훅의 `_NAME_RE`와 `_BUNDLE`에 접두를 추가하고 `tests/infra/test_golden_session_register.py`에 픽스처를 더한다.

### 5. 확인

- 스크립트 출력의 단계 구성과 크리티컬 패스가 계획과 맞는지 본다.
- 파일 하나를 열어 실행 방식, 선행 산출물 위치, 공유 계약, 작업 지시, 보고 형식이 다 있는지 확인한다.
- 용어 표 행 수가 지시서의 용어 표와 같은지 본다(공유 계약 안의 표가 섞여 들어가면 생성기 파싱이 어긋난 것이다).
- 지시서에 "(제안값)"이 남아 있으면 사용자에게 알린다.
- 저장소에 커밋할 때는 `scripts/ops/cp949_guard.py --root <폴더>`로 인코딩 무결성을 보고, 로컬 CI 미러(`scripts/harness/ci_mirror.py run`)를 **커밋 뒤에** 돌린다. 미러가 도는 동안 커밋·amend를 하면 그 실행은 오염으로 무효 처리된다(HARN-194 · 2026-11-08 실측 20분 손실).

### 6. 전달

출력 폴더를 zip으로 묶어 전달하고, 답변에 단계별 실행표(단계, 순차/병렬, 세션 목록), 크리티컬 패스, 시작 방법(1단계 세션들을 여는 것부터)을 짧게 적는다. 세션을 만들 때 파일 이름을 제목으로 직접 넣으라고 안내한다(클라우드 세션은 AI가 0단계에서 스스로 바꾼다).

## 변형 묶음 만들기

같은 계획의 조건부 변형(예: 피험자를 구하지 못했을 때)이 필요하면 지시서를 복사해 바뀌는 작업만 고치고, 바뀌지 않는 작업 절은 **바이트 동일**하게 둔다(파이썬으로 두 파일의 해당 절을 비교해 확인). 접두·`output_root`·`branch_prefix`를 다르게 주고, README `readme_notes`에 "둘 중 하나만 쓴다 · 갈아타는 절차"를 적는다. 예 = `golden/prompts_src/spec_no_students.md` + `config_no_students.json` → `golden/prompts_no_students/`.

## 고칠 때

계획이 바뀌면(작업 추가, 숫자 확정, 순서 변경) 생성된 파일을 직접 고치지 말고 원본 지시서와 설정을 고친 뒤 다시 생성한다. 스크립트가 출력 폴더를 지우고 새로 만들기 때문에, 파일을 직접 고친 내용은 다음 생성 때 사라진다.

## 원본과 다른 점 (2026-11-08 WhyMath 보강)

1. **공유 계약 절** — 지시서의 `**공유 계약**` 블록(표·코드 펜스 포함)을 모든 파일에 싣는다. 여러 세션이 같은 API·스키마를 각자 다르게 해석하던 문제를 막는다.
2. **저장소 위치 사전 기입** — `repo_location` 설정으로 "작업 환경"을 채워서 낸다. 자리표시자가 그대로 실행되는 사고를 막는다(CLAUDE.md 붙여넣기 블록 규칙).
3. **세션 제목 0단계 + 등록 훅** — 지시문이 스스로 세션 제목을 맞추고, 훅이 등록부를 쓴다.
4. **생성기 위치** — 스킬 폴더가 아니라 `scripts/golden_prompts/`에 둔다(린트 배선·단일 원본).

## 왜 이렇게 만드는가

- **파일 하나에 모든 맥락:** 병렬로 여러 세션을 열면 각 세션은 서로의 대화를 모른다. 배경, 규칙, 용어, 공유 계약, 선행 산출물 위치가 파일에 다 있어야 같은 기준으로 움직인다.
- **파일 이름 = 세션 이름:** 세션이 10개 넘게 늘어나면 어느 세션이 어느 작업인지 놓치기 쉽다. 이름에 단계 번호를 넣으면 정렬만으로 진행 상황이 보인다.
- **산출물 폴더와 보고.md:** 다음 세션이 앞 세션의 결과를 찾는 유일한 통로다. 선행 보고가 없으면 시작하지 않게 해서, 앞 작업이 덜 끝난 채 뒤 작업이 도는 사고를 막는다.
- **관문은 순차:** go/no-go 판정을 받아야 다음으로 넘어가는 작업은 병렬로 돌리면 판정이 의미가 없어진다.
