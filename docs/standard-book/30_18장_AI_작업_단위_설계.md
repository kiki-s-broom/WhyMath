# 18장. AI 작업 단위 설계

한 줄 요약: **AI에게는 목표·범위·완료 조건이 적힌 작은 작업 카드를 주고, 범위 밖 수정과 테스트 약화는 훅으로 막는다.**

#### ① 증상

- "알아서 해" → 40개 파일이 바뀌었고 절반은 요청과 무관
- 긴 세션 후반에 AI가 초반에 합의한 설계를 잊고 다른 방식으로 구현
- 테스트가 실패하자 AI가 **테스트를 고쳐서** 통과시킴
- "다 했습니다"라는 보고와 달리 절반은 미완성 (TODO 주석, 빈 함수)
- 같은 지시를 두 번 했더니 전혀 다른 구조의 코드

#### ② 근본 결함

작업 **명세**(무엇을·어디까지·언제 끝났다고 보는가)가 없습니다. 명세가 없으면 AI는 범위를 스스로 정하고, 완료를 스스로 선언합니다. 또 AI의 비결정성과 컨텍스트 한계를 **구조로 흡수하는 장치**(작은 단위, 파일로 된 기억, 기계적 완료 판정)가 없습니다.

#### ③ 업계 표준

| 표준 | AI 작업에의 적용 |
|---|---|
| 인수 조건 (Acceptance Criteria), Given-When-Then | BDD(Dan North, 2006). 완료 조건을 **명령으로 확인 가능한 문장**으로. 예: "`pytest tests/test_bkt.py` 통과" |
| 완료의 정의 (Definition of Done) | 스크럼 가이드. 모든 작업에 공통인 완료 기준 (테스트·린트·위헌 심사 통과) |
| INVEST | Bill Wake(2003). 좋은 작업 단위: 독립적·협상 가능·가치 있음·추정 가능·**작음**·**테스트 가능** |
| 작은 배치 | 『Accelerate』(2018): 작은 단위 변경이 배포 성과와 안정성을 함께 높임 |
| 리뷰 가능 크기 | SmartBear·Cisco 코드 리뷰 연구(2006): 한 번에 200~400줄을 넘기면 결함 발견율이 급격히 떨어짐 |
| 테스트 먼저 (TDD) | 사람이 승인한 테스트를 먼저 고정하고 AI는 구현만 → 테스트는 AI가 못 건드림 |

#### ④ 원전

- Nicole Forsgren·Jez Humble·Gene Kim, 『Accelerate』(2018)
- Claude Code 공식 문서 — 훅(hooks), 서브에이전트, 권한(permissions) 설정

#### ⑤ WhyMath 적용 — 작업 카드와 범위 훅

운용 지침서의 "계획 먼저, 소단위 실행" 원칙을 **파일과 훅**으로 구현합니다. 작업마다 `task/이름` 브랜치를 만들고 루트에 `TASK.md`를 둡니다. 범위 훅이 읽을 수 있도록 수정 허용 범위는 정해진 형식으로 적습니다.

**작업 카드 예시**

```text
# TASK.md — AI 작업 카드 (task/bkt-cap 브랜치)
## 목표
연속 정답 시 숙달 확률이 1.0을 넘는 버그 수정

## 입력 자료
- 판례 없음 / 관련 장: 표준북 23장 / 재현: tests/unit/test_bkt.py::test_cap (사람이 작성·승인)

## 수정 허용 범위 (scope)
scope: eos_core/knowledge_tracing/*.py
scope: CHANGELOG.md

## 테스트 잠금
tests-locked: yes          # AI는 tests/ 를 수정할 수 없음 (R18-03)

## 완료 조건 (모두 명령으로 확인)
- [ ] pytest -q tests/unit/test_bkt.py 통과
- [ ] python scripts/constitution/audit.py 차단 사유 0건
- [ ] 변경 400줄·파일 10개 이내 (R18-04)

## 되돌리기 경계
커밋 1: 상한 처리 로직 / 커밋 2: CHANGELOG
```

**범위 훅 (Python)**

```python
# .claude/hooks/guard_scope.py — 작업 범위 밖 편집 차단 (PreToolUse 훅, R18-02·R18-03)
import fnmatch
import json
import re
import sys
from pathlib import Path

def load_card(root: Path) -> tuple[list[str], bool]:
    try:
        text = (root / "TASK.md").read_text(encoding="utf-8")
    except FileNotFoundError:
        return [], False                                   # 작업 카드가 없으면 범위 제한 없음 (R18-01이 따로 경고)
    scopes = re.findall(r"^scope:\s*(\S+)", text, re.M)
    locked = bool(re.search(r"^tests-locked:\s*yes", text, re.M | re.I))
    return scopes, locked

def main() -> int:
    try:
        data = json.load(sys.stdin)                         # Claude Code가 넘기는 도구 호출 정보
    except json.JSONDecodeError:
        return 0
    if data.get("tool_name") not in ("Edit", "Write", "MultiEdit"):
        return 0
    root = Path(data.get("cwd") or ".").resolve()
    raw = (data.get("tool_input") or {}).get("file_path", "")
    try:
        rel = Path(raw).resolve().relative_to(root).as_posix()
    except ValueError:
        print(f"⛔ 저장소 밖 파일 편집 차단: {raw}", file=sys.stderr)
        return 2
    scopes, locked = load_card(root)
    if locked and rel.startswith("tests/"):
        print(f"⛔ 테스트 잠금 작업입니다. {rel} 을(를) 수정할 수 없습니다. 테스트가 틀렸다고 판단되면 멈추고 보고하세요.", file=sys.stderr)
        return 2
    if scopes and not any(fnmatch.fnmatch(rel, s) for s in scopes):
        print(f"⛔ {rel} 은(는) TASK.md 수정 허용 범위 밖입니다: {scopes}. 범위 확장이 필요하면 멈추고 보고하세요.", file=sys.stderr)
        return 2
    return 0                                               # 종료 코드 2 = 차단, 메시지는 AI에게 전달

if __name__ == "__main__":
    sys.exit(main())
```

두 훅(헌법 보호 `guard_constitution.py`, 범위 `guard_scope.py`)은 `.claude/settings.json`의 `PreToolUse`에 함께 등록합니다. 훅의 차단 메시지는 **"멈추고 보고하라"**로 끝납니다. AI가 우회로를 찾는 대신 사람에게 판단을 넘기게 하는 것이 목적이기 때문입니다.

> **훅의 한계와 두 번째 방어선**
>
> 이 훅은 실제로 실행해 확인했습니다(범위 안 편집 통과, 잠긴 테스트·범위 밖·저장소 밖 편집은 종료 코드 2로 차단). 다만 훅은 편집 도구(Edit·Write)만 봅니다. AI가 셸 명령(예: `sed -i`)으로 파일을 고치면 훅을 지나칩니다. 그래서 커밋 단계에서 `git diff --name-only`의 파일 목록을 TASK.md 범위와 대조하는 검사(`check_task_card.py`)를 **두 번째 층**으로 둡니다. 13장의 원리 그대로, 두 층은 서로 다른 지점(도구 호출 시점 / 커밋 시점)에서 봅니다.
>
> TASK.md 자체도 범위 목록에 없으므로 AI가 스스로 범위를 넓히는 편집은 같은 훅에 막힙니다. 범위 변경은 사람이 합니다.

### 역할 분리 — 운용 지침서 시스템 4의 구현

| 역할 | Claude Code에서의 구현 | 독립성 (13장) |
|---|---|---|
| 기획 | 계획 모드에서 TASK.md 초안 작성 → 사람이 승인 | 사람 승인이 게이트 |
| 코딩 | task 브랜치에서 구현 (범위 훅 적용) | — |
| 코드 리뷰 | **새 세션**의 별도 서브에이전트가 diff만 보고 검토 | 맥락 독립 (구현 대화를 모름) |
| 테스트 | 사람이 승인한 테스트 + 위헌 심사 (Stop 훅) | 방법 독립 (기계 판정) |
| 품질 관리 | 완료 보고서(발견·변경·근거)를 사람이 확인 | 행위자 독립 |
