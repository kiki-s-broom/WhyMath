# 13장. 검증 계층의 독립

한 줄 요약: **검증을 여러 겹 두는 것만으로는 부족하다. 각 겹이 서로 다른 정보·방법·행위자를 써야 구멍이 겹치지 않는다.**

#### ① 증상

- 기계 검사(중복 게이트)를 통과했으니 사람 검토를 생략 — 판례 P0001
- AI가 쓴 코드를 같은 AI가 같은 대화에서 리뷰 → 같은 맹점을 공유해 "문제없음"
- 생성 AI가 낸 정답을 같은 AI가 "검증" → 둘 다 같은 이유로 틀림
- 사람 검토자가 AI 판정표를 보고 옮겨 적음 → 사람 층이 AI 층의 복사본이 됨

#### ② 근본 결함

검증 층들이 **같은 입력, 같은 방법, 같은 행위자**를 공유합니다. 그러면 층이 몇 개든 실질적으로는 한 층입니다. 안전공학에서는 이를 **공통 원인 고장**(common-cause failure: 하나의 원인이 여러 방어막을 동시에 무너뜨리는 것)이라 부릅니다.

#### ③ 업계 표준

| 표준 | 핵심 |
|---|---|
| 스위스 치즈 모델 | James Reason, 『Human Error』(1990). 모든 방어막엔 구멍이 있고, 사고는 구멍들이 **일렬로 정렬될 때** 일어남 → 구멍 위치가 서로 달라야 함 |
| 심층 방어 (defense in depth) | 원자력·보안의 기본 원칙. 독립된 여러 겹의 방어 |
| 설계 다양성 / N-버전 프로그래밍 | Algirdas Avižienis(1977~). 같은 기능을 다른 방법으로 여러 번 구현해 결과를 대조 |
| 메이커–체커 (4-eyes) | 금융권 원칙. 만든 사람과 확인하는 사람이 달라야 함 |

독립성은 네 가지 차원으로 점검합니다. **하나 이상**에서 달라야 하고, 중요한 게이트일수록 더 많은 차원에서 달라야 합니다.

| 차원 | 질문 | WhyMath 예시 |
|---|---|---|
| 정보 | 같은 입력을 보는가? | 재도출 검증은 생성 단계의 **정답을 보지 않고** 문제만 받음 (블라인드) |
| 방법 | 같은 알고리즘인가? | 생성은 LLM, 검증은 SymPy 기호 계산 (CAS) |
| 행위자 | 같은 모델·같은 사람인가? | 생성은 Claude, 두 번째 풀이는 로컬 LLM(Ollama) 등 다른 모델 계열 |
| 시점·맥락 | 같은 대화·같은 순간인가? | 코드 리뷰는 새 세션의 별도 에이전트, 사람 검토는 AI 판정을 보기 **전에** 먼저 판정 |

#### ④ 원전

- James Reason, 『Human Error』(1990) · "Human error: models and management", BMJ 320 (2000)
- Algirdas Avižienis, "The N-Version Approach to Fault-Tolerant Software", IEEE TSE (1985)

#### ⑤ WhyMath 적용 — 정답 검증의 3중 독립

**블라인드 재도출 (Python)**

```python
# eos_core/verify_pipeline.py — 생성과 독립된 정답 검증 (R13-01, R13-02)
from dataclasses import dataclass

@dataclass
class VerifyResult:
    cas_answer: str | None      # SymPy가 구한 정답 선지 (CAS로 풀 수 없는 유형이면 None)
    llm_answer: str | None      # 다른 모델 계열이 '정답을 모른 채' 푼 결과
    agree: bool
    reason: str

def blind_view(item: dict) -> dict:
    """검증 층에 넘길 정보: 문제와 선지만. 생성 단계의 answer·풀이·op_code는 제거한다."""
    return {"stem": item["stem"], "choices": [{"label": c["label"], "text": c["text"]} for c in item["choices"]]}

def verify(item: dict, cas_solver, second_model) -> VerifyResult:
    view = blind_view(item)                        # 정보 차원의 독립
    cas = cas_solver(view)                         # 방법 차원의 독립 (기호 계산)
    llm = second_model(view)                       # 행위자 차원의 독립 (다른 모델 계열)
    claimed = item["answer"]
    answers = {a for a in (cas, llm) if a is not None}
    if not answers:
        return VerifyResult(cas, llm, False, "두 검증 모두 답을 내지 못함 → 사람 검토 필수")
    agree = answers == {claimed}
    reason = "일치" if agree else f"생성 정답 {claimed} ≠ 검증 {sorted(answers)}"
    return VerifyResult(cas, llm, agree, reason)
```

R13-01의 테스트는 간단합니다. `blind_view`의 결과에 `answer`, `solution`, `op_code` 키가 **없는지** 확인합니다. 이 한 줄짜리 테스트가 "검증이 생성의 답을 베끼는" 공통 원인 고장을 구조적으로 막습니다.

> **일치율 100%는 좋은 신호가 아니다**
>
> 독립된 두 층의 판정 일치율이 몇 주째 100%라면, 두 층이 정말 독립적인지 의심해야 합니다. 한쪽이 다른 쪽을 복사하고 있을 가능성이 있습니다(판례 P0001에서 검토 시간 중앙값 3초가 그 신호였음). R13-03은 층 간 일치율이 4주 연속 100%이면 경고합니다. 실사용 데이터가 쌓인 뒤(이식 6단계) 적용합니다.

#### ⑥ 자동 검사와 목표 강도

| 장치 | 강도 |

| 층 간 일치율 모니터링 | L4 |
