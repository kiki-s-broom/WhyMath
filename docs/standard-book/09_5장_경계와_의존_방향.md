# 5장. 경계와 의존 방향

한 줄 요약: **"누가 누구를 import해도 되는가"를 규칙으로 정하고, 도메인(핵심 논리)은 DB·AI·화면 같은 바깥 세계를 모르게 한다.**

#### ① 증상

- 한 곳을 고쳤는데 전혀 상관없어 보이는 곳이 깨짐
- 순환 import(A가 B를, B가 다시 A를 가져옴) 오류를 피하려고 함수 안에서 import하는 임시방편이 늘어남
- 학습 판정 로직 안에서 SQL을 직접 실행 → DB 없이는 테스트 불가
- 수학 전용 코드(LaTeX 처리, SymPy 호출)가 EOS 코어 곳곳에 섞여 있어 두 번째 과목을 붙일 수 없음
- AI 공급자나 모델을 바꾸려면 수십 개 파일을 고쳐야 함

#### ② 근본 결함

모듈 사이의 **의존 방향에 규칙이 없습니다.** 모든 모듈이 필요할 때마다 아무 모듈이나 가져다 쓰면, 의존 관계가 거미줄이 됩니다. 거미줄에서는 한 가닥을 당기면 전체가 흔들립니다. 특히 가장 오래 살아남아야 할 **핵심 규칙(도메인)**이 가장 자주 바뀌는 **바깥 기술(DB 드라이버, AI SDK, 화면)**에 묶이는 것이 치명적입니다.

#### ③ 업계 표준

핵심 원칙은 **의존성 규칙**(Dependency Rule)입니다. 의존 화살표는 항상 **바깥에서 안쪽으로만** 향합니다. 안쪽(도메인)은 바깥(DB·AI·UI)의 존재를 모릅니다. 안쪽이 바깥 기능을 써야 할 때는 안쪽이 **포트**(port: "이런 기능이 필요하다"는 약속, 즉 인터페이스)를 정의하고, 바깥이 **어댑터**(adapter: 그 약속을 실제 기술로 구현한 것)를 끼웁니다. 이것을 **의존성 역전**(DIP: 구체적인 것이 추상적인 것에 의존하게 뒤집는 것)이라 합니다.

| 이름 | 출처 | 핵심 |
|---|---|---|
| 헥사고날 아키텍처 (포트와 어댑터) | Alistair Cockburn, 2005 | 도메인을 가운데 두고 모든 외부 기술을 어댑터로 교체 가능하게 |
| 클린 아키텍처 | Robert C. Martin, 2012 블로그 → 2017 책 | 동심원 계층, 의존은 안쪽으로만 |
| SOLID의 D (의존성 역전 원칙) | Robert C. Martin, 1990년대 | 상위 정책이 하위 세부를 모르게 |
| 깊은 모듈 (deep module) | John Ousterhout, 『A Philosophy of Software Design』 2018 | 인터페이스는 좁고 단순하게, 기능은 깊게 — 경계를 넘는 정보량을 줄임 |
| import-linter | Python 도구 (David Seddon) | 계층·금지·독립 규칙을 설정 파일로 선언하고 CI에서 검사 |

가장 강한 경계는 **물리적 분리**입니다. Flutter(Dart) 쪽은 코어와 과목을 **별도 패키지**로 나누면, `pubspec.yaml`에 의존성을 선언하지 않은 패키지는 import 자체가 불가능해집니다. 규칙 검사(L5)보다도 강한, 구조로 막는 방식입니다.

#### ④ 원전

- Robert C. Martin, 『클린 아키텍처』(2017), 22장 "클린 아키텍처"
- Alistair Cockburn, "Hexagonal Architecture" (2005, alistair.cockburn.us)
- import-linter 공식 문서 — contract 종류: layers(계층), forbidden(금지), independence(독립)

#### ⑤ WhyMath 적용 — EOS의 4계층

| 계층 (안→밖) | 패키지 | 알아도 되는 것 | 몰라야 하는 것 |
|---|---|---|---|
| 1 코어 | `eos_core` | 파이썬 표준 라이브러리, Pydantic | 과목·DB·AI SDK·웹 프레임워크 |
| 2 과목 | `subject_math` (이후 `subject_chem` …) | `eos_core` | 다른 과목, DB·AI SDK |
| 3 인프라 | `infra` (PostgreSQL, AI API, OCR) | `eos_core`, 과목 | API·화면 |
| 4 진입점 | `api` (서버 엔드포인트, 배치 CLI) | 전부 | — |

**import-linter 설정 예시**

```ini
# .importlinter — 의존 방향 규칙 (lint-imports 명령으로 검사)
[importlinter]
root_packages =
    eos_core
    subject_math
    infra
    api
include_external_packages = True   # 외부 라이브러리(psycopg 등) import도 검사 대상에 포함

[importlinter:contract:layers]
name = 계층 규칙 — 위는 아래를 쓸 수 있지만 아래는 위를 모른다
type = layers
layers =
    api
    infra
    subject_math
    eos_core

[importlinter:contract:core-pure]
name = 코어는 DB 드라이버·AI SDK를 직접 모른다
type = forbidden
source_modules =
    eos_core
forbidden_modules =
    psycopg
    anthropic
    openai
```

**포트와 어댑터 (Python)**

```python
# eos_core/ports.py — 코어가 정의하는 '포트' (필요한 기능의 약속만, 구현 없음)
from typing import Protocol
from eos_core.models import Item

class ItemRepository(Protocol):
    """문항 저장소 포트. 실제 PostgreSQL 구현은 infra/가 제공한다."""
    def get(self, item_id: str) -> Item | None: ...
    def save_candidate(self, item: Item) -> str: ...

class Generator(Protocol):
    """문항 생성기 포트. Claude든 로컬 LLM(Ollama)이든 이 약속만 지키면 교체 가능."""
    def generate(self, node_id: str, op_code: str) -> dict: ...

# infra/pg_repository.py — 바깥 계층이 포트를 구현하는 '어댑터'
# import psycopg                      ← 인프라 계층이므로 허용
# class PgItemRepository:             ← ItemRepository 약속을 만족하면 코어는 차이를 모름
#     ...
```

이 구조의 실질적 이득은 세 가지입니다. 코어 로직을 **DB와 AI 없이 1초 안에 테스트**할 수 있고(12장), 생성 모델을 Claude에서 로컬 LLM으로 바꿔도 **어댑터 한 파일만** 바뀌며, 과목 추가 시 코어를 건드리지 않습니다(28장).
