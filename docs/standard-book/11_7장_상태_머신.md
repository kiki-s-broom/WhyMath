# 7장. 상태 머신

한 줄 요약: **데이터가 거칠 수 있는 상태와 허용된 전이(이동)를 표로 선언하고, 표에 없는 이동은 기계가 거부하게 한다.**

#### ① 증상

- `status='published'`인데 `is_rejected=true`인 문항 — 불가능해야 할 조합이 DB에 존재
- 상태를 바꾸는 코드가 여기저기 흩어져, 누가 언제 상태를 바꿨는지 추적 불가
- 검토를 거치지 않은 문항이 `candidate`에서 곧장 `published`로 이동
- 학습자가 숙달 게이트를 통과하지 않았는데 다음 단계로 진행됨

#### ② 근본 결함

상태와 전이가 **암묵적**입니다. 상태를 여러 플래그(불리언 컬럼)로 쪼개 저장하면 플래그 n개로 2ⁿ개 조합이 생기고, 그중 대부분은 의미 없는 조합입니다. 또 "어떤 상태에서 어떤 상태로 갈 수 있는가"가 코드 곳곳의 if문에 흩어져 있어 전체 그림을 누구도 모릅니다.

#### ③ 업계 표준

| 표준 | 핵심 아이디어 |
|---|---|
| 유한 상태 기계 (FSM) | 상태의 목록 + 허용된 전이의 목록. 전이표에 없는 이동은 불가능 |
| 상태차트 (Statecharts) | David Harel, 1987. 계층·병렬 상태로 복잡한 흐름 표현. XState(JS)가 대표 구현 |
| 불가능한 상태를 표현 불가능하게 | Yaron Minsky(Jane Street), 2011. 데이터 구조 자체가 모순 조합을 담을 수 없게 설계 |
| 이벤트 로그 | 상태 변경을 '사건'으로 기록(누가·언제·무엇에서 무엇으로) → 이력 추적과 재생 가능 (23장 이벤트 소싱) |

#### ④ 원전

- David Harel, "Statecharts: A Visual Formalism for Complex Systems", Science of Computer Programming (1987)
- PostgreSQL 공식 문서 — 트리거(`CREATE TRIGGER … EXECUTE FUNCTION`, 11 버전부터 이 문법)

#### ⑤ WhyMath 적용 — 문항 생명주기

| 현재 상태 | 허용된 다음 상태 | 전이를 일으키는 노드(1장) |
|---|---|---|
| draft | candidate | generate (계약 파싱 통과) |
| candidate | verified / rejected | derive_verify |
| verified | accepted / rejected | human_review (F1~F8) |
| accepted | published | publish (세 게이트 기록 필수, 2장) |
| published | quarantined / retired | 문항 통계 이상(24장) / 교육과정 개편 |
| quarantined | verified / retired | 재검토 |

**전이표 + 트리거 (PostgreSQL 11+)**

```sql
-- 전이표: 허용된 이동만 행으로 등록 (표 자체가 상태 기계의 원본)
CREATE TABLE item_transitions (
    from_state TEXT NOT NULL,
    to_state   TEXT NOT NULL,
    PRIMARY KEY (from_state, to_state)
);
INSERT INTO item_transitions VALUES
  ('draft','candidate'), ('candidate','verified'), ('candidate','rejected'),
  ('verified','accepted'), ('verified','rejected'), ('accepted','published'),
  ('published','quarantined'), ('published','retired'),
  ('quarantined','verified'), ('quarantined','retired');

-- 전이 검사 트리거: 표에 없는 이동이면 DB가 거부 (앱 코드를 우회해도 막힘 = L5)
CREATE OR REPLACE FUNCTION check_item_transition() RETURNS trigger AS $$
BEGIN
  IF NEW.status IS DISTINCT FROM OLD.status AND NOT EXISTS (
       SELECT 1 FROM item_transitions
       WHERE from_state = OLD.status AND to_state = NEW.status) THEN
    RAISE EXCEPTION '허용되지 않은 상태 전이: % → % (문항 %)', OLD.status, NEW.status, OLD.item_id;
  END IF;
  -- 전이 이력은 사건으로 남긴다 (누가·언제)
  INSERT INTO item_events (item_id, from_state, to_state, actor, at)
  VALUES (OLD.item_id, OLD.status, NEW.status, current_setting('app.actor', true), now());
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_item_transition
  BEFORE UPDATE OF status ON items
  FOR EACH ROW EXECUTE FUNCTION check_item_transition();
```

`current_setting('app.actor', true)`는 연결마다 `SET app.actor = 'kiki'` 또는 `'bot:publisher'`처럼 설정한 행위자 이름을 읽습니다(설정이 없으면 NULL). 이 트리거가 있으면 `is_published`, `is_reviewed` 같은 플래그 컬럼은 필요 없으므로 제거합니다(R7-01). 상태의 원본은 `status` 한 컬럼뿐입니다.

학습자 쪽도 같습니다. 7단계 학습 파이프라인(진단 게이트 → … → 숙달 게이트)은 학습자별 상태 기계이며, "숙달 게이트를 통과해야 다음 단계"는 전이표의 한 줄로 표현됩니다. 숙달 판정 자체의 재현성은 23장에서 다룹니다.

#### ⑥ 자동 검사와 목표 강도

| 장치 | 강도 |
|---|---|
| 전이 트리거 + 전이 테스트(허용 전이 전부 성공, 금지 전이 전부 실패) | L5 |
| 스키마 검사: items 테이블에 `is_`로 시작하는 상태 플래그 컬럼 없음 | L5 |
