# 3장. 멱등성 — 다시 실행해도 안전하게

한 줄 요약: **같은 작업을 1번 하든 10번 하든 결과가 같도록 만들면, 실패는 "다시 돌리면 끝"이 된다.**

#### ① 증상

- 스크립트가 중간에 죽음 → 다시 돌리면 **앞부분 데이터가 중복**으로 들어감
- "깨끗하게 처음부터" 하려고 DB를 비우고 다시 적재 → 그 사이 쌓인 검토 기록까지 날아감
- AI 문항 생성 배치를 두 번 실행했더니 **문항 수가 두 배**, API 비용도 두 배
- 실패한 작업을 어디서부터 다시 해야 하는지 몰라 로그를 뒤짐

#### ② 근본 결함

작업이 **"무엇을 하라"(명령)** 기준으로 설계돼 있고, **"어떤 상태가 되어야 한다"(목표 상태)** 기준이 아닙니다. 명령형 작업은 실행 횟수만큼 효과가 누적됩니다. 목표 상태형 작업은 이미 그 상태면 아무것도 하지 않습니다.

#### ③ 업계 표준

**멱등성**(idempotency)은 수학에서 온 말입니다. 함수 f가 f(f(x)) = f(x)를 만족하면 멱등이라 합니다. 절댓값 |x|가 대표적입니다 — ||−3|| = |−3| = 3. 소프트웨어에서는 "같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같다"는 뜻입니다.

| 기법 | 방법 | 대표 사례 |
|---|---|---|
| 자연키 + UPSERT | 데이터의 고유한 이름표로 "없으면 넣고, 있으면 갱신/무시" | PostgreSQL `INSERT … ON CONFLICT` (9.5 버전, 2016년부터) |
| 멱등 키 | 요청마다 고유 키를 붙이고 서버가 키를 기억 | Stripe 결제 API의 `Idempotency-Key` 헤더 |
| HTTP 메서드 규약 | GET·PUT·DELETE는 멱등, POST는 아님 | RFC 9110 (HTTP 의미론, 2022) |
| 체크포인트 | 단위 작업마다 완료 표식을 남기고 완료분은 건너뜀 | Airflow 작업 상태, Spark 체크포인트 |
| 원자적 교체 | 임시 파일에 다 쓴 뒤 이름 바꾸기(rename)로 한 번에 교체 | 반쯤 쓴 파일이 남지 않음 |
| 선언형 도구 | "이 상태가 되어라"를 선언하고 도구가 차이만 적용 | Terraform, Kubernetes |

#### ④ 원전

- RFC 9110 "HTTP Semantics" 9.2.2절 Idempotent Methods
- Stripe API 문서, "Idempotent requests"
- Kleppmann, 『데이터 중심 애플리케이션 설계』 11장 — 정확히 한 번 처리(exactly-once)와 멱등성

#### ⑤ WhyMath 적용 — AI 생성의 멱등성은 '출력'이 아니라 '자리'로

AI 문항 생성에는 특별한 어려움이 있습니다. **같은 요청을 보내도 AI의 출력은 매번 다릅니다.** 그래서 출력 내용의 해시를 키로 쓰면 재실행할 때마다 새 문항이 생깁니다. 해법은 **생성 요청의 '자리'(슬롯)를 키로 삼는 것**입니다. "개념 노드 X, 오답 유형 OP_03, 3번째 문항"이라는 자리는 몇 번을 실행해도 같습니다. 자리가 이미 채워졌으면 AI를 다시 부르지 않습니다.

**슬롯 키 기반 생성 (Python)**

```python
# generate_batch.py — 재실행해도 문항이 중복되지 않는 생성 배치
import hashlib
import json
import logging
import psycopg  # PostgreSQL 드라이버 v3. 설치: pip install "psycopg[binary]"

log = logging.getLogger("generate")

def slot_key(node_id: str, op_code: str, seq: int) -> str:
    """생성 요청 '자리'의 고유 키. AI 출력이 달라도 자리는 같다."""
    raw = f"{node_id}|{op_code}|{seq}"
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]

def generate_if_missing(conn, node_id: str, op_code: str, seq: int, generate_fn) -> str:
    key = slot_key(node_id, op_code, seq)
    try:
        with conn.cursor() as cur:
            # 1) 이미 채워진 자리면 AI를 부르지 않는다 → 비용·중복 방지
            cur.execute("SELECT 1 FROM items WHERE slot_key = %s", (key,))
            if cur.fetchone():
                return "skip"
            # 2) AI 호출 (실패하면 예외 → 아래 except에서 처리, 이 자리는 비어 있는 채로 남음)
            item = generate_fn(node_id, op_code)
            # 3) 동시에 두 번 실행돼도 한 행만 남도록 ON CONFLICT
            cur.execute(
                """INSERT INTO items (slot_key, node_id, op_code, body, status)
                   VALUES (%s, %s, %s, %s, 'candidate')
                   ON CONFLICT (slot_key) DO NOTHING""",
                (key, node_id, op_code, json.dumps(item, ensure_ascii=False)),
            )
        conn.commit()
        return "created"
    except Exception:
        conn.rollback()                               # 반쯤 쓴 상태를 남기지 않음
        log.exception("생성 실패: %s %s #%d", node_id, op_code, seq)
        return "failed"                               # 다음 실행 때 자동으로 재시도됨
```

**필수 제약 조건**

```text
-- 전제: slot_key에 UNIQUE 제약이 있어야 ON CONFLICT가 동작한다
ALTER TABLE items ADD CONSTRAINT items_slot_key_uq UNIQUE (slot_key);
```

이 구조에서는 배치가 300개 중 170번째에서 죽어도 그냥 다시 실행하면 됩니다. 앞의 169개는 `skip`, 실패한 170번째부터 다시 생성됩니다. "어디서부터 다시 해야 하지?"라는 질문 자체가 사라집니다.

백업에도 같은 원리가 적용됩니다. 현재 백업(매일 03:00, git bundle + pg_dump, age 암호화, 30개 보관)의 파일 이름이 날짜 기반이라면 같은 날 두 번 실행돼도 같은 파일을 덮어쓸 뿐이므로 멱등합니다. 다만 **덮어쓰기 도중 실패하면 그날 백업이 깨진 채로 남을 수 있으므로**, 임시 이름으로 쓰고 완료 후 rename하는 원자적 교체를 권합니다(16장에서 복원 검증과 함께 다룸).

#### ⑥ 자동 검사와 목표 강도

가장 강력한 검사는 단순합니다. **두 번 실행해 보고 결과가 같은지 비교**하는 테스트입니다.

**pytest 예시**

```python
# tests/test_idempotency.py — '두 번 실행 테스트'
def test_batch_is_idempotent(test_db, fake_generator):
    run_batch(test_db, generator=fake_generator)      # 1회차
    first = count_rows(test_db, "items")
    run_batch(test_db, generator=fake_generator)      # 2회차 (같은 입력)
    second = count_rows(test_db, "items")
    assert first == second, "재실행 시 행 수가 늘어남 → 멱등성 깨짐"
    assert fake_generator.calls == first, "이미 채운 자리에 AI를 다시 호출함 → 비용 낭비"
```

| 장치 | 강도 |
|---|---|
| 모든 배치 스크립트에 '두 번 실행 테스트' 필수 (CI) | L5 |
| `items.slot_key` UNIQUE 제약 | L5 (코드 실수가 있어도 DB가 중복을 거부) |
| 배치 종료 시 created/skip/failed 개수 요약 출력 | L4 |
