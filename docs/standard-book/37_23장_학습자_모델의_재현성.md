# 23장. 학습자 모델의 재현성

한 줄 요약: **학습자의 응답(사건)을 원본으로 보관하고, 숙달 확률(상태)은 버전이 붙은 모델로 계산한 파생물로 다룬다. 그래야 어떤 판정이든 다시 계산하고 설명할 수 있다.**

#### ① 증상

- BKT 파라미터를 조정했더니 "이 학생이 왜 숙달 판정을 받았는지" 설명할 수 없음
- 모델 업데이트 날 많은 학생의 숙달 상태가 한꺼번에 뒤집힘 → 학생·교사 혼란
- 같은 응답 기록인데 다시 계산하면 다른 결과
- 두 모델(BKT vs AKT) 중 무엇이 나은지 공정하게 비교할 방법이 없음

#### ② 근본 결함

**상태만 저장하고 원천을 버립니다.** 현재 숙달 확률만 덮어쓰며 저장하면, 그 값이 어떤 응답들과 어떤 모델로 계산됐는지 사라집니다. 4장의 언어로 말하면, 원본(응답)과 파생물(숙달 확률)이 뒤바뀐 상태입니다.

#### ③ 업계 표준

| 표준 | 핵심 |
|---|---|
| 이벤트 소싱 (Event Sourcing) | Martin Fowler(2005)·Greg Young. 상태가 아니라 **사건**을 추가 전용으로 저장하고, 상태는 사건을 재생해 계산 |
| BKT (베이지안 지식 추적) | Corbett & Anderson(1995). 파라미터 4개: 초기 숙달 P(L₀), 학습 P(T), 추측 P(G), 실수 P(S) |
| 모델 퇴화 방지 | 추측·실수 확률이 지나치게 크면 '모를수록 맞히는' 비논리적 모델이 됨. 문헌에서는 추측 ≤ 0.3, 실수 ≤ 0.1 같은 상한을 흔히 둠 (Baker·Corbett·Aleven, 2008) |
| 모델 버전·재현성 | 모델 레지스트리(MLflow 등), 난수 시드 고정, 파라미터 파일 해시를 판정 기록에 남김 |
| 섀도 배포·재생 비교 | 새 모델을 실제 판정 없이 병행 실행하거나 과거 응답을 재생해, 판정이 얼마나 바뀌는지 먼저 측정 |

#### ④ 원전

- A. T. Corbett & J. R. Anderson, "Knowledge Tracing: Modeling the Acquisition of Procedural Knowledge", User Modeling and User-Adapted Interaction (1995)
- R. S. Baker, A. T. Corbett, V. Aleven, "More Accurate Student Modeling through Contextual Estimation of Slip and Guess Probabilities in BKT", ITS 2008
- pyBKT (Badrinath·Wang·Pardos, 2021) — Python BKT 구현

**BKT 갱신과 재생 (Python)**

```python
# eos_core/knowledge_tracing/bkt.py — 버전이 붙은 BKT 갱신 (R23-02, R23-03)
from dataclasses import dataclass

MODEL_VERSION = "bkt-2026.10.1"          # 파라미터나 식이 바뀌면 반드시 올림
MASTERY_EXIT = 0.95                      # 숙달 게이트 출구 기준

@dataclass(frozen=True)
class BKTParams:
    p_init: float    # P(L0) 처음부터 알고 있을 확률
    p_learn: float   # P(T)  한 번의 기회로 새로 알게 될 확률
    p_guess: float   # P(G)  모르는데 맞힐 확률 (퇴화 방지: ≤ 0.3)
    p_slip: float    # P(S)  아는데 틀릴 확률   (퇴화 방지: ≤ 0.1)

    def __post_init__(self):
        for name in ("p_init", "p_learn", "p_guess", "p_slip"):
            v = getattr(self, name)
            if not 0.0 <= v <= 1.0:
                raise ValueError(f"{name}={v} 는 0~1 범위 밖")
        if self.p_guess > 0.3 or self.p_slip > 0.1:
            raise ValueError(f"퇴화 위험: guess={self.p_guess}, slip={self.p_slip}")

def update(p_known: float, correct: bool, prm: BKTParams) -> float:
    """응답 1건을 반영한 다음 숙달 확률 (베이즈 갱신 → 학습 전이)."""
    if correct:
        num = p_known * (1 - prm.p_slip)
        den = num + (1 - p_known) * prm.p_guess
    else:
        num = p_known * prm.p_slip
        den = num + (1 - p_known) * (1 - prm.p_guess)
    posterior = num / den if den > 0 else p_known
    nxt = posterior + (1 - posterior) * prm.p_learn
    return min(max(nxt, 0.0), 1.0)          # 부동소수 오차로 1.0을 넘지 않게 (판정 버그 방지)

def replay(responses: list[bool], prm: BKTParams) -> float:
    """응답 이벤트를 처음부터 재생해 현재 숙달 확률을 계산 — 언제 다시 해도 같은 결과."""
    p = prm.p_init
    for c in responses:
        p = update(p, c, prm)
    return p
```

**추가 전용 응답·판정 기록 (PostgreSQL)**

```sql
-- 응답 이벤트는 추가만 가능 (R23-01): 수정·삭제를 DB가 거부
CREATE OR REPLACE FUNCTION forbid_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION '응답 이벤트는 수정·삭제할 수 없습니다 (헌법 제8조의2). 정정은 새 이벤트로 기록하세요.';
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_responses_append_only
  BEFORE UPDATE OR DELETE ON responses
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();
-- 주의: TRUNCATE는 행 단위 트리거를 거치지 않으므로 문장 단위 트리거로 따로 막는다
CREATE TRIGGER trg_responses_no_truncate
  BEFORE TRUNCATE ON responses
  FOR EACH STATEMENT EXECUTE FUNCTION forbid_mutation();

-- 숙달 판정 기록: 어떤 모델 버전으로 계산했는지 필수 (R23-02)
CREATE TABLE mastery_decisions (
    learner_id    BIGINT      NOT NULL,
    node_id       TEXT        NOT NULL,
    p_known       REAL        NOT NULL,
    passed        BOOLEAN     NOT NULL,
    model_version TEXT        NOT NULL,
    decided_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

이 SQL은 PostgreSQL 16에서 실제로 실행해 확인했습니다. 확인 중에 **`TRUNCATE`(테이블 비우기)는 행 단위 트리거를 거치지 않아 모든 응답이 지워진다**는 구멍을 발견해 문장 단위 트리거를 추가했습니다. 또 트리거는 테이블 **소유자**가 끌 수 있으므로(`ALTER TABLE … DISABLE TRIGGER`), 앱과 AI가 쓰는 DB 계정은 테이블 소유자가 아닌 별도 계정이어야 L5가 성립합니다(7장 전이 트리거도 같음).

단, 법적으로 삭제해야 하는 경우(회원 탈퇴 시 개인정보 파기 등, 26장)는 예외 절차가 필요합니다. 이 경우 트리거를 우회하는 전용 관리 함수로만 삭제하고, 삭제 사실(누구의 데이터를 언제 파기했는지, 내용 없이)을 기록합니다. "추가 전용"과 "파기 의무"는 충돌하는 요구이므로 **설계 단계에서 함께** 다뤄야 합니다.

> **모델 변경 배포 게이트 (R23-04)**
>
> 새 파라미터나 AKT 모델로 바꾸기 전에, 과거 응답 전체를 두 모델로 재생해 **판정이 뒤집히는 학습자 비율**(flip rate)을 계산하고 보고서를 남깁니다. 기준(예: 5% 이하)은 운영 정책으로 정하되, 기준을 넘으면 섀도 배포 기간을 거칩니다. 실사용 응답이 쌓이는 공개 이후(이식 6단계)부터 적용합니다.
