# 구조화 에러코드 체계 (OPS-82)

> 정본 코드: `src/backend/whymath_backend/api/_error_codes.py` · 거버넌스 테스트: `tests/backend/api/test_error_codes.py`

## 1. 왜 필요한가
- 판정 기준 `main 8a5ea4d1`(2026-10-08) 실측: `src/backend`의 예외 클래스 **57종**(등재 당시 34종에서 증가), `error_code` 식별자는 도입 전 **0건**.
- API 에러는 `detail`(한국어 문장)으로만 나갔다. 문장은 바뀌고 변수가 섞여 "같은 종류의 실패"를 세려면 문장을 파싱해야 한다 → 12월 판정의 장애 분석 근거가 없다.

## 2. `GenerationFailureCode`(F1~F8)와의 관계 (acceptance ②)
| 축 | 대상 | 형식 | 정본 |
|---|---|---|---|
| `GenerationFailureCode` | *콘텐츠* 생성 실패 분류 | `F1`~`F8` | 검증설계서(EOS-51 동결) |
| 에러코드(이 문서) | *시스템* 에러 | `WM-<계열>-<NNN>` | 이 문서 |

형식이 갈라 충돌이 불가능하며, 거버넌스 테스트가 두 집합의 교집합 0을 단언한다.

## 3. 부여 규칙 (acceptance ⑥)
1. 형식 `WM-<FAMILY>-<NNN>` — FAMILY는 닫힌 집합(`FAMILIES`), NNN은 계열 내 3자리 일련번호.
2. **안정성 보증**: 배포된 코드는 의미 변경·재사용 금지. 폐기는 삭제가 아니라 `deprecated=True`.
3. 코드는 고정 문자열이다 — 필드값·시크릿을 담지 않는다(침묵 실패 금지 계약 ④와 동일).
4. 적용 범위 = **신규 예외 + 학생 대면 API 경로**. 기존 57종 전건 소급은 후속 태스크로 분리했다.
5. 하위 호환: 응답은 종전 `detail`을 유지하고 **옆에** `error_code`를 더한다.

## 4. 현행 코드표 (집행 지점 포함 — acceptance ⑤)
| 코드 | HTTP | 재시도 | 의미 | 싣는 지점 |
|---|---|---|---|---|
| `WM-RATE-001` | 429 | 가능 | 분당 호출 한도 초과(사용자·IP 공통) | `api/_rate_limit.py` 2곳 → `CodedHTTPException` |
| `WM-CLIENT-001` | 426 | 불가 | 앱 버전이 최소 지원 버전 미만 | `app.py` 버전 게이트 응답 |

- **응답 스키마**: `{"detail": <기존 문장>, "error_code": "WM-…"}` — 핸들러는 `app.py`의 `CodedHTTPException` 핸들러.
- **로그**: 핸들러가 `에러코드 응답 — <코드> (<예외 타입명>)`을 INFO로 남긴다(문장·필드값 제외).
- **분류 안 됨**: 코드가 없는 예외는 `error_code_of()`가 `WM-UNCLASSIFIED-000`을 돌려준다 — "없음"과 "미분류"를 구분해 보이게 한다. 이 값은 레지스트리에 등록되지 않는다.

## 5. 집행 (정본화≠집행)
`test_error_codes.py`가 AST로 소스 전체를 스캔한다: ①소스 속 코드 리터럴·`CodedHTTPException` 첫 인자가 전부 등록됨 ②등록된 코드(폐기 제외)는 최소 1곳에서 실제로 쓰임(허수 방지) ③스캔 0건은 실패(공허 통과 방지). 결함 주입 실측: 미사용 코드 등록 → RED, 핸들러 제거 → RED.
