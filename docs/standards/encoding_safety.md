**T1~T3은 정보가 보존돼 있다.** 잘못 읽었을 뿐 바이트 대응이 1:1이라 되돌릴 수 있다.
**T4~T5는 정보가 사라졌다.** U+FFFD나 `?` 하나가 원래 어떤 바이트였는지 알 방법이 없다.

> **가장 중요한 구분**: T7은 *손상이 아니다*. 파일은 정상인데 터미널만 깨진 것이다.
> 여기서 "고치려고" 파일을 다시 저장하면 T7(무해)이 T3(유해)이 된다.

## 2. 사고를 키우는 단 하나의 행동 — 깨진 채로 저장

```
cp949 원본
   ↓ UTF-8로 잘못 읽음        ← 여기까지는 화면만 깨진 상태(복구 쉬움)
깨진 문자열
   ↓ UTF-8로 저장             ← 이 순간 손상이 파일에 굳는다
깨진 문자열이 실제 파일 내용
```

그래서 **손상을 발견하면 첫 행동은 "저장하지 않기"** 다.

VS Code라면 `Save with Encoding`이 아니라 **`Reopen with Encoding` → Korean (CP949)**
를 먼저 시도한다. 정상으로 보이면 그때 `Save with Encoding` → UTF-8 한다.

## 3. Python에서 — `errors="replace"`가 손상을 만든다

```python
# ❌ 변환 작업에 쓰면 안 된다 — T4를 스스로 만든다
open("data.txt", encoding="utf-8", errors="replace")

# ✅ 안전한 변환: 바이트로 읽고 → 정확한 인코딩으로 디코드 → UTF-8로 인코드
from pathlib import Path
raw = Path("input.txt").read_bytes()
text = raw.decode("cp949")          # 틀리면 UnicodeDecodeError로 즉시 멈춘다(좋은 일이다)
Path("input_utf8.txt").write_text(text, encoding="utf-8", newline="")
```

`UnicodeDecodeError`는 **버그가 아니라 안전장치**다. `errors="replace"`/`"ignore"`는
그 안전장치를 끄고 T4/T5를 만든다. 진단용으로는 쓸 수 있어도 **원본 변환에는 쓰지
않는다.**

> 이 저장소의 실사례: `ruleset_drift.py`의 `read_json_text`는 `utf-8-sig`·`utf-16`을
> **순서대로 시도**하고 전부 실패하면 예외를 던진다 — `errors=` 를 쓰지 않는다.
> 다만 그 폴백은 *인코딩*만 가리므로 ④축(디코딩 왕복으로 바이트가 **유실된** 파일)은
> 막지 못한다. 손상된 파일은 UTF-8로 멀쩡히 디코딩되고 JSON 단계에서야 깨진다.

## 4. 반대 방향 — UTF-8을 cp949로 저장하면 T5가 된다

cp949에 없는 문자가 많다: `✓ → ① 𝑥 ∑ ≠ ⟨⟩`. 이 프로젝트는 수식·DSL·JSON이 많아
특히 위험하다.

```python
"𝑥² + 𝑦²".encode("cp949")   # UnicodeEncodeError — 정상 동작이다
```

문제는 어떤 프로그램이 이것을 `?² + ?²`로 **조용히 바꿔 버리는** 경우다. 그 순간
원래 문자를 알아낼 방법이 없다(T5).

**그래서 소스·JSON·YAML·Markdown·DSL·SQL·프롬프트는 UTF-8로 통일한다.** cp949는
외부 입력에서만 허용하고 **ingestion 경계에서 변환**한다.

## 5. 경계 설계 — 저장소 안은 UTF-8 전용, 예외는 *선언*한다

```
외부 cp949 입력
      ↓
  Import Boundary   ← 여기서 명시적으로 decode("cp949") → UTF-8
      ↓
  저장소 내부 = UTF-8 only
```

**단 하나의 예외**: `data/licenses/snapshots/**`. 외부 사이트가 서빙한 바이트
*그대로*가 법적 증거이므로 변환하면 증거가 훼손된다(실사례: 학교알리미가 euc-kr로
서빙).

이 예외를 **경로로 통째 면제하지 않는다.** 그러면 그 디렉터리에서 생기는 진짜 손상도
함께 통과한다. 대신 옆의 `*.meta.json`이 `content_type`에 선언한 charset과 대조해
**선언했고 그 선언대로 디코딩되는** 경우에만 통과시킨다.

```json
{ "content_type": "text/html; charset=euc-kr", "sha256": "c31a4c81…" }
```

선언이 없으면 위반이다. 선언과 실측이 어긋나도 위반이다.

## 6. 줄바꿈도 바이트다 — 2026-09-14 실측 사고

라이선스 스냅샷 20건 중 **5건의 sha256이 기록과 어긋나 있었다.**

원인은 인코딩이 아니라 **줄바꿈**이었다. `.gitattributes`에 `.html` 규칙이 없어 Git
기본 `text auto`가 CRLF를 LF로 정규화했고, 그만큼 바이트가 줄어 해시 검증이 깨졌다.

| 소스 | 기록 | 저장 | 차이 | LF 개수 | 판정 |
|---|---:|---:|---:|---:|---|
| ncic | 91,391 | 89,416 | 1,975 | 1,975 | **차이 = LF 개수** → CRLF 복원으로 해시 일치 ✔ |
| schoolinfo | 573 | 554 | 19 | 19 | **차이 = LF 개수** → CRLF 복원으로 해시 일치 ✔ |
| illustrative-mathematics | 412,464 | 410,549 | 1,915 | 2,667 | 불일치 → 원본이 혼합 줄바꿈, 복원 불가 |
| kogl-license-types | 136,576 | 136,471 | 105 | 2,646 | 불일치 → 복원 불가 |
| omnimath | 785,690 | 785,680 | 10 | 995 | 불일치 → 복원 불가 |

**"차이 = LF 개수"가 결정적 단서다.** 모든 줄이 원래 CRLF였다면 정규화로 사라진
바이트 수가 정확히 줄 수와 같다. 그 두 건은 되돌려 해시가 일치했다. 나머지는 원본이
혼합 줄바꿈이라 *어느 줄이* CRLF였는지 결정할 수 없어 원리적으로 복원 불가다
(전건 복원은 오버슈트, 부분 복원은 조합 폭발).

**재발 차단**: `.gitattributes`에 `data/licenses/snapshots/** -text`.
**복원 불가분 처리**: `stored_sha256`과 `integrity_note`를 meta에 기록해 **사실을
남기고** 통과시킨다. 기록 없이 통과시키면 깨진 증거가 멀쩡한 것으로 위장되고,
무조건 위반으로 두면 고칠 수 없는 위반을 상시 보고해 사람이 가드를 끄게 된다.
재수집 판정은 `OPS-79`가 소유한다.

## 7. 기계 집행 — `scripts/ops/cp949_guard.py`

```bash
python3 scripts/ops/cp949_guard.py          # 전수 검사
python3 scripts/ops/cp949_guard.py --json   # 기계 판독
```

종료 코드: `0`=정합 · `1`=위반 · `2`=측정 실패(대상 0건·git 조회 불가).
**스캔 0건은 통과가 아니라 실패다** — 대상을 하나도 못 찾은 전수 가드는 공허하게
초록을 낸다.

| 축 | 검사 | 면제 |
|---|---|---|
| **A** | U+FFFD 포함 | **없음** (T4 — 이미 정보가 사라진 상태) |
| **B** | UTF-8 디코딩 실패 | 스냅샷 + meta charset 선언 |
| **C** | mojibake (T1·T2·T3) | 파일 내 `encoding-guard: allow-mojibake` 마커 |
| **D** | 선언 ↔ 실측 불일치 | 없음 |
| **E** | 스냅샷 sha256 무결성 | `integrity_note` + `stored_sha256` 기록 |

### A축에는 면제가 없다 — 그래서 *문자를 박지 않는다*

U+FFFD를 설명하려면 그 문자를 예시로 보이고 싶어진다. 그런데 A축은 면제가 없으므로
그렇게 쓴 파일은 즉시 위반이 된다 — **이 문서와 가드 소스가 실제로 그렇게 잡혔다**
(2026-09-14). 이것은 가드의 결함이 아니라 의도된 동작이다: "예시니까 괜찮다"를
허용하는 순간 진짜 손상도 같은 변명으로 들어온다.

그러므로 규율은 하나다 — **U+FFFD는 문자로 쓰지 말고 코드포인트 이름으로 적는다.**
코드에서 필요하면 리터럴이 아니라 이스케이프(`"\uFFFD"`)를 쓴다. C축의 mojibake
예시는 정보가 보존된 형태라 마커로 허용하지만, A축은 그 예외조차 두지 않는다.

### C축은 패턴 열거가 아니라 산출물 검사다

"이 문자를 쓰지 마라" 형태는 표기 변형에서 뚫리고 정당한 문자까지 잡는다. 그래서
문자열이 아니라 **구성된 결과**를 본다 — 의심 런을 latin-1 바이트로 되돌려
cp949/UTF-8로 디코딩했을 때 **실제 한글이 나오는가**.

조건이 하나 더 필요했다. 2026-09-14 실측에서 수학 연산자 런(`·×·÷`)과 분수 기호
런(`¼½¾·`)이 **우연히** 유효한 한글로 디코딩돼 오탐 6건이 났다. 진짜 한글 mojibake는
cp949/UTF-8 바이트 구조상 **반드시 라틴 글자를 포함**하지만 연산자 런은 기호뿐이다.
이 조건을 넣자:

> **실측(2026-09-14)**: 변별력 8/8(`안녕하세요`·`수학 개념 그래프`·`표면 회귀 가드`·
> `학교알리미 공시서비스` × cp949/UTF-8 두 방향) · 오탐 **0/3,511**.

## 8. 정직한 공백 — 이 가드가 못 하는 것

1. **T5(`?` 치환)는 기계로 탐지할 수 없다.** `?`는 정상 문자와 구별되지 않는다.
   그 축의 방어는 탐지가 아니라 **예방**이다(`errors="replace"/"ignore"` 금지 · §3).
2. **자동 인코딩 탐지를 쓰지 않는다.** `chardet`·`charset-normalizer`는 ASCII 위주·
   짧은 파일·한글이 몇 자 없는 파일에서 오판한다. 이 가드가 하는 것은 추측이 아니라
   **결정론적 디코딩 시도와 선언 대조**뿐이다.
3. **T3 중 "UTF-8을 cp949로 읽어 굳은" 형태**(예: `媛??`)는 C축이 잡지 못한다.
   결과가 한자·한글 범위에 떨어져 정상 텍스트와 구별이 어렵고, 그것을 잡으려 하면
   이 저장소의 정상 한국어에 오탐이 쏟아진다. 사람이 읽어서 판단할 축으로 남긴다.
4. **편집기 설정은 예방일 뿐이다.** `.editorconfig`·`.vscode/settings.json`은 편집기가
   존중해 줄 때만 유효하다. 무엇이 실제로 들어왔는지는 가드가 본다.

## 9. 사고 대응 순서

```
손상 발견
   │
   ▼
1. 저장 중단                    ← 가장 중요. 저장이 T1을 T3으로 만든다
   ▼
2. 원본 바이트 복사              cp damaged.txt damaged.original.bin
   ▼
3. Git/백업 확인                git log -- <path> · git show HEAD~1:<path>
   │  └── 정상본 있으면 → 거기서 복구 (인코딩 추측보다 항상 우선)
   ▼
4. U+FFFD / ? 존재 검사          python3 scripts/ops/cp949_guard.py
   │  ├── 없음 → 역변환 가능성 높음 (T1~T3)
   │  └── 있음 → 부분 정보 손실 (T4~T5)
   ▼
5. 후보 인코딩 테스트            cp949 / euc-kr / utf-8 을 별도 파일로
   ▼
6. 사람이 한글·수식·코드 검증
   ▼
7. UTF-8로 통일 → git diff 확인 → commit
```

**원본에 직접 작업하지 않는다.** 복구 실험은 `damaged_try_cp949.txt` 처럼 별도
파일로 한다. 깨진 파일을 열어 계속 Save 하는 것이 가장 위험하다.

### 바이트를 직접 본다

```python
from pathlib import Path
print(Path("file.txt").read_bytes()[:200].hex())
```

`가` 한 글자: UTF-8은 `EA B0 80`(3바이트), cp949는 `B0 A1`(2바이트). 바이트만 봐도
상당수는 판단할 수 있다.
