> **상태**: **채택됨(adopted) · 2026-07-18** — 업로드된 v1.0을 대체하는 초기 단계 경량 정본. (검토 근거: `../reviews/dev_constitution_review_v1.md`)
> **정본 관계(중요)**: 이 문서는 **초보자용·일상 작업용 경량 요약 헌법**이다. 프로젝트의 **심화·법령(저작권/미성년자)·아키텍처(7계층)·검증 정본은 최상위 `CLAUDE.md`**이며, 이 문서에 없는 규칙은 `CLAUDE.md`를 따른다. **두 문서가 충돌하면 `CLAUDE.md`(정본)가 우선한다.**
> **코딩 헌법과의 관계**: `constitution/`(코딩 헌법)은 이 문서·CLAUDE.md와 별개의 코딩 구조 결함 규범이며 사람(Kiki)만 개정한다. 게이트 `G-const-precedence-declaration` 결정 전까지 서열은 잠정 해석을 따른다: 더 엄격한 쪽을 따르고, 판단할 수 없으면 멈추고 Kiki에게 보고한다(`docs/standards/coding_constitution_transplant.md` §1-2).
> **정체성 노트**: **AskMath = WhyMath** (같은 프로젝트의 다른 이름·장기 로드맵 포함본). 저장소 정본 브랜드는 WhyMath이며, 이 문서는 **초기 앱 개발 단계용으로 압축한** 헌법이다. 심화 규칙은 §12 로드맵으로 미룬다.
> **적용 단계**: ① 앱 개발 ② 지식 DB 본격 구축 ③ AI 답변 기능 개발(출시 전)

## 1. 기준 정의 (모호함 방지)

- **"대규모 변경"** = 3개 파일 이상 **또는** 100줄 이상 변경. (순증 기준이 아니라 추가+삭제 합. 자동 생성물·lock 파일은 제외) *(D2 명확화)*
- **"중요 변경"** = 파일 삭제·이동, 폴더 구조 변경, DB 스키마 변경, 공개 API 변경, 데이터 일괄 수정.
- 대규모 변경과 중요 변경은 **반드시 계획을 먼저 제시하고 승인 후 진행한다.** (계획 형식 = §11)

## 2. 작업 절차

- **계획 제시 임계 = §1.** 중요·대규모 변경은 코드 작성 전에 §11 형식으로 제시한다. 소규모 작업은 형식 없이 간결하게 진행한다. *(C2 해소 — §9와 임계 일치)*
- **작업 단위 = "한 기능(관련 테스트 포함) = 한 커밋."** ‘한 파일’이 아니다 — 기능과 그 테스트는 함께 간다. *(C1 해소)*
- 작업 전 관련 파일을 **다시 읽는다.** 이전 대화의 기억만 믿고 수정하지 않는다.
- **환경 사실도 다시 확인한다.** 포트·접속 경로·프로세스 생존 같은 환경 규칙은 **실측 증거(명령 출력)** 를 확보한 뒤에만 확정한다. 부분 성공(읽기만 됨·한 번 됨)을 전체 정상으로 해석하지 않는다. *(R7)*
  【왜】 좀비 프로세스의 `/health` 응답·죽은 pid 파일을 "성공"으로 오인해 트래픽이 엉뚱한 서버로 간 실측 사고.
- 모르면 추측하지 말고 질문한다.

## 3. 절대 금지

- 요청하지 않은 파일 수정 금지.
- 요청 없는 리팩토링·코드 스타일 변경·이름 변경 금지.
- **삭제(파일/코드/데이터)는 이유·영향 범위·대체 방법을 설명하고 승인받은 후에만.** 삭제·덮어쓰기 전 대상 실물을 먼저 확인한다. *(C4 — 삭제 규칙을 여기로 통합)*
- **중복 구현 금지** — 새 함수를 만들기 전에 기존 코드를 검색하고, 있으면 재사용한다. (= §4 DRY의 실천, 한 곳에만 기술) *(C5 통합)*
- **테스트 없이 "완료" 선언 금지** — 수정 후 회귀를 검증한다. *유효한 검증의 정의는 §10.* *(R2 연결)*
- 폴더·계층·명명 규칙 임의 변경 금지. (규칙은 별도 컨벤션 문서에 정의하고, 아직 없으면 최초 확립 후 동결한다) *(D3)*

## 4. 코드 품질

- **KISS·YAGNI**: 필요 이상으로 복잡하게 만들지 않고, 지금 필요 없는 기능은 만들지 않는다.
- **DRY**: 중복 코드를 만들지 않는다. (중복 구현 금지 규칙은 §3)
- 의미가 드러나는 이름을 사용한다.
- **순환 참조 금지(코드)** — 모듈이 서로를 불러 얽히는 구조를 만들지 않는다.
  - ※ **지식 그래프의 관계는 별개다.** 개념 그래프는 본질적으로 순환적이므로 §6.1에서 따로 다룬다. *(C7 해소)*
- 예외(오류)를 무시하지 않는다. 오류 메시지는 사용자가 이해할 수 있게 쓰고, **로그를 남긴다(로깅 규칙 = §9).**

## 6. 지식 데이터 규칙 (DB 구축 단계 — 최우선)

지식 DB는 나중에 소급 수정이 거의 불가능하다. 아래 규칙은 코드 규칙보다 우선한다.

- **[ID 불변]** 모든 Entity ID는 한번 부여하면 절대 변경·재사용하지 않는다.
- **[대표 ID 유일]** 하나의 개념은 하나의 대표(Canonical) ID만 갖는다. 별칭(Alias)은 허용하되 대표는 하나뿐이다.
- **[원본 불변]** 원본(Raw) 데이터는 수정하지 않는다. 정제·가공은 반드시 사본에서 한다.
- **[출처 필수]** 모든 데이터에 출처(source)를 기록한다. 출처 없는 데이터는 DB에 넣지 않는다.
- **[검증 후 반영]** 검증되지 않은 데이터는 운영 DB에 반영하지 않는다 (초안 → 검토 → 승인 상태 구분).
- **[AI 생성 표시]** AI가 생성한 데이터는 신뢰도(confidence)와 생성 정보(모델·일시)를 함께 저장한다.
- **[버전 관리]** 데이터·스키마 변경은 버전을 남기고, 스키마 변경 시 마이그레이션 방법을 함께 제시한다.
- **[관계 등록제]** Entity 간 관계는 정해진 목록에 있는 것만 쓰고, 새 관계 유형은 승인 후 추가한다. **관계 타입은 5~8개로 상한**을 둔다. 새 타입은 "이 관계가 없으면 튜터링에서 어떤 오류가 나는가"에 답하지 못하면 기각한다. *(R9)*
- **[오개념 근거]** 오개념(Misconception) 데이터는 반드시 근거 출처와 관련 개념 연결을 갖는다.
- **[교육과정 버전]** 교육과정 데이터는 개정 시기(예: 2022 개정)를 버전으로 구분해 저장한다.

### 6.1 관계의 순환 — prerequisite만 DAG *(신규 — R5·C7 해소)*
- **prerequisite(선수) 관계만 순환 없는 DAG를 강제**하고, 관계를 추가할 때 도달성(reachability) 체크로 순환을 막는다.
- 그 외 관계는 순환을 허용하되 traversal(그래프 탐색)에서 분리한다.
- `related_to`/`similar_to` 같은 약한 관계를 traversal에 쓰지 않는다.

【왜】 개념 그래프는 본질적으로 순환적이라 "순환 전면 금지"는 비현실적이다. 선수 관계만 DAG로 지키면 커리큘럼 순서가 무너지지 않는다.

### 6.2 비가역 작업 안전장치 *(신규 — R4)*
운영 데이터 일괄수정·스키마 마이그레이션은 다음을 지킨다.
1. **백업/스냅샷 선행**
2. **사본·소량 샘플에서 리허설**
3. **롤백 절차 명시**
4. **실행 후 건수·무결성 검증**

【왜】 "지식 DB는 소급 수정 거의 불가능"이라면 실행 전 안전장치가 원본 불변 규칙만큼 중요하다.

## 7. AI 답변 기능 (개발 중 — 출시 전부터 지킬 원칙)

- **RAG 우선**: 답변 생성 전에 지식 DB 검색이 먼저다. 검색 결과에 근거해서만 답한다.
- **출처 필수**: 출처 없는 답변은 만들지 않는다. 답변에 근거(참조한 개념/문항 ID)를 함께 반환하도록 설계한다.
- **도구 검증 게이트** *(신규 — R3)*: 수학적 주장은 학생에게 노출하기 전에 도구(SymPy 등)나 검증기로 확인한다. 검증할 수 없는 구간은 보류하거나 "불확실"로 표시한다. **환각을 발견하면 조용히 넘기지 말고 로그로 남기고 수정한다.**
  【왜】 출처가 있어도 유도가 틀릴 수 있다. "출처 있음 ≠ 수학적으로 맞음."
- 불확실하면 불확실하다고 표시하고, 모르면 모른다고 답하게 설계한다.
- 답변 생성 시 참조한 데이터·규칙·모델 버전을 로그로 남긴다 (로깅 규칙 = §9).
- (초기 단계 메모) LLM은 **직접 호출하지 말고 한 군데로 감싸** 둔다 — 나중에 라우터·캐싱으로 확장하기 쉽게. 정교한 라우터 인프라는 §12로 유예.

## 8. 보안·의존성 기본

- **[시크릿]** API 키·비밀번호 등 Secret 하드코딩 금지 (.env 사용, .gitignore 등록 확인).
  - **등록 직후 자가검증** *(신규 — R8)*: 길이·형식·`…`(생략 부호) 포함 여부를 검사한다(키 값 자체는 출력하지 않는다). 예시·런북에서 복사-실행되는 위치에 자리표시자를 두지 않는다.
    【왜】 자리표시자 키(`pk-lf-…`)가 그대로 등록되어 관측이 "0건 통과"로 위장된 실측 사고.
- **[입력 검증]** 모든 외부 입력은 검증한다 (SQL Injection 등 공격 방지).
- **[개인정보]** 로그에 개인정보를 저장하지 않는다 (로깅 규칙 = §9).
- **[의존성 pin]** *(신규 — R6)* 라이브러리 버전은 검증된 범위로 **상한**을 건다(`>=x,<y`). mock(가짜) 테스트만으로 외부 SDK 정합을 선언하지 않는다 — 우리가 호출하는 메서드가 실물 SDK(핀 범위)에 존재하는지 확인한다.
  【왜】 무상한 pin이 서로 다른 메이저를 설치해 호출 표면이 어긋난 실측 사고(관측 8일 전멸의 뿌리).
- **[설정파일 인코딩]** *(신규 — R10)* 외부 도구가 로케일 인코딩(한국어 Windows=cp949)으로 읽는 설정파일(예: uvicorn `--log-config`)은 **ASCII 전용**으로 둔다. 한국어 설명은 파일이 아니라 문서/런북에.
  【왜】 한글 설정키 → 인코딩 오류로 서버 기동 실패한 실측 사고.

## 9. 로깅 정책 *(신규 절 — C6 통합·R1 포함)*

로깅 규칙이 여기저기 흩어져 상충하지 않도록 한곳에 모은다.

**남긴다(O)**
- 오류 메시지(사용자 이해 가능하게).
- **예외를 삼킬 때는 반드시 예외 타입명** — best-effort/관측 코드가 조용히 예외를 삼키더라도 예외의 **타입 이름**을 로그에 포함한다. "실패"만 남기는 무타입 경고는 금지. *(R1)*
  【왜】 무타입 경고 뒤에서 관측 쓰기가 8일간 무증상 전멸한 실측 사고.

**남기지 않는다(X)**
- 시크릿(키·비밀번호)·그 값.
- 개인정보(특히 미성년자).

## 10. 검증 정책 *(신규 절 — R2)*

"테스트 없이 완료 금지"(§3)에서 말하는 *유효한 검증*의 정의.

- **변별력**: 검증(자가점검) 스텝은 **실패 상태에서 실제로 실패 신호를 내는지** 확인된 것만 인정한다. 성공/실패 양쪽에서 같은 값을 내는 검사는 검증이 아니라 위장이다.
  【왜】 정상 상태에서도 항상 실패를 반환하던 사전점검이 검증을 위장한 실측 사고.
- **검증 권위 서열**: ① 도구/기계 증명(SymPy 등) > ② 측정 통과 > ③ 사람 눈. 가능하면 위쪽을 쓴다. 특히 AI 생성 데이터·답변은 "유닛 테스트 통과 ≠ 수학적으로 맞음"임을 기억한다.
- (정교한 6축 초인간 검증·결함주입 강등전은 출시 규모에서 — §12.)
