# 골든 벤치마크 계약 v1 — 판정기를 판정한다 (EOS-60)

> **지위**: `EOS-60-golden-benchmark-qa-confusion-matrix` 산출물 · 코드 정본 =
> `src/backend/whymath_backend/harness/golden_benchmark.py`(승격·동결) +
> `src/backend/whymath_backend/ops/qa_confusion_matrix.py`(혼동행렬 판정).
> 상위 계약: `docs/standards/eos_verification_design_v1.md` §6(내용 KPI 동결) ·
> `docs/standards/superhuman_verification_standard.md` §4.5(재채점 금지).
> 갭 근거: `docs/reviews/eos_validation_n1_n10_gap_review_2026-08-30.md` §3.7(N8).

---

## §1. 왜 필요한가 — QA 엔진은 자기 FN율을 모른다

```
현재:   생성 → QA 엔진 → PASS  →  (그대로 신뢰)
필요:   골든 200건(as-found 라벨) → QA 엔진 → 혼동행렬
                                              ├─ Precision
                                              ├─ Recall
                                              └─ FN율  ← 무관용 관리 대상
```

`harness/qa_pipeline`이 9축을 조립해 PASS/FAIL을 내지만, **그 PASS가 얼마나 믿을 만한지 잰 적이
없다**. 교육 콘텐츠에서 결정적인 실패는 **False Negative(틀린 콘텐츠를 정상이라 판정)** 이고,
EOS-51 §6이 동결한 내용 KPI 6종 중 **4종이 골든 라벨에 의존**한다(§5 결선표).

G2(10/25) 기준선의 "자동검증 ≥70%"는 자동검증이 *맞는지* 모르면 의미 없는 숫자다.

`EOS-64`(앵커 E2E 야간 골든)와 **중복이 아니다** — EOS-64는 콘텐츠를 판정하는 *승격 경로*이고,
이 계약은 **판정기를 판정하는 벤치마크 셋**이다. 의존 방향은 `EOS-64` → `EOS-60`.

## §2. 골든 셋 구축 — 별도 라벨링 캠페인 금지

**골든 라벨은 새로 만들지 않는다.** EOS-54 검수 타이머 이벤트의 `verdict`·`failure_code`가 곧
사람 라벨이므로, 필요한 것은 "검수 결과 중 무엇을 승격하고 언제 동결하는가"의 규약뿐이다
(추가 인간 시간 ≈ 0 — 검수 185 CU 예산의 부산물).

| 항목 | 값 |
|---|---|
| 규모 목표 | 앵커 6개 × **30~35건** ≈ 200건 (`ANCHOR_QUOTA_MIN/MAX`) |
| 입력 | 검수 타이머 이벤트 JSONL(EOS-54) + `cu_slug→anchor_id` 매핑 |
| 라벨 어휘 | `defective` / `clean` (as-found 기준·폐쇄 2값) |
| 결함 코드 | `GenerationFailureCode` F1~F8(EOS-51 §4 동결 enum 소비 — 신규 어휘 금지) |
| 과목 축 | `subject_id`(기본 `math`) — Validation의 Math 비종속 좌석 |

앵커 매핑이 없는 CU는 **승격하지 않는다**(앵커별 쿼터·앵커별 FN 보고가 성립하지 않으므로).
제외 건수는 리포트에 명시된다 — 조용한 제외 금지.

## §3. as-found 라벨 무결성 — fail-closed (핵심 계약)

골든 라벨은 **QA 엔진이 실제로 본 입력**, 즉 *검수 전(as-found)* 상태를 말해야 한다.
손질 후 승인을 `clean`으로 승격하면 **원래 결함이던 입력이 정상으로 라벨링되어 FN율이
과소평가**된다 — 골든이 자기 목적을 훼손한다.

| verdict | 승격 | 근거(`AsFoundBasis`) |
|---|---|---|
| `rejected` | ✅ `defective` | `rejected_failure_code` — 반려는 정의상 손질 전 판정이고 F1~F8이 결함을 명시 |
| `approved` + ⓐ 검수 전 불변 스냅샷 | ✅ 스냅샷이 말하는 라벨 | `pre_review_snapshot` |
| `approved` + ⓑ EOS-62 edit-aware verdict(계약 착지 **이후** 검수분) | ✅ `clean` | `edit_aware_verdict` |
| `approved_with_edit`(EOS-62 착지 후) | ✅ `defective` | `edit_aware_verdict` |
| `approved` (ⓐ·ⓑ 둘 다 없음) | ❌ **제외 + 건수 명시** | 모호 — 미측정 ≠ 정상 |

**ⓑ에 시각 경계를 요구하는 이유**: EOS-62 ④가 소급 재분류를 금지하므로 계약 착지 *이전*의
`approved` 행은 어휘가 확장돼도 영구 모호다. 경계 없이 어휘 존재만으로 승격하면 그 과거 행이
조용히 clean으로 섞인다. 그래서 `--edit-aware-since`를 **명시 인자로 요구**하고, 없으면 전부
제외한다(fail-closed). **골든 표본은 계약 착지 이후 검수분에서 뽑는 것이 정본 경로다.**

ⓑ의 착지 여부는 상수로 박지 않는다 — `edit_aware_verdict_available()`이 `ReviewVerdict` 어휘를
**실측**한다. EOS-62가 착지하면 이 경로가 자동으로 열리고, 착지 전에는 아무도 손대지 않아도
fail-closed가 유지된다(선언과 실체의 드리프트 차단).

**clean 라벨이 0건인 상태는 정상이다** — ⓐ·ⓑ 없이 반려분만 승격되면 clean 축이 비고,
Precision·오검출률은 **미산출**로 보고된다(0%로 찍지 않는다).

## §4. 과적합 방지 — 재채점 금지 (S2-11의 골든 적용)

초인간 검증 표준 §4.5("결함 교정 후 같은 표본 재채점 금지·신규 독립 표본 재추출")를 골든에도
건다. 집행 수단 2개:

1. **동결 기록** — 골든 셋에 `golden_version`·`rotation`·`frozen_at`·`digest`(내용 sha256)를
   박는다. digest는 판정 축(slug·subject·anchor·label·failure_code·basis)만의 함수이므로
   **라벨 손편집은 로드 시점에 터진다**(부기 메타 변경은 digest를 바꾸지 않는다).
2. **평가 원장** — `qa_confusion_matrix --ledger --engine-revision`. 평가 1회마다
   (digest, engine_revision)을 append하고, **같은 골든을 다른 엔진 리비전으로 재채점**하면
   exit 1로 막는다. 같은 리비전 재실행은 재현성(S4) 확인이므로 허용한다.
   원장이 **깨져 있으면 통과가 아니라 측정 실패(exit 1)** 다 — 손상된 줄이 하필 이전 평가
   기록이면 빈 이력을 보고 재채점을 허용하게 되어, 금지 규율이 그 증거가 손상된 바로 그
   순간에 무력화된다(#928 리뷰 P1).
   **EOS-137 보강**: 원장 행은 판정기 종류와 판정치 스냅샷(문항별 판정 digest 포함)을 싣고,
   "같은 리비전 재실행"은 이제 이전 기록과 **대조**된다 — 다르면 exit 1(§9). 초판은 이 허용을
   대조 없이 통과시켜, 리비전 표기를 그대로 둔 채 예측만 바꾸는 재채점을 막지 못했다.

### 재추출의 독립성은 회전이 아니라 **제외**에서 온다

`rotation`만 올리는 재추출은 **작동하지 않는다**(#928 리뷰 P1 실측). 앵커 후보가 쿼터 이하면
— 그 구간이 하필 우리 목표 규모 **30~35 = 기본 쿼터 35** 다 — 회전은 선택 *순서*만 바꾸고
전건이 그대로 선택되므로 같은 셋·같은 digest가 나오고, 그러면 교정 후 재판정이 원장에
"재채점"으로 **영구 차단**된다. 규약이 스스로를 막는 상태다.

그래서 독립성의 원천은 **이전 골든의 명시적 제외**다:

```bash
python -m whymath_backend.harness.golden_benchmark \
    --events review_timer.jsonl --anchor-map anchors.jsonl \
    --rotation 1 --exclude-golden data/corpus/golden_benchmark_v1/golden.json \
    --golden-version v2 --out data/corpus/golden_benchmark_v2/golden.json
```

- `--exclude-golden`(반복 가능)의 slug는 후보에서 **빠진다** → 새 셋은 이전과 서로소다.
- `rotation > 0`인데 제외 집합이 없으면 **거부**한다(fail-closed — 독립을 확인할 근거가 없다).
- 제외 후 후보가 소진되면 **비운다**. 이전 표본을 재사용해 쿼터를 채우지 않으며, 승격 0건은
  exit 1(측정 실패)로 드러난다. 재판정하려면 **검수를 더 쌓아 후보를 늘려야 한다** — 이것이
  S2-11이 실제로 요구하는 비용이고, 규약이 그 비용을 숨기지 않는다.
- 회전은 제외 위에서 순서를 재배열하는 보조 축이다. 해시는 새로 만들지 않았다 —
  `reviewer_sample_package.rotation_key`(S2-11)를 그대로 재사용한다.

원장을 주지 않으면 재채점 금지는 **미집행**이며, 리포트가 그 사실을 상시 명기한다
(정본화 ≠ 집행). 제외 집합이 없을 때도 리포트가 "초판만 가능"함을 자인한다.

## §5. 내용 KPI 4종의 소비 지점 (집행 별항)

코드 정본 = `ops/qa_confusion_matrix.CONTENT_KPI_CONSUMERS`(표와 실체의 정합은
`tests/backend/ops/test_qa_confusion_matrix.py`가 기계로 동결 — 착지 표기는 import 가능해야
하고, 미착지분은 좌석 태스크가 백로그에 실재해야 한다).

| 내용 KPI (EOS-51 §6) | 골든 라벨 축 | 채점기 | 좌석 |
|---|---|---|---|
| 수학적 오류율 ≤0.5% (독립 모델 심판 전수) | `defective ∧ F1·F2` | `ops/qa_confusion_matrix`(착지) | `EOS-60` |
| 교육과정 정합률 ≥92% (블라인드 역매핑) | `defective ∧ F4` | **미착지** | `EOS-61` |
| 오개념 op-code 라벨 정확도 ≥85% | `defective ∧ F6` | **미착지** | `MISC-07` |
| 풀이 비약 지적률 ≤10% (LLM 심판 κ≥0.5) | `defective ∧ F3` | **미착지**(저장소 κ 구현 0건) | `EOS-61` |

리포트는 **라벨 축별 정답지 건수**를 함께 찍는다 — 골든이 있어도 F4 라벨이 0건이면 교육과정
정합률 KPI는 여전히 계산 근거가 없다는 사실이 그 자리에서 보인다.

## §6. "작동한 비율" 원칙 — 측정 실패는 통과가 아니다

| 사태 | 처리 |
|---|---|
| 골든 0건 · 승격 0건 | **exit 1**(측정 실패). "통과 0건"이 아니다 |
| 예측 0건 · 골든과 겹치는 예측 0건 | **exit 1** |
| 골든 항목에 QA 판정이 없음 | **pass로 간주 금지** — `미평가`로 분리 카운트(FN 위장 차단) |
| 평가 원장 파싱 실패 1건 이상 | **exit 1** — 재채점 이력이 손상된 상태에서는 금지를 판정할 수 없다 |
| 제외 후 후보 소진(승격 0건) | **exit 1** — 이전 표본 재사용으로 쿼터를 채우지 않는다 |
| 입력 파싱 실패 1건 이상 | **exit 1** — 유실된 행이 정답지·혼동행렬을 바꿨을 수 있다(부분 입력 판정 금지) |
| 예측 파일 안 판정기(`verdict_source`) 혼재 | **exit 1** — 두 판정기의 FN이 한 행렬에 합산된다(§10) |
| 같은 골든 × 같은 리비전 재실행인데 문항별 판정이 이전 기록과 다름 | **exit 1** · 원장 미기록 — 재현성 위반 = 리비전 고정 하 표류 신호(§9) |
| 문항 판정 불가(QA 엔진 좌석) | predictions에 **쓰지 않음** → 혼동행렬에서 미평가(§7 생산자 절) |
| clean/defective 라벨 0건으로 분모 없음 | **미산출**로 표기. 그 지표에 게이트가 걸리면 통과가 아니라 exit 1 |
| 적재율 | 골든 중 QA 판정 동반 비율을 **상시 보고**(Wilson 하한 병기) |

판정 형식은 불변이다 — **Wilson 단측 경계**만 쓴다(점추정 금지). "높을수록 좋은"
recall·precision은 하한, "낮을수록 좋은" FN율·오검출률은 상한을 본다.

## §7. 사용

```bash
# ① 검수 이벤트 → 골든 승격·동결
python -m whymath_backend.harness.golden_benchmark \
    --events review_timer.jsonl --anchor-map anchors.jsonl \
    --golden-version v1 --rotation 0 \
    --out data/corpus/golden_benchmark_v1/golden.json --report golden_promotion.md

# ② 검수한 문항 파일 → QA 엔진 문항별 판정(predictions) — EOS-137
python -m whymath_backend.harness.qa_item_verdicts \
    --input canary_review_queue.jsonl --out qa_verdicts.jsonl > qa_verdicts_summary.json

# ③ 골든 대비 QA 엔진 혼동행렬(재채점 금지·재현성 대조 집행 포함)
python -m whymath_backend.ops.qa_confusion_matrix \
    --golden data/corpus/golden_benchmark_v1/golden.json \
    --predictions qa_verdicts.jsonl \
    --engine-revision "$(git rev-parse --short HEAD)" \
    --ledger data/corpus/golden_benchmark_v1/eval_ledger.jsonl \
    --json qa_confusion.json
```

`--predictions`는 판정 JSONL이다: `{"cu_slug": ..., "qa_verdict": "pass"|"fail",
"verdict_source": "qa_engine"}`(`passed`/`qa_pass` 불리언 형식도 수용). 어휘 밖 판정은 pass로
관용하지 않고 파싱 실패로 센다. `verdict_source`는 선택이지만 **한 파일 안에서 섞이면**(밝힌
행과 안 밝힌 행의 혼재 포함) 파싱 실패다(§10).

**②의 생산자(`harness/qa_item_verdicts`)** — EOS-60 착지 시점에 이 입력을 만드는 도구가
저장소에 0건이었다(QA 엔진 9축이 전부 코퍼스·시험지 단위 게이트라 "이 문항을 통과시켰는가"를
내는 좌석이 없었다). EOS-137이 좌석(`harness/qa_pipeline.judge_item`)과 어댑터를 만들었다:

- **입력은 검수자가 본 그대로** — `review_session.load_review_items`를 재사용한다. 검수 큐 행은
  `candidate_payload`가, 코퍼스 행은 행 자신이 판정 대상이고, 파일 안 중복은 첫 행을 쓴다.
  골든 라벨이 검수자가 본 입력(as-found — §3)의 라벨이므로 엔진도 같은 입력을 판정해야 한다.
  그래서 런북은 **검수 세션이 먹은 그 큐 파일**(`canary_review_queue.jsonl`)을 넘긴다.
- **판정 범위는 정답 재검산 + 9축 중 문항 단위 3축**이다. 3축(`ITEM_LEVEL_AXES` — 조건 DSL
  폐쇄성·금칙어/타인 PII·레코드 출처 필드)에 더해, 9축 밖의 기계 검증 스택인 **S6 정답 재검산**
  (`ITEM_VERIFICATION_AXES` — `corpus_reverify._reverify_one`, 야간 잡과 같은 함수)을 **필수 성분**
  (`ITEM_REQUIRED_AXES`)으로 부른다. 정답 재검산이 `ok`가 아닌 문항은 pass가 될 수 없다(재료 없음·
  unverifiable은 판정 불가). 나머지 6축은 문항을 판정하지 않는다(`CORPUS_LEVEL_ONLY_AXES`에 축별
  사유). 즉 이 혼동행렬의 FN율은 **그 좌석의 FN율**이지 9축 전체의 것이 아니다.
  - **재검산을 좌석에 넣은 이유(EOS-150 · 2026-09-28)**: 3축은 어느 것도 *답이 맞는가*를 보지
    않아, 정답만 틀린 문항이 pass였다. 그러면 골든의 수학 결함(F1·F2)이 엔진의 한계가 아니라
    **좌석이 부르지 않은 검증기**의 몫으로 FN에 쌓인다 — "엔진이 무엇을 못 보는가"를 재려는
    측정(§8-5)이 엔진이 이미 가진 검증기를 빼고 재는 셈이다. 첫 평가(원장 첫 행) **전에** 넓혔으므로
    §9의 재채점 금지와 충돌하지 않는다. 저장소 문제은행 14,034건 실측: 재검산 ok 14,034 ·
    새 fail 0 · 판정 불가 0.
- **판정 불가는 pass로 채우지 않는다** — cu_slug 없음·본문 없음·slug 불일치·입력 간 본문
  충돌·판정 불가 축은 predictions에 쓰지 않고 사유와 함께 요약에 전건 싣는다. 혼동행렬에서
  그 골든 항목은 "미평가"로 분리된다(§6).
- **작동한 비율** = 판정된 문항 / 입력 문항을 요약이 낸다. 입력 0건·판정 0건은 exit 1,
  입력 손상·부재는 exit 2이며 둘 다 파일을 쓰지 않는다.

## §8. 한계 명기 (정직)

1. **표본 200건은 FN율의 자릿수만 잡는다** — EOS-51 §7-3이 인정한 검출력 한계 안이다.
   0.5% 수준의 정밀 추정은 못 한다. Wilson 상한을 보는 이유이기도 하다.
2. **골든은 검수가 쌓이는 동안에만 싸게 만들어진다** — 나중에 만들면 as-found 상태가 복원
   불가다(N5·N7·N9의 논지가 N8에도 적용). 승격은 검수와 **같이** 돌려야 한다.
3. **과거 `approved` 행은 영구 모호다** — 소급 재분류 금지(EOS-62 ④)의 귀결. 초기 골든이
   defective 편중(clean 0건)일 수 있고, 그때 Precision 축은 미산출로 남는다.
4. **QA 판정 입력은 파일 기반이다** — 현행 검수·감사 흐름이 JSONL이라 그 관례를 따른다.
   DB 직접 조회 모드는 미구현(정직한 공백 — 소비처가 생기면 확장).
5. **QA 엔진의 문항 단위 표면은 좁다** — 정답 재검산 + 9축 중 3축(§7)만 문항을 판정한다.
   재검산은 정답 값이 조건과 맞는지(F1·F2의 계산 오류 부분)는 보지만, 풀이 비약(F3)·교육과정
   이탈(F4)·오개념 오연결(F6)·문장 수준(F7)은 어느 성분도 보지 않는다. 따라서 첫 평가의 재현율은
   낮게 나올 것으로 **예상**된다 — 그것이 측정의 목적이다(엔진이 무엇을 못 보는지가 FN
   실패코드 분포로 드러난다). 재현율이 낮다고 좌석을 넓히는 판단은 이 계약 밖이며, 좌석을
   넓히면 엔진 리비전이 바뀌므로 §9의 회전 규칙을 따른다.
6. **금칙어 축의 PII 정규식은 한국어 조사 부착을 못 본다** — `ops/log_scrubber`의 전화번호
   패턴이 `\b` 경계라 `010-1234-5678로`처럼 조사가 붙으면 검출되지 않는다(2026-09-28 EOS-137
   테스트 작성 중 실측). 문항 좌석은 그 함수를 그대로 쓰므로 같은 사각을 물려받는다 — 좌석이
   고칠 일이 아니라 검출기 소관이다.

## §9. 표류 시계열 — 재채점 금지와 "모델 표류 감지"의 관계 (EOS-137 ③)

> 판정 기준: main `919865d4` · 판정 세션 EOS-137 · 코드 정본 =
> `harness/golden_benchmark.EvaluationSnapshot`·`find_reproducibility_violation` +
> `ops/qa_confusion_matrix`(재현성 대조·원장 스냅샷). 동결 테스트 =
> `tests/backend/ops/test_qa_confusion_matrix.py::TestDriftTimeSeriesDesign`.

### 9.1 무엇이 충돌하는 것처럼 보였나

설계서 §7은 골든 벤치를 "모델 표류 감지"의 시계열로 쓰겠다고 했다. 그런데 §4의 재채점 금지는
**같은 골든(digest)을 다른 엔진 리비전으로 다시 재는 것**을 exit 1로 막는다. 표류 감지가 "같은
자로 시간에 따라 다시 잰다"는 뜻이라면 두 규율은 정면으로 부딪친다. 그리고 초판 원장 행에는
(digest·리비전·시각)만 있고 **지표 값이 없어서**, 원장을 시계열로 읽을 방법도 없었다.

### 9.2 판정 — 표류는 두 종류이고, 각각 다른 축에 점을 찍는다

| 표류 종류 | 무엇이 바뀌나 | 측정 축(정본) | 재채점 금지와의 관계 |
|---|---|---|---|
| **리비전 간 표류** | 우리가 판정기를 바꿨다(좌석 확장·임계 조정·모델 교체) | **회전별 독립 표본** — `--exclude-golden`으로 만든 새 골든마다 한 점 | 같은 골든으로 리비전을 비교하는 것은 표류 측정이 아니라 **교정 후 재채점**이다(과적합이 개선처럼 보인다). 금지는 **불변**이다 |
| **리비전 고정 하 표류** | 리비전 표기는 그대로인데 결과가 바뀐다(상류 모델의 조용한 갱신·입력·환경 변화) | **같은 골든 × 같은 리비전 재실행** | 재채점이 아니다 — §4가 이미 "재현성(S4) 확인"으로 허용한 바로 그 경로다 |

두 규율은 충돌하지 않는다 — **재채점 금지는 첫 번째 종류를 같은 골든에서 재지 못하게 막고,
그 종류의 정본 축을 회전으로 보낸다.** 두 번째 종류는 원래 같은 골든에서 재는 것이 맞다.

### 9.3 실측으로 드러난 공백 — "재현성 확인"은 선언만 있고 집행이 없었다

§4는 같은 리비전 재실행을 "재현성 확인이라 허용"했다. 그러나 원장에 지표도 판정도 없으니
**재실행 결과를 무엇과도 비교하지 않았다.** 그 결과 두 가지가 동시에 성립했다:

1. 리비전 고정 하 표류를 **감지할 수단이 0**이었다(재실행은 항상 통과했다).
2. **재채점 금지의 우회로**가 열려 있었다 — 판정기를 고친 뒤 리비전 표기만 그대로 두고 예측을
   바꿔 다시 재면, 원장은 "같은 리비전 재실행"으로 보고 막지 못한다.

### 9.4 결정 — 정본은 회전, 원장은 보강한다(둘 중 하나가 아니다)

EOS-137 ③은 "회전별 독립 표본을 정본으로 할지, 원장 행을 보강할지"를 물었다. 답은 **둘 다이며
역할이 다르다**:

1. **리비전 간 표류의 정본 시계열 = 회전별 독립 표본.** 새 리비전의 점은 항상 이전 골든을
   제외한 새 골든 위에 찍는다(§4 규약 그대로). 점과 점 사이의 비교는 서로 다른 표본의 비교이므로
   **Wilson 구간으로 읽는다**(점추정 차이로 표류를 선언하지 않는다).
2. **원장 행 보강** — 평가 1회마다 `verdict_source`(판정기 종류)와 `snapshot`(문항별 판정
   digest · 혼동행렬 4칸 · 미평가 수 · 골든 규모 · 신뢰수준 · recall/precision 하한 · FN율/
   오검출률 상한 · 적재율 하한)을 싣는다. 원장 자체가 시계열이 된다 — JSON 리포트는 실행마다
   덮어써지므로 시계열의 저장소가 될 수 없다.
3. **재현성 집행** — 같은 골든 × 같은 리비전 × 같을 수 있는 판정기의 이전 기록 중 스냅샷이 있는
   것과 **문항별 판정 digest**가 다르면 exit 1이고 원장에 적지 않는다(첫 관측이 기준으로 남는다
   — 어긋난 행을 쌓으면 이후 모든 재실행이 둘 중 하나와 영구히 어긋난다). 비교 키가 4칸이 아니라
   digest인 이유: 두 문항의 판정이 서로 뒤바뀌면 개수는 같고 문항은 다르다.
4. **구형식 행은 대조하지 않는다** — 스냅샷 없는 행(EOS-137 이전)은 대조할 값이 없으므로 위반으로도
   일치로도 세지 않고 리포트가 "대조 불가 N건"으로 드러낸다. 반면 확장 필드가 **있는데 깨졌으면**
   원장 손상(exit 1)이다 — 깨진 스냅샷을 없는 것으로 접으면 대조가 조용히 빠진다.

### 9.5 재현성 위반을 만났을 때

재현성 위반은 "판정기가 리비전 표기 밖에서 바뀌었다"는 신호다. 원인이 입력 파일 차이(다른 큐를
넘겼다)면 같은 입력으로 다시 돌린다. 판정기를 **실제로** 바꾼 것이면 그것은 새 리비전이고,
새 리비전은 §4에 따라 `--exclude-golden`으로 만든 신규 독립 표본에서만 잴 수 있다. 어느 쪽이든
원장을 손으로 고쳐 통과시키지 않는다(CLAUDE.md "거부의 우회 금지").

### 9.6 한계

- 결정론 판정기(현재의 QA 엔진 좌석)에서 재현성 위반은 입력·코드 차이만을 뜻한다 — "모델 표류"는
  LLM 판정기가 좌석에 들어올 때 비로소 실질적인 의미를 갖는다. 지금 집행하는 이유는 우회로
  봉쇄(9.3-2)이고, 표류 감지는 그 부수 효과다.
- 회전별 표본은 검수가 쌓여야 생긴다 — 시계열의 점 간격은 검수 속도가 정한다(§4 "재추출 비용을
  숨기지 않는다"와 같은 사실).

## §10. 대용 입력 판정 — 생성 게이트 outcome을 predictions로 쓸 것인가 (EOS-137 ④)

> 판정 기준: main `919865d4` · 판정: **미채택**(어휘 좌석과 혼입 차단만 둔다).

생성 파이프라인 outcome(`accepted_stored`·`needs_review`·`rejected_*`)은 문항마다 이미 있으므로
predictions의 **대용**으로 쓸 수 있어 보인다. 채택하지 않은 이유:

1. **재는 대상이 다르다** — 그 outcome은 QA 엔진이 아니라 **생성 게이트**(SymPy 검산·동등성 가중
   점수·중복 검출)의 판정이다. 대용 혼동행렬의 FN율은 "생성 게이트가 결함을 들여보낸 비율"이지
   QA 엔진의 것이 아니다. 둘을 같은 이름으로 부르면 G2 "자동검증 ≥70%"가 무엇을 말하는지 다시
   결정 불가가 된다(N8 갭이 겨냥한 바로 그 상태).
2. **pass/fail 사상이 모호하다** — `needs_review`는 "걸렀다"인가 "보류"인가, `rejected_duplicate`는
   내용 결함 판정이 아니라 중복 판정이다. 사상을 하나 고르는 순간 그 선택이 FN율을 정한다 —
   근거 없는 사상은 측정이 아니라 가정이다.
3. **대상 표본이 편향된다** — 생성 게이트가 걸러 낸 문항은 코퍼스에 없고 검수 큐로만 간다.
   카나리 검수 표본은 그 두 경로가 섞인 것이라, 게이트 판정과 골든 라벨이 독립이 아니다
   (검수 대상 선정 자체가 게이트 outcome에 의존한다).

**그래도 두는 것**: 어휘 `generation_gate`(`golden_benchmark.VERDICT_SOURCES`)와 혼입 차단.
손으로 만든 대용 파일이라도 판정기를 밝히지 않고는 섞일 수 없게 하기 위해서다 — 파일 안 혼재는
파싱 실패(exit 1)이고, `generation_gate` 리포트는 **제목부터** "생성 게이트 혼동행렬 — 대용
입력"이며 머리에 "재는 것은 QA 엔진이 아니라 생성 게이트"를 적는다. 원장 행에도 `verdict_source`가
남는다. 판정기를 밝히지 않은 파일(`verdict_source` 부재)은 리포트 머리가 "미기재 — 어느 판정기의
FN율인지 결정할 수 없다"를 자인하고, 원장에는 "모름"으로 남아 재채점 금지에서 **모든 판정기와
같은 것으로** 취급된다(보수적). 재채점 금지는 판정기가 **확실히 다를 때만** 서로를 면제한다
(다른 판정기는 서로의 교정 대상이 아니므로).

대용안을 나중에 채택하려면 위 1~3의 답(사상 규칙의 근거·표본 독립성 처리)을 결정 로그에 먼저
적고, 생산자를 `generation_gate`로 표기해 만든다.
