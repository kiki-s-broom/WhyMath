# ADR — 답 형태 계약(Answer Form Contract) (EOS-28)

**결정일** 2026-09-01 · **상태** 채택·배선 완료 · **소유** `EOS-28-answer-form-contract`

---

## 1. 문제 — 지시를 읽지 않는 채점기

문항이 `"확률을 **기약분수로** 나타내시오"`라고 지시해도 채점기는 그 문장을 보지 않았다.
`verify_final_answer`를 직접 호출한 실측(2026-09-01):

| 제출 | 판정 | 문제 |
|---|---|---|
| `1/36` | `correct` | 정상 |
| `2/72` | `correct` | 기약이 아닌데 통과 |
| `5/180` | `correct` | 동상 |
| `0.0277777777` | `correct` | 분수조차 아닌데 통과 |

값 동치만 보면 넷 다 같다. **지시를 따랐는가는 다른 질문**이고, 그 질문에 답하는 코드가
시스템에 없었다(`verify_answer`·`verify_final_answer`·`verify_step` 전수 — 형태 검사 0건).

## 2. 도입 판정 — 측정이 먼저

「측정 없는 도입 없음」에 따라 코퍼스를 전수 조사했다
(`scripts/analysis/answer_form_requirement_scan.py`, 2,638문항·7뱅크 — 2026-09-01 결정 당시 코퍼스).

| 형태 어휘 | 적중 | 비율 |
|---|---:|---:|
| `reduced_fraction` | **26** | 0.99% |
| `factored`·`expanded`·`rationalized`·`simplified`·`decimal_places`·`specified_form` | 0 | 0.00% |

**0건이 아니므로 도입한다.** 다만 실증된 어휘는 **1종뿐**이고, 그 사실이 아래 §4 범위를 정한다.

### 측정 방법이 왜 두 축인가

1차 시도는 내가 상상한 어휘로 `grep`했고 `꼴로` 패턴이 **24건을 잡았는데 전부 "사다리꼴"**
이었다. 「부재 판정 절차」가 경고하는 실패다 — *이름을 잘못 고르면 조용히 틀린 답이 나온다*.

그래서 스캐너는 두 축을 함께 돌린다:
- **축 A(역할 기반)** — 지시문 꼬리(`…로 나타내시오`)를 전수 추출해 **데이터가 어휘를 말하게**
  한다. 상상하지 못한 형태 어휘는 여기서 드러난다. 실행 결과 49종의 꼬리 중 형태를 요구하는
  것은 `기약분수로|나타내` 하나뿐이었고, 나머지는 전부 *값*을 묻는다(`값을|구하` 1,075건 등).
- **축 B(어휘 매칭)** — 후보 어휘를 오탐 차단 패턴과 **쌍으로** 둔다. `factored`는
  `이용하여|사용하여`를 배제한다("인수분해를 *이용하여* 근을 구하시오"는 풀이 *방법* 지시이지
  답의 형태 요구가 아니다 — 어겨도 답은 여전히 수 하나다).

## 3. 결정 — `answer_constraint` 확장 (신설 아님)

| 후보 | 성격 | 판정 |
|---|---|---|
| `answer_format` (enum 4종) | 답의 **타입 라벨**("이 답은 분수다") | ❌ 타입과 요구를 섞는다. 형태마다 값을 늘리면 4종이 폭발한다 |
| **`answer_constraint` (JSONB)** | 문항별 제약 슬롯 · 실측 소비 **0건** | ✅ **채택** |
| 신규 컬럼 | — | ❌ 1%(26/2,638) 기능에 마이그레이션. 그 용도의 컬럼이 이미 있다 |

채택 근거 셋: **마이그레이션 0** · **SEC-24 비노출 경계 자동 상속**(형태 요구는 문항 본문에
이미 있어 비밀이 아니지만, 제약 슬롯의 기존 노출 규칙을 그대로 따르는 편이 안전하다) ·
**그 슬롯이 정확히 이 용도로 존재**했고 소비자가 없었다.

자유형 JSONB의 위험(스키마 강제 없음)은 **닫힌 키 + 닫힌 어휘 + fail-closed 리더**로 막는다.
`expected_form`에 모르는 값이 오면 `not_required`가 아니라 `unverifiable`로 흐른다 —
저작 오타를 "요구 없음"으로 흘리면 형태 검사가 있는 척하면서 아무것도 안 하게 된다.

## 4. 폐쇄 어휘 — 측정이 허가한 것만

`ExpectedForm`은 현재 `reduced_fraction` **1종**이다. 없는 것을 미리 넣지 않는다
(소비처 0 추상 금기). 어휘 추가 조건은 **기계가 묻는다**:
`test_expected_form_vocabulary_is_measurement_gated`가 각 enum 값에 대해
①스캐너 패턴 존재 ②코퍼스 적중 ≠ 0을 검사한다. 근거 없이 추가하면 CI가 적색이다.

양방향으로 의미가 있다 — 코퍼스에서 형태가 사라져도 실패하며, 그때는 그 어휘가 죽었다는 뜻이다.

## 5. 판정 어휘 — 값과 **다른 enum**을 쓴다

```
FormVerdict = satisfied | violated | not_required | unverifiable
```

값 3상태(`VerificationOutcome`: correct/incorrect/unverifiable)를 재사용하지 **않았다**.
재사용하면 "형태가 `incorrect`"라는 문장이 만들어지고, 그 순간 형태 위반이 오답으로 읽힌다.
어휘 분리가 이 혼동의 1차 방어다.

> EOS-69가 세운 "상태 enum은 공유한다(별도 정의 금지)" 규칙과 어긋나 보이지만 아니다.
> 그 규칙은 **같은 축**을 두 어휘로 표현하지 말라는 것이고, 형태는 값과 **다른 축**이다.
> 같은 축을 쪼개면 경계마다 매핑이 필요해지고, 다른 축을 합치면 의미가 섞인다.

`not_required`가 독립 상태인 이유(None-vs-zero): 문항의 **99%는 형태 요구가 없다**.
그것을 `satisfied`로 적으면 형태 준수율 지표가 99%로 부풀어 오른다 — 요구 없음 ≠ 지켰음.

## 6. 표면을 본다 — "표현 ≠ 의미"의 한 사례

`2/72`와 `1/36`은 값이 같다. 형태 요구는 정확히 *그 같은 값들 사이*를 가르는 축이므로
값으로는 아무것도 가를 수 없다. 그래서 표면 표기를 보존한 채 파싱한다(2026-09-01 실측):

```
sympify("2/72")                 → 1/36   (즉시 약분 — 표면 소실)
sympify("2/72", evaluate=False) → 2/72   (표면 보존 ✔)
```

소수 표기는 **타입으로 먼저** 가른다. `fraction(0.5)`가 `(0.5, 1)`을 주어 분모 1이 되므로
정수와 구별되지 않고, 이 검사가 없으면 `0.5`가 gcd 검사를 조용히 통과한다.

## 7. 교수학 계약 — 코드로 동결한 금기

형태 검사는 잘못 붙이면 **맞은 답에 오답 표시를 하거나 제출을 막는 기능**이 된다.
산문으로 적은 금기는 다음 세션이 모르고 어기므로 테스트로 동결했다:

| 금기 | 동결 방식 |
|---|---|
| 형태 위반은 오답이 아니다 | 같은 값을 형태만 달리 제출했을 때 `problem_complete`·`awaiting_reflection`·`completed_attempt_id`·발화·적재가 **비트 동일**함을 API 테스트가 검사 |
| 어휘가 오답을 표현할 수 없다 | `FormVerdict` 값 집합을 동결 — `correct`/`incorrect`가 없음을 단언 |
| 정답이 형태 경로로 새지 않는다 | `verify_answer_form` **시그니처를 동결** — 정답을 인자로 받지 않는다(구조적 보장 > 규율) |
| 두 축이 독립이다 | 형태 모듈이 값 판정 심볼을 **AST 기준** import·참조하지 않음을 검사 |
| 학생 입력을 거부하지 않는다 | 형태 위반 제출도 정상 응답·발화가 비지 않음을 검사 |
| 판정 불가를 위반으로 접지 않는다 | 문자식·빈 제출·파싱 실패가 전부 `unverifiable`임을 검사 |

## 8. 배선 — 계약이 아니라 경로가 완료 조건이다

집행 지점은 `api/coach.py` 완료 경로다. `_final_answer_state`가 `(값 판정, 형태 판정)`
두 축을 나란히 내고, `_CompletionResult`가 운반해 두 세션 응답(`SessionCreateResponse`·
`TurnAppendResponse`)의 `answer_form` 필드로 노출된다.

**형태는 완료 판정에 인자로 들어가지 않는다** — `decide_completion`은 형태를 받지 않으며,
`final_correct`/`final_incorrect`는 값 판정만으로 정해진다. 형태가 완료를 막는 경로가
코드에 존재하지 않는다.

stateless `/v1/coach`에는 싣지 않았다 — DB 없이는 문항 제약을 읽을 수 없어 항상
`not_required`인 가짜 계기판이 된다(기존 `client_state_mismatch` 선례와 동형).

배선 실재성은 뮤테이션으로 확인했다: 배선을 `not_required` 상수로 바꾸자 API 테스트 5건이
적색이 됐다. "계약을 만들었으나 아무도 부르지 않는" 상태를 CI가 잡는다.

## 9. 남은 것

- **학생 대면 문구는 만들지 않았다.** 백엔드는 `violated` 신호만 내고, "값은 맞았고 기약분수로
  바꾸면 어떻게 될까?" 같은 발화 생성은 L5/클라의 몫이다(응답 필드 설명에 사용 규약 명시).
- **소수 허용 오차**는 별개 축이다. 실측 중 `0.0277777777`이 `1/36`과 `correct` 판정된 것을
  발견했으나(값 판정의 tolerance 문제) EOS-28 범위가 아니라 손대지 않았다.
- **어휘 확장**은 코퍼스가 먼저다. 인수분해·전개형 문항이 생기면 스캐너가 잡고, 그때 어휘와
  검증기를 함께 추가한다.
