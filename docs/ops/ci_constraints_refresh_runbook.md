# CI 의존 제약 파일 갱신 런북 — 정기(주 1회)·긴급(보안 패치)·갱신 PR이 빨갛게 될 때

- 태스크: `OPS-121` · 판정 문서: `docs/reviews/ops121_ci_dependency_resolution_options_2026-10-09.md` (Kiki 승인 2026-10-09)
- 도구: `scripts/ops/ci_constraints.py` (`refresh` 갱신 · `check` 정적 게이트) · 제약 파일: `infra/ci/constraints-py312.txt`
- 판정 기준: `origin/main` — 이 런북의 명령은 OPS-121 PR이 main에 머지된 뒤 기준이다.

## 0. 이 파일이 왜 있나 (초보자용 풀이)

- **제약 파일(constraints)**은 "이 패키지는 정확히 이 버전만 설치하라"를 적은 목록이다. CI의 모든 `pip install`이 이 목록을 따른다(워크플로 최상위 `env: PIP_CONSTRAINT`).
- 이 목록이 없던 2026-10-08, `pydantic 2.14.0`이 올라온 지 약 20분 만에 머지 큐 3건이 `mypy --strict`에서 같은 줄로 실패했다. 목록이 있으면 **새 릴리스는 이 파일을 바꾸는 PR(갱신 PR)을 거쳐서만** main에 닿고, 그 PR이 전체 CI를 돌므로 깨지면 병합 전에 걸린다.
- 그 대가가 이 런북이다 — 파일이 오래되면 취약한 버전이 굳으므로 **주기적으로 갱신 PR을 낸다.**

## 1. 누가 무엇을 하나

| 일 | 주기·시한 | 실행 주체 |
|---|---|---|
| 정기 갱신 PR | **주 1회(월요일)** | Claude 세션(Linux) — 아래 §2 |
| 긴급 갱신 PR | 보안 공지 확인 후 **영업일 1일 이내** | Claude 세션 — 아래 §3 |
| 갱신 PR 검토·머지 | 갱신 PR이 초록이면 | Kiki (또는 `pr` 지시) |
| 연령 센서 | 매일 18:00Z 야간 잡이 **30일 초과 시 빨갛게** | 자동 (`constraints-freshness` 잡) |

**Kiki 머신(Windows)에서 실행할 명령은 없다.** `refresh`는 CI와 같은 해석을 내려고 **python 3.12 + linux**에서만 돈다 — Windows에서 실행하면 측정 실패(exit 2)로 거부된다. WSL에 python3.12가 있는지는 확인하지 않았다(미확인).

왜 자동화(워크플로가 PR을 대신 여는 것)가 아닌가: 기본 토큰(`GITHUB_TOKEN`)으로 만든 PR은 다른 워크플로를 자동으로 깨우지 않는 것으로 알려져 있어(이 저장소에서 실측하지 않음) 별도 자격 증명이 필요하다. 그 결정은 별건이며, 지금은 세션이 스크립트를 돌려 PR을 여는 가장 단순한 경로를 쓴다.

## 2. 정기 갱신 (주 1회)

### 사전 브리핑 (세션 실행 기준)

1. **과제 명칭**: CI 의존 제약 파일 정기 갱신.
2. **목적**: 선언 범위 안의 최신 버전으로 핀을 옮기되, 그 변경이 전체 CI를 통과하는지 PR에서 먼저 확인한다.
3. **절차**: 최신 main 위에 새 브랜치 → `refresh` 실행(PyPI 해석, 약 1~3분) → 변경 목록 확인 → 커밋 → PR → CI 통과 확인.
4. **성공 기준**: `refresh` 종료 코드 0 · `check` 종료 코드 0 · PR의 CI 전체 초록. 실패 시 §4.
5. **실행 환경**: Linux, python 3.12, 저장소 루트, 네트워크로 PyPI 접근 가능.
6. **창 구분**: 해당 없음(세션 안에서 실행).

```bash
# Linux · python3.12 · 저장소 루트에서 실행 (Kiki 머신 아님)
git fetch origin main && git switch -c "ci/constraints-refresh-$(date -u +%Y%m%d)" origin/main
python3.12 --version
python3.12 scripts/ops/ci_constraints.py refresh
```

`refresh`는 변경된 핀을 `~ 이름: 이전 → 이후`로 출력한다. 그 목록을 PR 본문에 그대로 붙인다(리뷰어가 무엇이 움직였는지 본다).

```bash
# 갱신 직후 자가검증 — 종료 코드를 직접 본다 (출력을 자르거나 -q로 죽이지 않는다)
python3 scripts/ops/ci_constraints.py check; echo "CHECK_EXIT=$?"
git diff --stat -- infra/ci/constraints-py312.txt
```

`CHECK_EXIT=0`이 아니면 커밋하지 않는다. 변경 파일이 제약 파일 **1개뿐**이어야 정상이다(코드 수정이 같이 필요한 경우만 예외 — §4).

## 3. 긴급 갱신 (보안 패치 · 영업일 1일 이내)

정기 주기를 기다리지 않고 **패키지 하나만** 올린다. 나머지 핀은 그대로 둔다.

```bash
# 예: pydantic만 올린다. 쉼표로 여러 개 가능. 대소문자는 정규화된다.
python3.12 scripts/ops/ci_constraints.py refresh --only pydantic
python3 scripts/ops/ci_constraints.py check; echo "CHECK_EXIT=$?"
```

- `--only`는 대상 패키지만 풀고 나머지를 제약으로 넘겨 해석한다. 대상이 요구하는 전이 의존이 기존 핀과 충돌하면 해석이 실패(exit 2)한다 — 그때는 전체 `refresh`를 쓴다.
- 대상이 제약 파일에 없으면 거부된다(철자 오류가 조용히 아무것도 안 하는 것을 막는다).
- 긴급 PR도 **전체 CI를 통과해야** 머지한다. 급해서 CI를 건너뛰는 경로는 만들지 않는다.

## 4. 갱신 PR이 빨갛게 될 때 (이것이 이 제도의 본래 목적이다)

초록이 아니라 빨강이 나오는 것은 실패가 아니라 **사고가 main에 닿기 전에 걸렸다는 뜻**이다. 원인에 따라:

| 상황 | 조치 |
|---|---|
| 새 버전과 우리 코드가 호환되지 않음(예: `mypy --strict` 오류) | 같은 PR에서 코드를 고친다. 2026-10-08 `_schema_seam.py:77`가 이 유형이다. |
| 호환되게 고치기 어렵다 | 문제 패키지의 **상한을 `pyproject.toml`에서 좁힌 뒤** `refresh`를 다시 돌린다(`<2.14`처럼). 상한은 두 pyproject·워크플로 인라인 설치가 같아야 한다(OPS-94). |
| 어느 패키지가 원인인지 모르겠다 | `refresh --only`로 패키지를 나눠 올려 이분 탐색한다. 한 PR에 평균 약 30건의 릴리스가 묶이므로(최근 90일 382건·13주) 전체 갱신이 깨지면 분할이 빠르다. |
| 갱신 PR을 당장 못 낸다 | 기존 파일이 계속 유효하다 — CI는 영향받지 않는다. 단 **30일**을 넘기면 야간 센서가 빨갛게 된다. |

## 5. 의존을 추가·삭제한 PR에서

`pyproject.toml`에서 직접 의존을 추가·삭제하면 `ci_constraints.py check`가 **직접 의존 집합 지문 불일치**로 빨갛게 된다. 새 직접 의존의 전이 의존이 고정 없이 떠다니는 것을 막는 장치다. 같은 PR에서 `refresh`를 돌려 제약 파일을 함께 커밋한다. 범위(`>=,<`)만 바꾸고 이름이 같으면 갱신은 필요 없지만, 핀이 새 범위 밖으로 나가면 빨갛게 된다.

## 6. 이 장치가 보지 못하는 것 (정직 기술)

- **오프라인 정적 검사는 전이 의존의 일관성을 직접 보지 못한다.** 직접 의존의 핀·집합 지문만 본다. 전이 정합은 `refresh` 시점의 pip 리졸버가 보장한다.
- **Dockerfile 설치 표면**(`pip install -e /app/src/backend`)은 이 제약 파일을 아직 쓰지 않는다. `OPS-103` 소관이며 OPS-121 착지 후 같은 파일을 쓰도록 맞춘다 — 그 전까지 프로덕션 이미지와 CI의 해석이 다를 수 있다.
- **CI가 설치하지 않는 extras**(`embedding`·`ocr`·`ocr-heavy`·`playwright`·`xlsx`)는 핀이 없다. CI 구성(`CI_TARGETS`)이 바뀌면 그 상수와 이 파일을 함께 고친다.
- **해시 고정**(`--require-hashes`)은 하지 않는다. 공급망 변조 방어는 `SEC-22` 소관이다.
- **연령 검사는 PR 경로에 없다.** 날짜는 시계에 따라 결과가 바뀌는 입력이라, 넣으면 "머지 큐의 입력은 코드뿐이다"라는 이 고정의 목적이 깨진다. 야간 센서가 맡는다.
- `pip` 자체의 상한은 워크플로 `pip<27`과 제약 파일의 `pip==…`이 함께 정한다. 부트스트랩의 상한 검사는 OPS-94가 이미 본다.
