# HARN-302 판정 — 적재 전 외래키 대상 사전확인은 채팅 블록 가드가 아니라 쓰기 도구의 몫이다

> 판정 기준: main `0607bc070` (2026-10-07). 이 문서가 서술하는 코드는 모두 그 시점 main 기준이며,
> 구현은 같은 PR(브랜치 `claude/gallant-euler-blngpj`)에 있다. 미머지 근거는 쓰지 않았다.

## 1. 정본 사고와 그것이 말해 주는 것

2026-10-07 G-misc40 DB 동기화: 크로스링크 68건 적재가 첫 행에서 `ForeignKeyViolation`으로 실패했다
(`M0864`이 `misconception_catalog`에 없음). 두 가지를 갈라서 봐야 한다.

| 피해 | 원인 | 이미 막혔나 |
|---|---|---|
| 블록이 실패를 무시하고 `DELETE` 2건을 이어 실행 | 쓰기 뒤 종료 코드를 확인하지 않음 | **막혔다** — HARN-300 ①(`chat_block_guard`) |
| 적재 데이터 | 적재는 한 트랜잭션(`engine.begin()`)이라 외래키 위반 시 전체가 롤백된다 | 애초에 DB가 지켰다 |
| 고치고 다시 돌리는 왕복 | 오류가 **첫 행의 키 하나만** 말한다 | **이 태스크의 대상** |

즉 HARN-302가 더하는 가치는 "데이터를 지킨다"(DB가 이미 한다)가 아니라 **쓰기 전에 누락 키를 전부
말하고 아무것도 쓰지 않는 것**이다. 누락이 N건이면 종전에는 N번 실패해야 모두 알았다.

## 2. 판단 ① — 채팅 블록의 정규식 검사로 알 수 있는가: **알 수 없다**

가드가 "이 블록이 적재 전에 대상 키를 확인했는가"를 판정하려면 세 가지를 알아야 한다.

1. **값** — 적재 파일 안의 `mis_id`들. 블록에는 `promote --queue Q.json --load` 같은 *명령 한 줄*만 있고,
   값은 파일 안에 있다.
2. **라이브 DB 내용** — 그 `mis_id`가 지금 카탈로그에 있는가. 블록 텍스트에는 없다.
3. **테이블 ↔ 외래키 대응** — 어느 적재가 어느 테이블에 쓰고 그 테이블이 어느 외래키를 갖는가. 이것은
   ORM 메타데이터에만 있다. 블록이 CLI 이름만 부르면 테이블 이름조차 블록에 나오지 않는다.

HARN-214가 같은 방향으로 이미 결론을 냈다 — "변수 경유 실행·파일 입력 SQL·변경 범위의 의미는 텍스트
스캔으로 볼 수 없다. 변경 범위의 보호는 쓰기 도구 자신의 몫이다." 이 태스크는 그 결론의 *외래키 축*이다.
알 수 없는 것을 아는 척하는 검사는 오탐이든 미탐이든 "보호 있음"의 위장이 된다
(`guard-effect-assumed-from-code-shape` 계열 — 1회차 2026-09-28, 2회차 2026-10-07).

**판정**: `chat_block_guard`에 HARN-300 ②(외래키 사전확인 검사)를 **두지 않는다.** 가드가 할 수 있는 것은
HARN-300 ①이 이미 한다 — 쓰기 뒤 종료 코드를 확인하지 않고 파괴 단계로 넘어가면 막는다.

## 3. 판단 ② — 그러면 어디서: **쓰기 도구(로더) 안에서, 값과 DB를 둘 다 쥔 지점**

값(입력 payload)과 DB(엔진)를 한꺼번에 쥔 곳은 `load_crosslinks`뿐이다. 구현은 다음과 같다.

- `l1/fk_precheck.py` — `missing_fk_targets(conn, table, rows)`: ORM 테이블의 외래키를 메타데이터에서
  읽고, 각 외래키 컬럼의 값(NULL 제외)이 참조 테이블에 있는지 청크(500개) 단위로 **읽기만** 한다. 누락을
  외래키별로 **전건** 반환한다. 복합 외래키는 조용히 건너뛰지 않고 `NotImplementedError`로 멈춘다.
- `MisconceptionCrosslinkStore.missing_fk_targets` — 위 함수를 이 테이블의 ORM 모델에 연결한다.
- `load_crosslinks(..., check_fk_targets=True)` — 게이트(검수 서명) 통과 **뒤**, `populate` **앞**에서 호출한다.
  누락이 있으면 `ForeignKeyTargetMissingError`(전건 열거)를 올리고 **쓰기 0건**이다.
- `promote --load` CLI — 그 오류를 잡아 전건을 출력하고 **종료 코드 3**으로 끝난다(1=검수 큐 위반 ·
  2=입력 부재와 구분). 블록은 `$LASTEXITCODE`로 후속 쓰기를 멈출 수 있다(HARN-300 ①이 요구하는 형태).

설계 결정 3건과 근거:

| 결정 | 근거 |
|---|---|
| `populate`에는 넣지 않고 `load_crosslinks`에 둔다 | `populate`는 resolve/shadow 단위 테스트가 합성 시딩에 쓰는 순수 쓰기 원시 함수다. 거기에 읽기 질의를 섞으면 가짜 엔진 테스트(`_FakeEngine`)의 실행 횟수 단언이 오염된다 — 실제로 `load_crosslinks`에 사전확인을 걸자 `populate` 횟수를 세는 기존 테스트 2건이 깨져 `check_fk_targets=False` 좌석을 두었다. 승인된 경로(게이트를 거치는 `load_crosslinks`)에 둬야 동작 변경이 `promote --load`로 한정된다. |
| 확인과 쓰기는 다른 트랜잭션 | 확인을 쓰기 트랜잭션 안에 넣으면 `populate`를 바꿔야 한다. 확인 뒤 쓰기 전에 대상이 지워지는 경합은 DB 외래키 제약이 마지막 방어선으로 막는다(실패는 하되 데이터는 지켜진다). 이 모듈은 제약을 대체하지 않고 **앞당긴다**. |
| 게이트 위반이 외래키 확인보다 먼저 | 검수 서명이 없는 입력을 DB 조회로 확인하지 않는다(검수 우회를 DB 질의 뒤에 알리지 않는다). |

## 4. HARN-215와의 범위 분할 (acceptance ②)

| | 무엇을 | 입력 |
|---|---|---|
| **HARN-302(이 문서)** | 참조되는 키가 **존재하는가** | 적재 행의 외래키 컬럼 값 |
| **HARN-215** | 적재가 **몇 행을 바꾸는가**(신규/변경/그대로) — 기대 건수 단언 | 의미 유일키 `(kebab_id, mis_id, link_type)`와 라이브 행 |

둘 다 "쓰기 전 읽기 전용 계획 단계"이므로 HARN-215를 구현할 때 같은 읽기 연결에서 이 확인을 함께 실행할
수 있다 — 라이브 DB를 한 번만 읽는다(후속 `HARN-303` ④가 이 합치기를 판정한다). 종료 코드는 3이
HARN-302 전용이므로 HARN-215의 "전용 종료 코드"는 **4 이상**을 배정한다.

## 5. 변별력 (acceptance ③)

실 PostgreSQL에서 사고를 재현한 통합 테스트와 단위 테스트(SQLite 메모리)로 각 절을 밟았다.

| 입력 | 기대 |
|---|---|
| 존재 2 + 누락 2 | `ForeignKeyTargetMissingError`가 누락 **2건 모두** 열거 · 크로스링크 **0행**(존재하는 키도 쓰지 않음) |
| 전부 존재 | 정상 적재(사전확인이 모든 적재를 막으면 고장이다) |
| 사전확인을 우회한 `populate` | 종전대로 `IntegrityError`(DB 제약이 마지막 방어선) |
| `promote --load` + 누락 | 종료 코드 **3** · 출력에 누락 키 전건 · 존재하는 키는 누락으로 보고 안 함 |

뮤테이션 **14종 전건 RED**(NULL 제외·전건 열거·청크·복합 외래키·존재/누락 반전·빈 항목·중복·로더 호출·
기본값·raise·CLI 종료 코드·CLI 예외 처리·메시지 값 목록·Store 반환). 주입 적용(`count==1`·원본≠변경)과
원복 바이트 동일을 단언했다. **첫 회차에 2건이 살아남았다**:

- **M3(첫 청크만 확인)**: 확인하지 않은 값이 전부 '누락'으로 보고되어, 누락 값만 있는 입력에서는 정답과
  같았다. 뒤쪽 청크에 **존재하는** 값(`ZZ_LAST`)을 둬야 차이가 난다 — 그 반례를 픽스처에 추가했다.
- **M7(중복 제거 해제)**: 제가 만든 뮤테이션이 등가 변이였다(집합 컴프리헨션이라 문자열을 덧붙여도 중복
  제거가 유지됨). 집합→리스트로 바꾼 진짜 변이로 다시 만들어 RED를 확인했다.

## 7. 이 PR이 하지 않는 것 (정직한 공백)

- **나머지 외래키 적재 지점 13곳은 채택하지 않았다.** `on_conflict` 적재 지점 36곳 중 외래키가 걸린 테이블에
  쓰는 곳은 14곳이고 이번에 채택한 것은 `crosslink_loader` 1곳이다(`Base.registry`와 `pg_insert` 대상 모델
  대조, 2026-10-07 — 변수로 모델을 받는 `l2/learning_metrics_rollup.py` 1건은 집계에서 해소하지 못했다).
  나머지는 **`HARN-303`**이 소유한다. 지점마다 말뭉치 적재(사고 형태가 성립)인지 요청 경로 런타임 쓰기
  (제외)인지 판정이 필요하다.
- 복합 외래키는 지원하지 않는다(멈춘다). 크로스링크 테이블은 단일 컬럼 외래키 1개뿐이다.
- 확인과 쓰기 사이의 경합은 막지 못한다(DB 제약이 마지막 방어선).
- Kiki 머신의 실제 적재 블록은 이 PR로 바뀌지 않는다. 블록이 이 종료 코드를 보고 멈추는지는 블록
  쪽(HARN-300 ① 가드)이 요구하는 형태에 달려 있다.
