## 1. M0674를 직접 읽은 결과

`misconceptions.json`의 M0674(원문 그대로):
- canonical_statement: "평균값 정리 조건 미확인"
- student_wrong_thinking: "연속·미분가능을 확인하지 않고 적용하거나 롤의 정리와 혼동한다"
- distractor_rule: "끝점에서 미분 불가능한 함수에 평균값 정리 결론(c 존재)을 그대로 적용한 보기를 정답으로 유도"
- correction_point: "함수에 대한 평균값 정리를 설명하고, 이를 활용할 수 있다."

이 문장은 **두 절차**를 적는다. ① 조건을 확인하지 않고 *적용*한다 ② 롤의 정리와 *혼동*한다. 정직한 선지는 둘 중 하나의 계산 산출이어야 한다.
- ②는 값이 나온다: 평균변화율 대신 0을 놓고 `f'(c)=0`을 푼다. (기존 은행 12건이 c값 선지로 이미 이렇게 한다.)
- ①은 *값*이 아니라 *판정*("c가 존재한다")이다. 그래서 값 선지로 달려면 **판정이 숫자로 접히는 틀**이 필요하다(→ B: 함수 *개수*).

**distractor_rule의 수학적 부정확(보고 사항)**: "끝점에서 미분 불가능"은 평균값 정리의 위반이 아니다. 정리는 *닫힌구간에서 연속·열린구간에서
미분가능*만 요구하므로 `√x`를 [0, 4]에 쓰면 끝점에서 미분 불가능해도 c가 존재한다(c=1). 위반이 되는 것은 **열린구간 안의 꺾인점**
(또는 끝점·내부의 불연속)이다. 틀 B는 꺾인점을 항상 열린구간 안에 두고, 끝점 꺾임은 일부러 풀에서 뺐다(충족이라 오답 유도가 반대로 간다).

## 2. 출발 가설 실측 — 무엇이 맞고 무엇이 틀렸나

가설: "구간 안 미분불가능점이 있는 함수에서 정답 0, 조건을 안 보고 적용하면 1, 롤 혼동이면 f'=0 근의 수."

1. **개수형에서 M0674 규칙의 반응(실측)**: `_misconception_rules`의 M0674 항은 연결 선지 값이 `_critical_roots(probe)`에 드는지 본다.
   `_critical_roots`는 *검산 조건의 `Derivative(...)` 호출*에서 `F'=0` 근을 모은다. 개수형(`real_root_count`)의 조건은
   `(다항식 = 0, x > a, x < b)`이고 `verify_real_root_count`가 Derivative 조건을 받지 못한다(코드를 읽은 판단: 범위 조건의 자유기호가 정확히 1개여야 하는데 `Derivative(...).doit() = 수` 조건은 0개라 `_count_bounds`가 None — 직접 주입해 보지는 않았다).
   그래서 **`_critical_roots`는 항상 공집합**이고 규칙은 *어떤 값을 달아도* 위반이다. 실측: 개수형 48건 전부 `M-link-procedure`
   (`proto_run8.log` "개수형 표본의 _critical_roots = set()"), 생성기 빌드는 `ValueError`로 멈춘다(`종단` 절).
   → **규칙 확장이 필수**(규칙이 틀려서가 아니라 값 종류(c값 vs 개수)를 모른다).
2. **"조건을 안 보고 적용하면 1"은 산출값이 아니다.** 평균값 정리의 *결론*("c가 존재한다")을 읽은 주장이지 방정식을 푼 값이 아니다.
   개수형 선지에 M0674로 `1`을 다는 것은 이 프로젝트가 가장 경계하는 "라벨만 바꾸기"다. 정직하게 달 수 있는 개수형 값은 **롤 값 하나**다.
3. **꺾인점 개수형(틀 K)은 검산이 안 된다.** 조각함수의 c 개수를 단일 다항식 검산(`verify_real_root_count`)에 담는 유일한 방법은
   두 조각 방정식의 곱 + 구간 범위인데, 서로 다른 315개 조합을 재 보니 **306건(97%)이 참 개수가 아닌 값을 pass**시켰다(거짓 통과;
   예 `x^3-3x^2-6x+|x|`, [-3,3]: 참 2, 검산기는 3을 pass). 9건만 우연히 정합. 또 참 개수 0은 후보 16,308건 중 442건(2.7%)뿐이고,
   판정기는 `visible_polynomials`가 `2|x-1|`의 `x-1`을 다항식으로 오독하고 `V-count-interval`도 낸다. 새 검산기 없이는 못 닫는다.
4. **정답 0은 다항식 개수형에서 불가능**하다(평균값 정리가 ≥1을 보장). 정답 0이 되는 것은 꺾인점 함수뿐이므로 "정답 0 → 1" 구도는 틀 K에서만 성립하는데 3번에서 막힌다.
   → 조건 확인 축은 *개수를 함수 단위로 옮긴* 틀 B가 정직하게 담는다.

## 3. 틀 A — "c의 개수" 객관식 (다항식)

**발문 틀 3종** (모두 객관식, 선지 `0 1 2 3`):
- A1 `함수 f(x) = {f}에 대하여 열린구간 ({a}, {b})에서 f'(c) = (f({b}) - f({a}))/({b} - ({a}))를 만족시키는 실수 c의 개수는?`
- A2 `함수 f(x) = {f}에 대하여 닫힌구간 [{a}, {b}]에서 평균값 정리의 결론을 만족시키는 c의 값이 열린구간 ({a}, {b})에 몇 개 있는가?`
- A3 `곡선 y = {f} 위의 두 점 A({a}, {fa}), B({b}, {fb})에 대하여, {a} < x < {b}인 범위에서 접선이 직선 AB와 평행한 점의 개수는?`

**정답 절차**: `f'(x)` → 평균변화율 `m=(f(b)-f(a))/(b-a)` → 방정식 `f'(c)=m`(삼차/사차 f면 이차/삼차방정식, 근이 전부 유리) → 열린구간 안 서로 다른 근의 수 `n`.

**오개념 절차(M0674 ②, 롤 혼동)**: `f(a)≠f(b)`인데 `m` 자리에 0을 놓고 `f'(c)=0`을 풀어 구간 안 서로 다른 실근 수 `r`를 센다.
오개념 상황이 문면에서 실제로 발생한다: 문면이 `f(a)=f(b)`를 말하지 않고 실제로 `m≠0`(풀 조건)이다. 선지 값 = `r`, `r≥1`(0이면 "c가 없다"는 자기모순이라 제외), `r≠n`.

**선택지 산출 공식**: 선지 `{0,1,2,3}` 오름차순. 정답 `n`, M0674 = `r`, 나머지 둘은 미귀속(무관 오답). 연결 id는 M-id 그대로(`M0674` — 이 M-id에는 kebab이 없다).

**선형항 s의 역할(설계의 핵심 자유도)**: `f = (n을 정하는 부분) + s·x + t`에서 s는 방정식 `f'(x)=m`을 바꾸지 않는다(f'과 m에 똑같이 더해져 상쇄).
그래서 **정답은 그대로 두고 롤 값만 움직이는** 노브다. 이 덕에 같은 방정식(=같은 검산 조건)에서 오개념 산출값을 문항별로 고른다.

**문제유형**: `ptype.count-solutions`("해의 개수 세기") — 스킬 graph-sketching·case-analysis·graph-reading, 02-06 스킬(deductive-reasoning·graph-reading)과 **graph-reading에서 겹친다**
(`problem_types.jsonl` 직접 확인). 기존 승인 은행의 02-06 연결 6건과 같은 유형이라 새 유형 주장이 아니다. 거짓 유형 아님: 묻는 것이 정말 "방정식 `f'(c)=m`의 구간 안 해의 개수".

**검산 조건(Tier1)**: `("<f'-m 다항식> = 0", "x > a", "x < b")`, `answer_kind="real_root_count"`, 출발식 `solution_setup=_mvt_setup(f, a, b)`.
기존 `_count_item`과 같은 형식이라 저장소 검산기 `verify_real_root_count`가 정답 pass·오답(정답+1 mod 4) fail을 48건 전부에서 냈다.

**걸리는 우회로 규칙**: 기존 판정기에서 **`M-link-procedure` 하나뿐**(48/48 — 위 §2-1). 그 밖 규칙(T-quadratic-mean-value·T-midpoint-answer·T-integer-pinned·V-count-interval·E-derivative·U-extra-solution 등) 위반 0건.
삼차 이상이라 중점 우회로(이차함수 평균값 정리, 5회차 감사)에 안 걸린다.

**슬롯 배정**: 오개념 유발 슬롯 전용(연결 집합 `{M0674}` 균일). 나머지 5슬롯은 같은 틀을 선지 없는 단답형으로 낼 수 있으나 기존 은행의 `count-solutions` 6건과 겹치므로 이 보강 은행에서는 만들지 않는다.

**권고 구성**: 정답 `n=1`인 문항(전체의 약 1/3)은 "평균값 정리가 ≥1을 보장하니 선지 중 가장 작은 양수"라는 추측이 맞는다 — 기존 은행이 개수형을 두 근이 모두 구간 안인 사례(정답 2)로 제한한 이유와 같다.
트리거 슬롯은 `n≥2` 층만 쓰는 것을 권고한다(§9 용량).

## 4. 틀 B — 조건을 만족시키는 함수의 개수

**발문 틀**: `다음 함수 중 닫힌구간 [{a}, {b}]에서 평균값 정리의 조건(닫힌구간 [{a}, {b}]에서 연속이고 열린구간 ({a}, {b})에서 미분가능)을 만족시키는 것의 개수는? ㄱ. f(x) = …, ㄴ. g(x) = …, ㄷ. h(x) = …`
(조건을 발문에 명시해 "끝점 미분가능" 해석 갈림을 막는다. 예: `|x+3|, |x|, x^3+2x`, [-2,3] → 정답 2.)

**정답 절차**: 함수마다 열린구간 안 꺾인점(절댓값 안 식의 실근)의 좌·우 미분계수를 비교 → 만족 개수 `n`.
**오개념 절차(M0674 ①)**: 조건을 확인하지 않고 평균값 정리를 세 함수 모두에 적용 → 만족 개수를 **나열된 함수 총수(3)**로 센다. 선지 3 = 총수, 정답 n≠3.

**함수 풀 설계(우회로 차단)**: ① 다항함수 ② 매끄러운 절댓값 꼴(`x|x|`, `x^2|x|`, `|x^2+1|`) ③ 꺾인점이 열린구간 안(`|x-k|`, `x^2+|x-k|`) → 불만족 ④ 꺾인점이 구간 밖(`|x-k|`) → 만족.
**한 문항에 절댓값 함수가 만족·불만족 둘 다 들어가고 정답이 1~2개**여야 한다 — "절댓값이 있으면 불가"라는 우회로가 틀리고, 정답이 0/3이어서 "전부/없음" 찍기가 통하는 것도 막는다.

**문제유형**: `ptype.condition-satisfaction`("조건 성립 판정") — 스킬 constraint-interpretation·case-analysis·graph-reading, 02-06과 **graph-reading에서 겹친다**. 묻는 것이 실제로 "평균값 정리의 조건이 성립하는가"의 판정이라 거짓이 아니다.
(대안 `verify-claim`·`existence-decision`은 deductive-reasoning으로 겹치지만, 이 문항이 묻는 것은 c의 존재 주장이 아니라 *조건 성립*이라 유형 이름이 덜 정직하다.)

**검산 조건(Tier1)**: `(f1, f2, f3, "x >= a", "x <= b")`, `answer_kind="mvt_hypothesis_count"` — **저장소에 없는 kind**(§6의 신설 필요 항목).
풀이 단계는 첫 함수의 한 조각에 대한 도함수 항등식을 `solution_setup`으로 달면 `steps_of`가 통과한다(40/40; 달지 않으면 "출발식으로 쓸 등식이 없다"로 40/40 실패 — 실측).

**걸리는 우회로 규칙**: 기존 판정기에서 `M-link-procedure`만(40/40). 해설에 함수마다 `g'(x) = …` 식을 쓰면 `E-derivative`가 사라진다(처음엔 21/40이 걸렸다).

**슬롯 배정**: 오개념 유발 슬롯 전용.

## 8. 위험 — 감사 판정자가 결함으로 볼 만한 지점

1. **해석 갈림(A)**: M0674의 두 절 중 *롤 혼동* 절에만 기댄다. MISC-40이 M0674를 omission형·문항 맥락 종속형으로 보아 kebab 승격을 하지 않았고, 감사 판정자가 같은 해석을 취할지는 측정하지 않았다(02-08의 M0676 후단 해석과 같은 한계).
2. **정형 패턴**: (정답, 함정) 쌍이 (1,2)·(2,1)·(3,1) 셋뿐이고 `n≥2` 층만 쓰면 함정이 거의 늘 `1`이다. 선형항 s 범위를 ±12에서 ±40으로 넓혀도 n=3인 방정식은 r=1만 나왔다(관측 사실 — 구조적 원인은 확인하지 못했다). B는 함정이 늘 `3`이고 선지가 늘 `{0,1,2,3}`이다.
   트리거 슬롯 안의 규칙성이므로 슬롯 밖(다른 슬롯)에는 정답 3인 문항을 섞어 학습 가능한 규칙으로 굳지 않게 한다.
3. **난이도**: 사차 f는 `f'(c)=m`이 삼차방정식(유리근 3개 인수분해). 트리거 슬롯 난이도 3.0보다 높게 느껴질 수 있다 — 삼차 f(이차방정식) 층 49건을 섞어 조절.
4. **A1은 방정식을 발문이 준다**: `f'(c) = (f(b)-f(a))/(b-a)`를 읽어 풀면 된다. 평균변화율 계산·방정식·구간 판정의 *행위*는 하지만 정리 인식은 A2·A3가 요구한다. 기존 은행 `rep-two-candidates-one-inside`와 같은 부류(승인 이력 있음).
5. **B의 영역**: 연속·미분가능 판정은 수학Ⅱ 내용과 겹친다. M0674의 correction_point("평균값 정리를 설명하고 활용")의 *조건 설명* 쪽을 재는 문항이다.
6. **끝점 꺾임**: 풀에서 뺐다. 넣으면 정리는 *성립*(충족)이라 학생이 "끝점 미분불가 = 불가"로 오판하는 별개 오개념을 건드린다 — 발문이 조건을 명시해도 해석 갈림 위험.

## 10. 확인하지 못한 것

- **감사 통과 여부**: 판정기(`shortcut_violations`)·수용 게이트는 통과하지만 독립 감사 판정자(S5)가 결함으로 보는지는 측정하지 않았다. 특히 §8-1의 해석 갈림.
- **틀 B의 검산기**: 신설 코드를 쓰지 않았다(제안만). `verify_mvt_hypothesis_count`를 `_CONCEPTUAL_VERIFIERS`에 등록할 때 닿는 다른 소비 지점(`harness/qa_pipeline`·`corpus_reverify`·`populate`·교차검증 관점 등록)을 전수 확인하지 않았다.
- **가드 패치 적용본**: 프로토는 패치를 프로세스 안 monkeypatch로 흉내 냈다. 실제 파일에 적용했을 때 `tests/…/test_p3_diff_shortcut_guard`의 규칙 ID·회차 슬라이스 동결 테스트가 무엇을 요구하는지(새 규칙 ID는 만들지 않고 기존 `M-link-procedure`의 분기라 영향이 작다고 보지만) 돌려 보지 않았다. 전체 스위트도 돌리지 않았다.
- **사슬 닫힘은 시뮬레이션**: 합성 문항을 approved로 *가정*한 것이다. 실제 승인은 n≥200 라벨·S5 감사 회차가 정한다.
- **풀이 단계(Tier2)**: A는 `steps_of`로 전이 전건 correct를 확인했다. B는 첫 함수 한 조각의 도함수 항등식 한 줄(2단계)이라 "풀이 단계 있음" 계측은 충족하나 해설 전체를 단계로 옮기지는 못한다.
- **B의 해설 정확성**: 해설 문장(함수별 도함수·꺾인점 설명)은 SymPy로 계산한 조각 도함수를 쓰지만, 문장 전체의 정합은 기계로 검증하지 못했다(A는 저장소 위생 게이트가 해설 산술을 검증했고, 그 게이트가 초기 구현의 평균변화율 표기 오류 — s 추가 후 m 미갱신 — 를 잡아 수정했다).
- 학생이 실제로 `r`·`3`을 고르는 비율(오개념 유발력)은 측정하지 않았다.
