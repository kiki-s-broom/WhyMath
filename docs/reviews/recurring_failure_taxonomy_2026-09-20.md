## §0. 한 줄 요약 (다섯 문장)

1. 130일 동안 결정 로그에 기록된 **코딩 과정의 사고·실수는 676건**이며, 세션 330개 기준 **세션당 2.05건**, 커밋 1,204개 기준 **커밋 100개당 56건**이다.
2. 사고의 **4분의 1(26%)은 "보호 장치가 있다고 믿었는데 작동하지 않은" 유형**(B)이고, 다음이 미머지 고립·병렬 충돌(13%), 검증 판정 무효화(9%), 부재·존재 오판(9%), 대장 조작 결함(9%)이다. 학생·교수학·저작권 원칙 위반에서 난 사고는 규칙 대장 기준 **0건**이다 — 문제는 수학이 아니라 *공정*이다.
3. 가장 비싼 피해는 "틀린 것"이 아니라 **"모르고 지나간 시간"**이다. 잠복(latent) 피해가 173건(26%)으로 낭비 왕복(141건)보다 많고, 기록된 것만 합쳐도 잠복 256일·폐기 16,472줄·헛된 왕복 58회다.
4. 재발 방지 규칙 52건 중 **29건(56%)은 산문(글)으로만 존재**하고, 9월에 등재된 22건 중 16건은 *새 유형*이 아니라 **기존 규칙이 다시 뚫려 붙은 확장**이다. 같은 계열이 최대 4회차(인코딩·검사 판정 무효화)까지 반복됐다. 글로 적은 규칙은 통계적으로 2~3회차까지 재발을 막지 못했다.
5. 그래서 이 문서의 결론은 "규칙을 더 쓰자"가 아니다. **사고를 구조화된 대장에 넣고, 2회차부터는 코드(훅·게이트·러너)만 대책으로 인정하며, 세션이 매번 읽는 헌법을 절반 이하로 줄이는 것**이다. 구체 대책 7건과 경제적 코딩 방안 9건을 §5·§6에 두고, 그중 5건을 백로그 태스크로 등재했다(§7).

### 1.2 방법

- 결정 로그는 5구간으로 나눠 서브에이전트 5개가 같은 스키마(§2.2의 대분류 11종 A~K)로 추출했다. 규칙 대장·프로세스 통계는 각각 별도 에이전트가 맡았다. 병합 시 같은 날짜·같은 분류·제목 유사도 0.6 이상을 1건으로 접었다.
- "사고"의 정의: *되돌리거나 다시 해야 했던 일*, *틀린 채로 지나간 판정*, *작동하지 않는 보호*. 단순 설계 변경이나 계획 수정은 제외했다.
- 피해는 문서에 적힌 숫자만 옮겼다. 없는 숫자는 "미정량"이다.

### 1.3 한계 (이 숫자를 읽을 때 알아야 할 것)

- 추출은 LLM 판독이다. 대분류 경계(특히 B·J·K)는 판독자마다 흔들릴 수 있어 **±10% 정도의 분류 오차**를 전제로 읽어야 한다. 부록 JSONL을 사람이 검수하면 정확도가 오른다.
- 결정 로그에 *적힌* 사고만 센다. 적히지 않은 사고는 없다는 뜻이 아니다. 특히 5~6월은 기록 밀도가 낮아 과소집계다.
- 구간 경계에서 같은 사고가 두 번 잡혔을 가능성이 있다(중복 병합은 1건만 잡혔다). 총수는 ±3% 여유를 둔다.
- 회차 카운터는 문서가 **스스로 적은 숫자** 그대로다. 문서 간 계수가 다른 계열(태스크 ID 중복 등)은 그대로 병기했다.

## §4. 횡단 진단 — 왜 규칙이 뚫리는가 (다섯 기전)

**M1. 산문 규칙은 3회차까지 못 막는다 — 통계적으로.** 규칙 52건 중 산문만 29건. 계열 11개 중 코드가 1회차에 붙은 것(태스크 ID·인코딩·보호 장치)조차 축이 바뀌면 재발했고, 산문만 있던 계열(검사 판정 무효화·증거 펜스·자리표시자)은 예외 없이 2~4회차까지 갔다. 결정 로그 스스로 "동일 유형 텍스트 규칙 2회 실패 후 코드 착지"를 선례로 삼았지만, 그 선례가 **규칙(산문)**으로 적혀 있어 세션마다 다시 잊는다.

**M2. "존재 ≠ 작동"이 78%의 뿌리다.** §2.2에서 본 대로 B·C·A·D·G·H·J 528건은 전부 *있다*를 *작동한다*로 읽은 사고다. 갭 리뷰 §6이 같은 계열을 11회차까지 세고 있다(1~8=만들고 안 함, 9=경계에서 흘림, 10=자인 공백을 판정이 안 읽음, 11=정정 자체가 도달 실패). 이건 규칙으로 고칠 수 없다. **작동 여부를 산출물에 내장**해야 한다 — 가드에는 뮤테이션 픽스처, 알고리즘에는 작동 비율, 계약에는 집행 지점, 태스크에는 판정 명령.

**M3. 검증 표면이 둘이다.** CI backend 잡은 26스텝·전체 18잡인데 `/drive` 런북은 "pytest·ruff"다. 로컬 판정과 CI 판정이 다르니 "로컬 green·CI red"가 구조적으로 생긴다(A 61건). 사람이 매번 스텝을 고르는 한 4회차는 5회차가 된다.

**M4. 병렬은 구조이고 조율은 선택이다.** 하루 4.5세션. claim은 세션이 *해야* 작동하고, 경고는 21,019건 중 0건이 차단이다. 측정을 시작한 조건("2주 또는 30세션 관찰 후 승격")은 74일·330세션으로 충족됐지만 **승격 결정을 내리는 주체가 없었다.** 측정 없는 도입을 막으려던 설계가 "측정만 있고 결정 없음"으로 굳었다.

**M5. 기억은 쓰기 전용이다.** `MEMORY.md` 3.1MB는 어느 세션도 읽지 못한다. 그래서 사고 경위가 `CLAUDE.md`로 올라가고(62,239자), 그것을 매 세션이 통째로 읽는다(추정 4.5만~6.8만 토큰). 태스크 중앙값 0.62시간짜리 세션에 이 고정비가 붙는다. 반면 정작 필요한 정보(이 파일을 만질 때 난 사고)는 검색되지 않는다 — 회차 계수조차 문서마다 다르다(§1.3).

**P3 뮤테이션 러너 (HARN-120)**: `scripts/harness/mutate.py` — 뮤테이션 명세(파일·앵커·치환) 목록을 받아 ①`mutated != original` 단언 ②지정 테스트 실행 → RED 확인 ③바이트 동일 원복 ④절별 픽스처 접촉(치환 대상이 픽스처 실행 경로에서 실제로 평가됐는지 coverage로 확인)을 자동 단언하고 표를 낸다. 기존 101파일 중 하네스가 인라인인 상위 10건을 이관. CI `harness-integrity`에 러너 자기검증 1스텝.

## §6. 혁신적·경제적 코딩 방안 9건 (재발 방지 밖의 것)

"경제적"의 기준은 세 가지다 — **토큰(세션 고정비)**, **사람 시간(Kiki 왕복)**, **폐기 코드(중복·고립)**. 각 방안에 어떤 비용을 얼마나 줄이는지 근거 수치를 붙였다.

**E1. 규칙의 적시 주입(JIT rule injection) — 헌법을 읽히지 말고 *필요할 때만* 보여준다.**
지금은 476줄을 매 세션 통째로 읽는다. 대신 `PostToolUse(Edit|Write)` 훅이 편집된 파일 경로를 P1 사고 대장과 대조해 **그 경로에서 난 사고와 그 규칙만** 3~5줄로 주입한다(예: `scripts/harness/*.py` 편집 → "제자리 편집 3단언·백틱 heredoc" 2줄). `check-edit` 훅이 이미 매 편집마다 돈다 — 실행 비용 0 추가. 절감 = 세션당 3만~5만 토큰(P4와 합산) × 하루 4.5세션. 부수 효과 = 규칙의 *관련성*이 올라가 주의 희석(attention dilution)이 준다. 이것은 이 프로젝트가 LLM 컨텍스트에 적용하는 원칙("전체 그래프를 주지 마라, Minimal Reasoning Subgraph만")을 **세션 자신에게 적용**하는 것이다.

**E2. 작동 증명 필드(evidence command) — acceptance를 산문에서 명령으로.**
태스크 736건의 acceptance는 평균 3.7항·평균 923자의 산문이다. `done`은 사람(세션)이 자기평가한다. 각 acceptance 항에 선택 필드 `check:`(exit 0/1 명령)를 두고 `backlog.py done`이 있는 것은 실행한다. 처음엔 선택, 측정 후 신규 태스크는 필수. 절감 = "정본화≠집행"(3회차)·"작동 신호 없는 부착"(J 32건) 계열의 사후 발견 비용(잠복 중앙값 7일). 이미 게이트 CLI 16종이 exit code 계약을 쓰므로 새 인프라가 아니다.

**E3. 세션 배치(batching) — 세션 시작 고정비를 여러 태스크가 나눠 낸다.**
착수→완료 중앙값 0.62시간, 세션당 태스크 중앙값 1. 세션 시작(브리핑·헌법·환경 파악)이 태스크 본체와 같은 자릿수다. `/drive --max 3`이 이미 있으나 세션 대부분이 1건에서 끝난다(같은 세션 done 없는 start 88건). `next`가 **같은 paths 군의 소형 태스크 2~3건을 묶음으로 제안**하면(겹침 계산은 `pathscope.py`가 이미 한다) 시작 비용이 1/3이 된다. 조건: P5(claim-first block)로 묶음 claim이 안전할 때.

**E4. 폐기 회계(waste accounting) — 주간 지표에 3종 추가.**
현재 `weekly-metrics` 6종은 제품 KPI다. 여기에 ①폐기 PR 수·줄 ②중복 구현 건 ③사고 건수·계열 최대 회차(P1)를 append. 측정되지 않는 비용은 줄지 않는다 — 폐기 43 PR·16,472줄이 지금까지 어디에도 합산돼 있지 않았다(이 보고서가 처음).

**E5. 런북 컴파일러 — Kiki 명령 블록을 손으로 쓰지 않는다.**
E 34건·F 24건·게이트 1건당 왕복 최대 4회·백업 게이트 26일. YAML 단계 명세 → PowerShell 렌더러가 ①자리표시자 불가(값은 세션이 채우거나 `Read-Host`) ②실행 코드 출처 동결(`__file__` 출력) ③단일 `if` 가드 + 거부 가지 출력 ④`git log -1` 자가검증 ⑤`cmd /c` 인코딩 우회 ⑥언어 태그 펜스를 **자동 삽입**한다. 기존 `check_runbook_blocks.py`는 출력을 재검사. 절감 = Kiki 왕복(사람 시간). 현재 규칙 13건이 전부 "렌더러가 하면 사람이 기억할 필요 없는 것"이다.

**E6. 감사의 자동화 — 사람이 쓰던 감사 문서를 워크플로 산출물로.**
미머지 감사 12회(회수 등재 0~1건/회로 수렴)·갭 리뷰 r1~r3. `backlog.py branches`가 이미 5분류를 계산한다. `harness-audit` 워크플로(존재)가 주 1회 분류 표를 PR 코멘트 또는 `docs/reviews/auto/`에 내고, 사람은 **변화분만** 본다. 갭 리뷰의 "존재≠작동" 스캔은 `declared-unwired-audit` 잡이 이미 돌므로 그 결과를 같은 곳에 합친다. 절감 = 감사 1회당 세션 1개(약 1시간 + 토큰).

**E7. 알고리즘 좌석의 작동 비율 필드.**
