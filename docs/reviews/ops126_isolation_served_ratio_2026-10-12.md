# OPS-126 — SymPy 격리가 *작동한 비율*의 관측 배선 + 상한·용량 재판정

판정 기준: `main d873d064` 위의 `claude/relaxed-keller-4wk0b2`(미머지 작업 트리). 측정 환경: Linux 6.18 · Python 3.12.3 · SymPy 1.14.0 (Windows·Phaiakes9 미측정).

## 0. 한 줄 결론

| acceptance | 판정 | 요지 |
|---|---|---|
| ① 소비자 배선 | **이행** | `/health/ready`에 `sympy_isolation` 섹션 신설 — `isolated_ratio`·`undecidable_ratio`·사유별 카운터. 기존 좌석 재사용(신규 엔드포인트·모듈 0) |
| ② 상한 재판정 | **부분 이행 + 승계** | 합성 대리 분포로 실측해 **5.0초 유지**. 실제 학생 입력 분포는 파일럿 데이터가 필요해 `OPS-131`로 분리 |
| ③ 운영 용량 | **이행** | 워커당 RSS 73~76MB(종전 주석 100~150MB는 과대) → 기본값 2 유지. 증설 신호를 지표(`queue_waits`)로 지정 |

## 1. ① 무엇이 비어 있었나

`api/_isolated_call.isolation_stats()`는 호출 수·상한 초과·대기열 포화·워커 사망·폴백을 세지만 **읽는 비테스트 코드가 0건**이었다(테스트 4곳만 읽음). 정상 응답 200은 격리가 일했다는 증거가 아니다 — 격리를 끄거나(`sympy_isolation_enabled=false`) 호출이 전부 스레드 폴백으로 새도 200은 같다. "작동한 비율" 원칙(CLAUDE.md)의 갭이다.

### 배선

- `api/_isolated_call.py` — `IsolationSnapshot`(불변)과 `isolation_snapshot()` 신설. 풀이 없으면 만들지 않고 0을 읽는다.
- `app.py` — `/health/ready` 응답에 `sympy_isolation` 섹션. **기존 좌석**(`ocr`·`solution_segmentation`·`l6_mode_reach`와 같은 자리)을 재사용했고 새 엔드포인트·모듈은 없다.

### 두 비율의 정의

- `isolated_ratio` = `calls / (calls + fallbacks)` — 격리 대상 호출 중 **시간 상한이 걸린 프로세스 풀에서 실제로 돈 비율**. 1.0이 아니면 일부가 pickle 불가로 스레드 폴백한 것이고 폴백에는 상한이 없다.
- `undecidable_ratio` = `(timeouts + queue_waits + worker_deaths) / calls` — 풀에 맡겨진 호출 중 **판정 불가로 접힌 비율**. 0이 아니면 그만큼이 "모른다"로 떨어졌고, 정상 입력이 섞였는지는 `OPS-131`의 입력이다.
- **None-vs-0** — 분모가 0이면 `null`이다(0건 중 0건이 아니라 측정 대상 없음). 격리를 끄면(`enabled=false`) 호출이 인라인이라 카운터가 서지 않아 항상 `null`이다.

### 한계(명시)

- 카운터는 **프로세스별**이다. uvicorn `--workers`가 여럿이면 응답은 요청을 받은 워커 1개의 값이다. `process_id`로 워커를 가리고 합산은 외부 스크레이퍼 몫이다. 재시작하면 0부터다.
- 풀 카운터는 I/O 스레드에서 증가하므로 극단적 경합에서 근사값이다(정확한 회계가 아니라 비율 관측이 목적).
- 취소된 요청(클라이언트 끊김)은 `calls`에는 들어가지만 접힘으로 세지 않아 `undecidable_ratio`는 하한 쪽 편향이다.

### 검증

- 신규 테스트 `tests/backend/api/test_sympy_isolation_observability.py` 16건. 실 verify 요청이 실 풀 카운터를 올리고 그것이 `/health/ready`에 나오는 것까지 양방향(정상 → 0.0, 상한 초과 → 0.5)으로 확인한다. 격리를 끈 대조군은 같은 요청이 `calls=0`·비율 `null`을 낸다.
- **뮤테이션 7종 전건 RED**(주입 적용·원복 바이트 동일을 하네스가 단언): ready 결선 제거, `timeouts`/`queue_waits` 키 바꿔치기, `isolated_ratio` 항상 1.0, 분모 0을 0.0으로(None-vs-0 붕괴), `enabled` 하드코딩, `worker_deaths` 누락, `health_ready`에서 `isolation_snapshot()` 호출 제거(AST 배선 테스트).

## 2. ② 상한 재판정 — `sympy_isolation_timeout_s = 5.0` 유지

### 무엇을 재판정했나

종전 근거는 **최종답 경로** 정상 문항 14,034건(p50 1.2ms·p99 11ms·최대 107.5ms)뿐이었다. 학생 풀이 **단계** 입력(`verify-step`·`verify-solution`)의 분포는 코퍼스에 없고, 저장소에는 파일럿 `isolation_budget_exceeded` 로그도 없다. 그래서 `scripts/analysis/measure_sympy_isolation_budget.py --mode steps`를 추가해 두 가지를 쟀다.

### (가) 교육과정 형태 합성 단계 354건 (시드 20261012)

| 범주 | n | p50 | 최대 |
|---|---:|---:|---:|
| 전개 올바름 / 오류(분배 누락) | 60 / 60 | 24 / 22 ms | 157 / 45 ms |
| 인수분해 이차 / 삼차 | 40 / 40 | 15 / 22 ms | 26 / 35 ms |
| 일차방정식 / 이차방정식(인수·근) | 40 / 40+40 | 8 / 16·2 ms | 13 / 21·4 ms |
| 유리식 · 지수 · 삼각 · 고차 전개(6~8차) | 8·6·11·9 | 33·13·47·24 ms | 34·18·80·39 ms |
| **전체** | **354** | **17.8 ms** | **157 ms (p99 50 ms)** |

판정: correct 294 · incorrect 60. 후보 상한 0.25초에서도 판정 불가로 떨어지는 건 **0건**이다. 5초 상한은 최대치의 약 32배 여유다.

### (나) 구조 예산을 통과하는 가장 느린 부류 — 고차 방정식 단계

`x^d + k·x + 1 = 0 → x^(d-1) + k·x + 2 = 0`, 상한 없이 끝까지 돌린 소요(초):

| 차수 d | k=1 | k=7919 |
|---:|---:|---:|
| 6 | 0.29 | 0.92 |
| 8 | 0.22 | 1.34 |
| 10 | 0.58 | 1.29 |
| 12 | 0.73 | 2.25 |
| 14 | 1.13 | 3.81 |
| 16 | 1.50 | 4.74 |
| 18 | 3.41 | **6.24** |
| 20 | 2.77 | **9.84** |

무릎은 **18차 이상 + 큰 계수**다. 중요한 발견: 이 16건은 상한 없이 끝까지 돌려도 **전부 `unverifiable`**이다. 즉 5초 상한이 끊는 입력은 어차피 "판정 불가"가 났을 입력이라, 상한은 **지연만 줄이고 판정 정보는 잃지 않는다**. 정상 입력이 판정 불가로 떨어지는 경로는 이 부류에서 확인되지 않았다.

### 판정과 한계

값을 **유지**한다(조정 근거 없음). 단 이 판정의 한계를 숨기지 않는다:

- 합성 대리 분포이지 실제 학생 입력이 아니다. 학생은 생성기가 만들지 않는 식(오타·비표준 표기·긴 연쇄 등식)을 쓴다.
- 측정은 한 머신(샌드박스)의 값이다. 느린 CI 러너·저사양 서버에서는 소요가 커질 수 있다.
- 남은 판정은 `OPS-131`이 소유한다 — 파일럿이 격리 호출을 1,000건 이상 쌓은 뒤 `/health/ready`의 `sympy_isolation`을 읽어 `timeouts`가 0이 아니면 그 입력이 상한 없이 돌렸을 때 correct/incorrect로 끝났을지 판정한다.

## 3. ③ 운영 용량 — `sympy_isolation_max_workers = 2` 유지

### 실제 배포 형상 (문서 근거)

- `Dockerfile` `CMD` = 단일 `uvicorn whymath_backend.app:create_app --factory` (**`--workers` 없음** → 컨테이너당 서버 프로세스 1개).
- `docker-compose.prod.yml` `app` 서비스는 `command` 오버라이드·`mem_limit`·`cpus`가 **없다**(메모리 제한 미선언). `docker-compose.pilot.yml`은 DB만 정의한다.
- `isolated()`를 쓰는 곳은 `api/verify.py`·`api/coach.py`(API 프로세스)뿐이라 celery/quality-worker에는 SymPy 워커가 뜨지 않는다.
- 따라서 컨테이너당 상주 SymPy 워커 = `1 × 2 = 2`개.

### 메모리 실측

| 항목 | RSS |
|---|---:|
| 앱 프로세스(임포트 직후 → `create_app` 후) | 148 → 167 MB |
| SymPy 워커 1개(정상 호출 후) | **73~76 MB** (HWM 동일) |
| 상한 초과로 kill → 교체된 워커 | 73~76 MB (HWM이 오르지 않음) |
| 컨테이너 정상 상태 합계(앱 + 워커 2) | **약 320 MB** (+ 교체 중 일시적으로 워커 1개 ≈ 75 MB) |

종전 `config.py` 주석의 "개당 약 100~150MB"는 이 환경에서 **과대**였다(실측 73~76MB). Windows는 미측정이라 주석에 100MB 안팎 가정을 병기했다. 서버 워커를 N개로 늘리면 `N × 2 × 75MB`가 더해진다.

### 점유 시나리오 실측

느린 입력 2건이 워커 2개를 동시에 점유한 상태에서 정상 요청 20건을 보냈다:

- 20건 전부 성공(접힘 0). 단 **대기 p50 5.77초·최대 5.80초** — 느린 입력이 상한(5초)까지 워커를 잡고 있는 시간만큼 기다린다.
- 풀 통계: `calls=25`·`timeouts=3`·`queue_waits=0`·`worker_deaths=0`·`fallbacks=0`.

이 대기는 큐 상한(시간 상한 × 2 = 10초) 안이라 접히지 않지만 **학생 체감 지연**이다. 느린 입력이 동시에 3건 이상 오면 큐 상한을 넘겨 `queue_waits`가 오른다.

### 판정

기본값 2를 **유지**한다. 근거: 메모리 비용이 작고(워커당 약 75MB), 현 형상에서 느린 입력의 동시 도착률은 파일럿 데이터 없이는 알 수 없으며, 증설은 **지표가 신호를 줄 때** 하는 편이 낫다. 신호는 `/health/ready`의 `sympy_isolation.queue_waits > 0`이다(① 배선이 ③의 판정 도구다). 이 신호의 사후 판정은 `OPS-131`②가 소유한다.

## 4. 이 세션이 하지 않은 것

- 실제 학생 입력·파일럿 로그 기반 실측 — 데이터가 없다(`OPS-131`).
- Windows(Phaiakes9)·실 배포 이미지의 메모리 실측 — 이 환경에 도커 데몬이 없다.
- 상한·워커 수 기본값 변경 — 근거가 변경을 지지하지 않았다.
- 알림 임계 신설 — 관측만 배선했다(게이트·알림은 별건).
