## 2. 정의와 근거

### (a) 자동검증 1차 통과율

정본 문구는 `docs/standards/eos_verification_design_v1.md` §6 "Deterministic Gate pass ÷ 전체 생성 (수용 게이트 로그)"이다. 결정론 검증의 범위는 EOS-207 acceptance ①(a)가 "SymPy 검산·스키마·출처"로 정했다.

- **결정론 검증의 범위**: 수용 게이트(`l3/equivalent/acceptance.py` — 저작권·SymPy 정확성·위생·동등성 4종)만이 아니다. 그 앞 단계인 응답 형식 검증(JSON 파싱)과 Problem 스키마·Provenance 불변식 조립(`l3/equivalent/llm_generator.py` — "Problem/Provenance 불변식 위반(저작권 게이트가 생성 거부)")도 포함한다. 둘 다 LLM을 쓰지 않는 결정론 거부이고, acceptance ①(a)의 "스키마·출처"가 바로 이 단계다.
- **pass**: 결정론 사슬을 끝까지 통과한 후보다. 오케스트레이터(`l3/equivalent/orchestrator.py`)는 "생성 → 수용 게이트 → 중복 검사 → 저장" 순서로 돈다. 그래서 `accepted_stored`와 `rejected_duplicate`가 통과다(중복 거부는 게이트를 통과한 뒤 신규성 축에서 걸린 것이다).
- **전체 생성**: 모델이 응답을 돌려준 시도다. 미생성(전송 타임아웃)은 생성이 없으므로 뺀다. 파싱 거부·조립 거부는 생성은 있었고 결정론 검증이 거부한 것이므로 분모에 넣는다. 생성 로그의 `error_detail` 앞머리로 셋을 가르고, 어디에도 들지 않는 실패 원인이 있으면 분모를 정할 수 없으므로 값을 내지 않는다.
- **1차**: 결정론 검증이 처음 판정한 결과다. 사람이 고친 뒤의 승인은 자동검증 통과가 아니다.
- **수용 게이트 로그**: `cu.jsonl`(저장분) + `cu.review.jsonl`(비저장분)이다. 생성 로그와 slug 단위·실패 건수로 대조하고, 어긋나면 측정 실패로 처리한다.

대안 값(게이트 도달 기준 13/89)을 주 값으로 쓰지 않은 이유가 있다. 그 정의는 형식·스키마 단계에서 거부된 22건을 "생성되지 않은 것"으로 취급한다. 그러면 결정론 검증의 실패가 분모에서 사라져 통과율이 부풀어 보인다.

**우회된 통과는 통과로 세지 않는다.** 게이트의 정확성 축은 후보가 스스로 적은 검산식에 정답을 넣어 본다. 검산식이 `n = 3`처럼 정답 상수를 다시 적은 것이면, 정답이 틀렸어도 같은 틀린 값으로 적히므로 언제나 통과한다. `l3/equivalent/verify_bypass.py`가 이것을 판정한다. 식의 AST에 나오는 수(0·1 제외)가 정답 표기의 수와 정확히 같으면 다시 계산할 재료가 없다고 보고 재진술로 판정한다. 헌법 R13-01("재도출 검증은 생성 단계의 정답을 입력으로 받지 않는다")의 사후 판정이다.

이 판정기가 놓치는 경우도 있다. `2 = -4 + b`처럼 미리 구한 중간값을 쓴 검산이나 `M**2 - M - 182 = 0`처럼 거꾸로 만든 이차식은 재계산으로 센다. 그러므로 0.1171은 **실제 검증의 상한**이다. 약한 검산은 블라인드 재도출(EOS-205)의 몫이다.

검수 메모의 실측과 대조하면, 메모가 "동어반복"으로 지목한 저장분은 17건이다(EOS-205 acceptance ①). 기계 판정도 저장 30건 중 재진술 17건이다. 회귀 테스트 `test_eos197_round_has_seventeen_restatements`가 이 값을 고정한다.

주간 KPI(`ops/weekly_metrics_report` 파일 입력 모드 `--authoring-run-dir`)의 `auto_gate_pass_rate`도 같은 정의를 쓴다(값 = 13/111).

### (b) 힌트 정답 누설

CU 정의(§3)의 "3단계 힌트" 좌석은 S4-11 `hints` 표다. EOS-197 산출물(`cu.jsonl`)에는 힌트 필드가 없고, 같은 회차의 `hints` 표 내보내기도 없다. 그래서 측정 대상이 0건이다. 이것은 "누설 0"이 아니다(스캔 0건은 통과가 아니다).

측정 경로는 준비돼 있다. `--hints-jsonl`(Hint 모델 JSON 1행 1건)을 주면 힌트 게이트 B(`l4/hint_content/gates.check_answer_leakage`)를 그대로 돌린다. 이 게이트는 글자 축(정답 문자열)과 값 축(계산하면 정답이 되는 식)을 본다. 힌트 1건은 3상태로 판정한다. 누설이면 True, 두 축 모두 clean이면 False, 그 밖은 None(사람 폴백)이다. 무관용 기준은 F8 정의대로 L1·L2이고 L3 누설은 따로 센다.

축 상태는 보지 않은 것을 통과로 세지 않는다. 판정한 L1·L2 힌트가 0건이면 측정 불가다. L1·L2 힌트가 없는 CU, 어느 CU에도 붙지 않는 힌트(problem_id 조인 실패), 사람 폴백 힌트가 하나라도 있으면 판정 불가(UNDECIDED)다. 앞의 두 경우는 첫 판에서 PASS로 새던 구멍이었다(독립 리뷰 P1).

**의미 축은 이 도구가 재지 않는다.** §5 F-Ⅴ가 의미적 누설을 "자동 검사 밖"으로 정의했고, §6은 "전수 자동 + LLM 심판 + 인간 30건"을 요구한다. 기계 두 축이 clean이어도 의미상 누설 0의 증명은 아니다. 그래서 출력은 항상 `HINT_SEMANTIC_AXIS=NOT_MEASURED`를 싣는다(`docs/standards/superhuman_verification_standard.md`).

### (c) 메타 누락

| 필드 | 출처 |
|---|---|
| `achievement_standard_codes` (1개 이상) | CLAUDE.md "모든 콘텐츠는 성취기준 코드 1개 이상 태그" · §3 성취기준 좌석 |
| `license`, `source_type` | `ops/provenance_audit.py` ③④ (같은 상수를 공개 이름으로 재사용) |
| `generation_type`, `authored_by` | 헌법 R27-01 "출처 필드(유형·근거·생성 모델·라이선스)" |
| 같은 `cu_slug`의 성공 생성 호출 | `ops/provenance_audit.py` ⑥ |
| 그 호출의 `model_name`, `prompt_version`, `input_sha256` | 감리 W-18 · provenance_audit ⑦ |
| 그 호출의 `seed` | `l3.generation_seed.capability_for_model`이 "지원"으로 분류한 좌석에서만 (provenance_audit ⑦) |

EOS-197의 30 CU는 모두 채워져 있다. openrouter 좌석 27건의 모델(`deepseek/deepseek-v4.1-flash`)은 `capability_for_model`이 seed 지원 여부를 **미상**으로 분류한다. 그래서 seed를 검사하지 않았다(도구 출력 `META_SEED_NOT_APPLICABLE={"deepseek/deepseek-v4.1-flash(미상)": 27}`). 클라우드 좌석의 `seed=null`을 위반으로 보지 않는다는 것은 Kiki 2026-10-27 결정이다. 다만 검사하지 않은 것은 통과가 아니므로 모델별 건수를 따로 낸다.

## 5. 재현 명령

Kiki 머신에서 이 브랜치 코드로 재현하는 블록이다(읽기 전용 · 쓰기 0). 머지 뒤에는 `origin/main` 작업 트리에서 같은 CLI를 돌리면 된다.

```powershell
# Windows PowerShell — Phaiakes9
cd C:\Users\kiki\Desktop\__AI\WhyMath
git fetch origin claude/eos-207-g3-measures
git worktree add --detach "$env:TEMP\wm-eos207" origin/claude/eos-207-g3-measures
$env:PYTHONPATH = "$env:TEMP\wm-eos207\src\backend"
python -m whymath_backend.ops.g3_content_measures --round eos197-a6 --runs-root "$env:TEMP\wm-eos207\data\runs"
"G3_MEASURES_EXIT=$LASTEXITCODE"
```

이 세션(Linux)의 판정 줄 실측은 `GATE_FAILURE_KINDS={"assembly_rejected": 11, "not_generated": 25, "parse_rejected": 11}` · `GATE_RESPONDED=111` · `GATE_EVALUATED=89` · `GATE_PASS_RAW=35` · `GATE_PASS_BYPASSED=22` · `AUTO_GATE_PASS_RATE=0.1171` · `AUTO_GATE_PASS_RATE_GATE_REACHED=0.1461` · `HINT_MACHINE_AXIS=NOT_MEASURABLE` · `HINT_SEMANTIC_AXIS=NOT_MEASURED` · `META_CU_MISSING=0` · `LABEL_MISMATCH=2` · `EXIT=2`이다. 성공 기준은 `G3_MEASURES_EXIT=2`와 이 값의 일치다. 값이 다르면 좌석 폴더가 다르다는 뜻이다.

주간 KPI 미리보기는 EOS-197 ⑦ (d)로 고정한 원장 레코드와 같은 창(`2026-10-27T14:06:14.101338Z`~`2026-10-28T07:52:53.299873Z`)을 썼다. `--authoring-run-dir`에 좌석 두 폴더를 주면 `auto_gate_pass_rate`가 `measured: true` · `0.11711…`로 나온다. 원장(`metrics/weekly.json`)에는 쓰지 않았다(고정 증적을 건드리지 않는다).

## 6. 한계와 후속

- 재진술 판정은 가장 강한 우회 하나만 잡는다. 약한 검산은 재계산으로 세므로 통과율은 실제 검증의 상한이다.
- 수 리터럴이 문항 본문에서 왔는지는 보지 않는다. `x = 2*3`(정답 6)도 재계산으로 센다.
- `x = 1+1+1`(정답 3)처럼 1의 합으로 정답을 적으면 놓친다(0·1 제외 때문에 리터럴이 비어 재계산으로 판정된다). 상수 부분식을 접으면 잡히지만, 그러면 `4*3 + 7` 같은 진짜 재계산이 재진술로 둔갑한다. 그래서 미탐 쪽을 택했고, 테스트 `test_sum_of_ones_is_a_known_miss`가 이 한계를 고정한다. 생성 단계 거부는 EOS-205 몫이다.
- 힌트 의미 축과 기계 판정 불가 힌트의 사람 폴백 입력 경로가 없다. 후속 태스크로 등재했다.
  - **EOS-209**: 동등문제 생성기가 CU 3단계 힌트(L1·L2·L3)를 만들고 `--hints-jsonl` 형식으로 내보낸다. EOS-197 회차는 힌트가 0건이었다.
  - **EOS-210**: 힌트 누설 사람 판정 좌석. 기계 판정 불가 폴백과 의미 누설 표본(§6 인간 30건)을 기록하고, 측정 CLI가 그 기록을 읽어 UNDECIDED와 의미 축을 낸다.
  - 두 태스크를 G-eos-g3의 입력으로 묶을지는 Kiki 결정 사항이라 게이트에 연결하지 않았다.
- 이 CLI는 CI 차단 스텝에 배선하지 않았다. 현행 회차에서 exit 2가 정직한 설계값이라 차단 스텝이면 항상 red가 된다. 대신 backend 잡의 pytest(`tests/backend/ops/test_g3_content_measures.py::TestEos197FirstMeasurement`)가 실데이터 측정값을 고정한다. 선언≠배선 감사에는 `by-design`으로 등재했다.
