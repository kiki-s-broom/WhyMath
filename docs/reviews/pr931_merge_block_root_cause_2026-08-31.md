## 2. 구조 원인(라운드 2·3)의 해부 — 왜 매번 충돌했나

`backlog/events.ndjson`은 **모든 세션이 append하는 단일 공용 파일**이다(start/done/policy_warn…
전 이벤트). 저장소는 `.gitattributes`에 `merge=union`을 걸어 뒀고, 실제로 **로컬 git 병합은
매번 충돌 0**으로 해소됐다(이 사고 중 4회 전부 실측).

그런데 **GitHub의 mergeability 판정과 머지 실행은 저장소가 선언한 merge driver를 적용하지
않는다.** 그래서:

- main에 *어떤* PR이 착지하든 — 내용이 무엇이든 — events.ndjson에 줄이 추가되고,
- 그 파일을 만진(=사실상 모든) 열린 PR은 GitHub 눈에 충돌(dirty)이 되며,
- auto-merge는 발동하지 못하고, 사람이/세션이 main을 병합해 다시 푸시해야 하고,
- 그 푸시가 CI(~30분)를 재기동하는 사이 main이 또 착지하면 — 처음으로 돌아간다.

main 착지 간격(이날 실측 30~90분)과 이 PR의 CI 소요(~30분)가 겹치는 한 **이 경합은 확률이
아니라 구조**다. union이 지켜 준 것은 "충돌을 로컬에서 자동 해소할 수 있다"까지고, "GitHub이
충돌로 보지 않는다"는 애초에 보장된 적이 없다 — 우리가 그렇게 믿고 있었을 뿐이다.

## 3. 근본 대책 (HARN-46 — 이 커밋에서 적용)

**원리: 충돌을 '해소 가능'하게 두지 않고 '발생 불가능'하게 만든다.**
`backlog/tasks/`가 태스크당 1파일로 병렬 충돌을 원천 차단한 것과 같은 원리를 이벤트 대장에
적용한다.

| 항목 | 변경 |
|---|---|
| 쓰기 | `store.append_event()`가 `backlog/events/<actor새니타이즈>.ndjson`(세션=브랜치당 1샤드)에 기록. **서로 다른 세션은 서로 다른 파일** → 같은 파일 동시 append가 사라짐 |
| 레거시 | `backlog/events.ndjson`은 읽기 전용 역사로 보존(신규 기록 없음·개작 없음) |
| 읽기 | `store.event_paths()`가 레거시+샤드 전부를 돌려주고, policy 리포트가 그것을 순회·ts 정렬(무손실) |
| 새니타이즈 | 파일명 안전 문자 외 `_` 치환 + 선두 `.` 제거 + 120자 상한 — 경로 탈출·하위 디렉터리 해석 불가 |
| .gitattributes | `backlog/events/*.ndjson merge=union` 병기 — 같은 actor 샤드가 재생성 브랜치에서 겹치는 잔여 경우의 **로컬** 방어(서버가 적용 안 한다는 사실은 불변임을 주석 명시) |

**테스트 동결** (`tests/harness/test_event_ledger_sharding.py`, acceptance와 1:1):
① 샤드 기록 ② 레거시 바이트 불변 ③ **서로 다른 actor → 서로소 파일**(충돌 불가 속성 자체)
④ 리포트가 레거시+샤드 합산 ⑤ 경로 안전·결정론 ⑥ .gitattributes 배선 실재.
뮤테이션 3종(쓰기를 레거시로 회귀·리포트를 레거시 단독 읽기로 회귀·gitattributes 줄 제거)
전부 red 실측 후 `cp` 백업 복원 — 변별력 확인.

## 4-c. `blocked`의 **두 번째 축** — behind (2026-09-03 추가 · HARN-56)

> **이 문서 초판은 `dirty`(파일 충돌) 축만 다뤘다.** 그 대책(HARN-46 events.ndjson 샤딩)은
> behind 축에 **작동하지 않는다**. 두 축은 증상이 똑같이 "머지 못 함"이라 혼동되며, 잘못된
> 축의 대책을 적용하면 시간만 쓰고 다시 막힌다. 다음 세션이 구분할 수 있도록 여기에 적는다.

### 두 축 구분표 — 먼저 이것부터 본다

| | **dirty 축** | **behind 축** |
|---|---|---|
| `mergeable_state` | `dirty` | `behind` |
| 무슨 일인가 | 내 브랜치와 base가 **같은 줄**을 고쳤다 | base가 **앞서 있다**(내용 충돌은 없음) |
| 원인 | 공용 append 파일 경합(events.ndjson 등) | `Require branches to be up to date` × 긴 CI |
| 해결 | 충돌 해소 후 재푸시 | base 병합 후 **CI 전체 재실행** |
| 반복되는 이유 | 같은 파일을 여러 세션이 동시에 만짐 | CI(약 20~30분) 도는 사이 main이 또 전진 |
| 대책 | HARN-46 샤딩 (착지) | **merge queue** (HARN-56) |
| 사람이 이길 수 있나 | 예 — 충돌은 유한하다 | **아니오** — 30분 게이트가 15~30분 간격 전진을 산술적으로 못 이긴다 |

**behind 축 실측**: PR #935가 재동기화 4회(2026-08-31). PR #952가 CI 16잡 green을 **3회**
확보하고도 3라운드 소요 — 2·3라운드는 전부 behind였고, CI가 도는 사이 #963·#964·#957이
차례로 착지했다. 이 세션의 PR #974도 같은 상태를 겪었다. 즉 산발적 불운이 아니라 **구조**다.

### behind 축을 만났을 때 (큐 도입 전 · 현행 절차)

base 병합 후 재푸시한다. `rebase`·`force-push`가 아니라 **병합**이다 — 남의 체크아웃을
깨지 않는다. 다만 이것은 해결이 아니라 **재시도**이며, 다시 질 수 있다.

### merge queue 도입 후 (HARN-56 ②③ 착지 시)

큐가 PR을 main 최신 위에 얹어 검증하고 통과분만 넣는다. `Require branches to be up to date`는
**유지**한다 — 보호를 낮추는 것이 아니라 충족 방식을 바꾸는 것이다(우회 아님).

**⚠ 순서 제약**: `ci.yml`의 `merge_group` 트리거가 main에 **먼저** 착지해야 한다. 트리거 없이
큐를 켜면 required check가 큐 안에서 한 번도 보고되지 않아 **모든 PR이 무한 대기**한다.
증상이 "실패"가 아니라 "대기"라 원인 규명이 늦다. 배선은
`tests/infra/test_merge_queue_wiring.py`가 동결한다(트리거 실재 + required 체크 전건이
`merge_group`에서 실제 실행되는지를 `if` 표현식 평가로 확인).

### 큐 실패 경로 — 축출(dequeue)되면 무엇이 남는가 (acceptance ④)

큐는 재검증 red·타임아웃·충돌 시 PR을 **축출**하고 다음으로 넘어간다. 축출이 조용하면 PR이
열린 채 방치된다.

> **정직한 미확인**: GitHub이 축출 시 PR에 어떤 흔적(코멘트·타임라인 이벤트·알림)을 남기는지
> **이 저장소에서 실측한 적이 없다.** 문서에서 읽은 동작을 실측인 것처럼 적지 않는다.
> 확인은 HARN-56 ③(큐 도입 후 주입 실험)에서 함께 한다.

그래서 세션 절차는 **그 알림에 의존하지 않도록** 설계한다 — 알림이 오든 안 오든 성립한다:

1. PR을 큐에 넣은 뒤 **끝난 것으로 치지 않는다.** 큐 대기는 CI 대기와 같은 급의 미완 상태다.
2. 다음 확인 시점에 PR 상태를 **직접 조회**한다. `merged`가 아니고 큐에도 없으면 **축출된
   것으로 간주**한다 — 축출 알림이 왔는지 여부로 판정하지 않는다(오지 않을 수 있다).
3. 축출로 판정되면 원인을 먼저 규명한다. **재투입은 원인 규명 뒤에만** 한다 — 같은 red로
   다시 축출되면 큐 처리량만 깎는다.
4. 재검증 red가 base의 최신 변경과 이 PR의 조합에서 났다면 그것은 **큐가 일한 것**이다.
   이 조합 검증이 실제로 결함을 잡은 사례가 이미 있다: #931이 `ReviewStatus`에 `quarantined`를
   추가하자 #935의 단언이 red — 동기화하지 않았으면 머지 후 main에서 터졌다. 이 실측이
   대안 2)(`up to date` 요구 해제)를 배제한 근거다.

## 5. 잔여 위험 (정직)

- **`MEMORY.md`가 같은 충돌 계급이다.** 모든 세션이 append하는 공용 union 파일이라는 조건이
  동일하다 — 이번 사고에서 events가 먼저 터졌을 뿐이다. 다만 MEMORY는 *사람이 읽는 서사
  정본*이라 샤딩하면 읽기 경험이 부서진다. 개편 여부(예: 결정로그의 월별 분권·머지 후
  통합 등)는 **Kiki 결정 대기**로 남긴다 — 이 태스크에서 손대지 않았다.
- **샤드 이름 붕괴 쌍**: `a/b`와 `a_b` 같은 두 브랜치는 같은 샤드로 접힌다. 그 한 쌍만
  종전(단일 파일) 상태로 퇴화하며 union 로컬 방어는 유지된다 — 발생 확률·피해 모두 종전보다
  작다.
- **이 문서·이 구현이 담긴 커밋 자체도** 머지 전까지는 종전 규칙의 적용을 받는다 — 샤딩
  효과는 main 착지 이후의 신규 이벤트부터다(레거시 파일의 기존 경합은 소급 제거되지 않고,
  각 열린 브랜치가 다음 main 병합 시 마지막으로 한 번씩 겪을 수 있다).

## 6. 이 사고가 남긴 일반 교훈 (CLAUDE.md 후보)

> **"로컬에서만 성립하는 방어를 서버 판정의 방어로 믿지 말 것"** — `.gitattributes`의
> merge driver·훅·로컬 설정은 **그 도구를 실행하는 쪽**에서만 작동한다. 서버(GitHub)가
> 같은 판정을 내린다는 보장은 별도로 실측해야 하며, "로컬 green"과 "서버 green"이 갈라지는
> 지점(mergeability·머지 실행·required check)은 각각이 독립 검증 대상이다.
> 본문 등재 여부는 Kiki 판단(규칙 신설은 헌법 개정이므로 여기서는 후보로만 남긴다).
