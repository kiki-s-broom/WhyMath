> **판정 기준**: main `30848ab4` (2026-10-09T04:34Z). 측정 수치는 모두 이 커밋 기준이다.
> **상태**: 판정 완료 · 구현(④)은 이 문서 뒤. Kiki가 2026-10-09 이 세션에서 아래 §5의 추천안을 승인했다.

## 0. 한 줄 결론

(가) **결정 로그를 항목당 파일 1개로 쪼갠다.** 기존 `MEMORY.md`는 이관하지 않고 동결하며, 인덱스는 커밋하지
않고 세션 시작 때 생성한다. (나) 머지 후 자동화와 (다) 자동 재동기화는 채택하지 않는다.

|---|---|---|

**파일 끝에** append"라고 하고, 실제 결정 로그 머리글은 "시간 역순"이라 관행은 **최상단 삽입**이다. 같은
저장소에 두 규약이 공존하는 것 자체가 위치 규약의 한계를 보여 준다.

## 2. 왜 기존 방어가 못 막는가

- `.gitattributes`의 `MEMORY.md merge=union`은 **로컬 git에서만** 작동한다. GitHub의 병합 가능 판정과 머지
  큐는 저장소의 merge 드라이버를 적용하지 않는다(`.gitattributes` 주석과 HARN-211 실측).
- 같은 세 파일(공통 조상·내 것·main)에 대해 `git merge-tree`(ort)는 충돌 0건, `git merge-file`(xdiff)은
  충돌 1건으로 갈린다(PR 1533 세션의 즉석 실측). 로컬 `git merge`가 늘 깨끗한 이유가 ort다. GitHub가 어느
  병합기를 쓰는지는 **직접 확인하지 못했다** — merge-file 쪽 결과와 관측(dirty 패턴)이 일치한다는 추정이다.
- dirty PR에는 `pull_request` 워크플로가 시작되지 않아 체크가 0건이다(충돌을 푼 뒤에야 CI가 돈다).

## 3. 선택지 비교

| | (가) 항목당 파일 | (나) 머지 후 자동화가 기록 | (다) 현상 유지 + 자동 재동기화 |
|---|---|---|---|
| 충돌 제거 | 구조적으로 제거 — 서로 다른 세션이 서로 다른 파일에 쓴다 | 제거되나 새 쓰기 경로가 생긴다 | 못 제거 |
| 머지 큐 경로 | 풀린다(추정 — ④에서 실증) | 봇의 기록 PR도 같은 큐에 줄을 서고, 봇이 만든 push는 워크플로를 재발화시키지 않는 제약(HARN-85)을 만난다 | **못 푼다** — 큐는 서버 병합이고, 아직 착지하지 않은 PR끼리의 동시 삽입은 미리 병합해 둔다고 사라지지 않는다 |
| 선례 | 있음 — 이벤트 대장 `backlog/events/<actor>.ndjson`(HARN-46)·사고 대장 | 없음 | HARN-85(BEHIND만 처리, 충돌 409는 사람 몫) |
| 구현 비용 | 중 — 가드·인덱스 생성·안내문 정정 | 대 — 봇 권한·브랜치 보호·실패 처리 | 소 — 그러나 효과가 없다 |
| 규범 변경 | 필요(§4) | 필요 | 불필요 |
| 실패 모드 | 읽는 쪽이 최근 결정을 못 찾음(→ 인덱스로 완화) | 봇 중단 시 결정이 기록되지 않음 | 계속 사람이 위치를 옮김 |

위치 규약을 고치는 안((라): "N번째 자리에 넣어라")은 표에서 뺐다. 모든 세션이 같은 규약을 따르면 그 자리가
새 충돌 지점이 된다 — PR 1533이 최상단에서 3번째 자리로 옮겨 충돌 1→0이 됐지만 그것은 *다른 PR이 그 자리를
쓰지 않았을 때*의 일시적 해소다.

## 5. 판정 — (가) 채택, 세 조건 (Kiki 승인)

1. **기존 `MEMORY.md`는 이관하지 않고 동결한다 (ⓒ).** 726개 항목을 옮기면 299개 파일의 인용이 가리키는
   앵커가 모두 깨진다. 동결은 추가·수정·삭제를 모두 막는 가드로 집행한다(§6 ④-1).
2. **새 결정은 항목당 파일 1개** — `docs/decision_log/<YYYY-MM>/<YYYY-MM-DD>_<태스크ID 또는 PR>.md`. 첫 줄은
   기존과 같은 `### 날짜 (분류 · 식별자): 제목` 형식으로 두어 변환·검색을 쉽게 한다. 월별 하위 디렉터리로
   목록 가독성을 지킨다(하루 18건 안팎 기준 연 6,000개 안팎). 같은 태스크가 같은 날 같은 파일명을 두 PR에서
   만들면 충돌이 나는데, 이는 **같은 결정의 이중 기록**이라는 신호이므로 의도된 동작이다.
3. **인덱스는 커밋하지 않는다.** 인덱스를 커밋하면 그 파일이 다시 공유 파일이 되어 같은 충돌이 되살아난다.
   `backlog.py brief`(SessionStart 훅이 이미 호출)가 조각 디렉터리에서 "최근 결정 N건"을 읽어 출력한다.

## 6. ④ 구현 범위 (이 문서가 정하는 인수 조건)

- **④-1 동결 가드**: base 대비 `MEMORY.md`가 바뀌면 CI 실패. 대조군 = `MEMORY.md`를 건드리지 않는 PR은 통과.
  **전환기 유예는 만료를 둔다** — 전환 시점에 이미 열려 있는 PR은 `MEMORY.md`를 고쳤을 수 있으므로 한시 면제하되,
  만료 날짜(또는 면제 대상 PR 목록이 비는 시점)를 코드에 박는다(CLAUDE.md "만료 없는 유예 금지").
- **④-2 조각 규약**: 디렉터리·파일명 규칙·첫 줄 형식을 `docs/standards/`에 한 쪽으로 정본화하고, 형식 검사기를
  CI에 건다(이름 충돌·월 디렉터리 이탈·첫 줄 형식).
- **④-3 인덱스 생성**: `backlog.py brief`에 "최근 결정 N건" 출력 추가. 생성물은 커밋하지 않는다(커밋 시 가드 RED).
- **④-4 안내문 정정**: `CLAUDE.md` 4곳(97·321·383·422행) · `parallel_sessions.md` 3곳(41·143·186행, 끝 append
  규약 폐기) · `.claude/agents` 7 · `.claude/commands` 8 · `.gitattributes`의 `MEMORY.md merge=union` 주석.
- **④-5 실증 (HARN-210 ④)**: 임시 저장소에 두 브랜치가 같은 창에서 서로 다른 조각을 더해도 서버 방식 병합
  (`merge=` 선언을 지운 3-way, HARN-211 프로브 방식)이 충돌하지 않음을 재현한다(수정 전 RED → 후 GREEN, 뮤테이션으로
  각 절 확인). **머지 큐에서 실제로 풀리는지는 실 PR 쌍으로 관측하고, 못 했으면 "미확인"으로 적는다.**
- **④-6 지표 (7일 관측)**: ⓐ 사고 대장의 `memory-md-append-github-dirty` 계열 신규 줄 수 = 0 ⓑ 머지 큐
  MERGE_CONFLICT 이탈 중 `MEMORY.md` 기인 = 0건 ⓒ 조각 신규 파일이 하루 10~20건 수준으로 쌓이는지(안 쌓이면
  결정이 어디에도 기록되지 않는 것) ⓓ 동결 가드 RED 횟수(우회 시도 신호).

## 7. 정직한 공백

- **서버 병합기의 정체는 미확인**이다(§2). (가)의 효과 주장은 "서로 다른 파일의 추가는 어떤 병합기에서도 충돌하지
  않는다"는 일반 동작에 기댄 추정이며 ④-5가 실증한다.
- 7일 빈도는 shallow 클론(3.2일·80커밋) 한계로 직접 재지 못했다. 24시간 수치(33건 중 18건)가 더 믿을 만하다.
- 소비처 조사는 `git grep` 패턴 기준이다. 안내문 15개의 문구가 실제 세션 행동에 얼마나 영향을 주는지는 측정하지
  않았다 — 정정 후 한 주 동안 `MEMORY.md` 수정 시도가 가드에 걸리는 횟수(④-6 ⓓ)로 간접 관측한다.
- 이 PR은 `MEMORY.md`에 결정 로그 항목을 더하지 않았다. 바로 이 문제 때문이고, 이 결정의 기록은 이 판정문과
  HARN-210 대장 정정이 맡으며, ④가 착지하면 첫 조각으로 옮겨 적는다.
- 전환 직후 에이전트가 습관대로 `MEMORY.md`를 읽어 최근 결정을 못 보는 구간이 생긴다. 완화는 ④-3의 브리핑이고,
  그 효과는 측정하지 않았다.

## 8. 되돌리기

조각 파일은 그대로 두고 동결 가드를 해제하면 `MEMORY.md` 병합이 재개된다. 조각에 쓴 결정은 데이터로 남는다(손실
없음). 되돌릴 때 필요한 것은 가드 한 곳과 안내문 정정의 역방향뿐이다.
