## §0. 결론

**R6를 집행한다 — 첫 R6는 오답 개념이 막혔을 때만 선수 쪽으로 간다. 측정된 선수 약점이 있으면 그 약점을 연습하고, 없으면 미측정 직접 선수 1문항을 탐침한다. 연속 두 번째 R6는 상태 머신 문면(같은 개념 연습)대로 간다.**

- **첫 R6 · 오답 개념 C가 막힘(사후 숙달 < 0.4)**: C의 직접 선수를 측정 상태 셋으로 나눈다 — 미측정 · 약점(< 0.7) · 숙달(≥ 0.7).
  - 측정된 약점이 하나라도 있으면 **탐침하지 않는다.** 잴 것이 이미 재어져 있다. 후보를 C로 제한하고, 기본 경로의 이름표 연산(EOS-124 (가))이 가장 약한 선수로 다시 골라 `practice_prerequisite`를 낸다(`known_prerequisite_deficit`).
  - 약점이 없고 미측정 선수가 있으면 후보를 **그 미측정 선수들의 문항으로 제한**한다 — 선수 탐침(`prerequisite_probe`). Kiki 기준 ⓐ가 여기서 구조적으로 선다.
- **첫 R6 · C가 막히지 않음(≥ 0.4)**: 1회 실수를 선수 결손으로 읽지 않는다. 같은 개념 C를 연습한다(`same_concept_not_blocked`). 숙달 0.80 이상이던 학생은 오답 1회로 0.4 아래로 떨어지지 않는다(BKT 기본값 · 2자리 저장 — §5 발견 2).
- **연속 두 번째 R6(직전 정책 결정이 R3 또는 R6)**: 방금 틀린 개념 X로 제한한다. R6 결정(`PRACTICE_SAME_CONCEPT`) 문면 그대로다. 탐침을 틀린 경우 X는 선수 P다. 첫 R6의 막힘 게이트가 C < 0.4를 보장하므로 EOS-124 (나)가 `practice_prerequisite`(목표 P)를 붙인다. Kiki 기준 ⓑ가 여기서 구조적으로 선다.
- **연습 경로는 학습 밴드로 고른다.** 요청 목적과 무관하며 EOS-24 교정 경로와 같은 규칙이다. 탐침만 측정 자체라 요청 목적 그대로다.
- **셋째 연속 오답은 R5**(임계 3)라 이 경로를 타지 않는다. R6 개입은 최대 2문항이다. 다만 이것은 안전장치가 아니라 **개선 범위의 끝**이다 — 셋째부터는 이 태스크가 고치려던 기본 경로로 인계된다(`EOS-148`이 재판정).
- 탐침할 선수가 없거나(엣지 없음 · 전부 숙달 · 문항 없음 · 시간 초과) C의 숙달 측정이 없으면 같은 개념 연습이다 — R6 문면. 같은 개념에도 문항이 없을 때만 기본 경로다.
- **R2(정답+미측정 확신)는 집행하지 않는다**(ⓓ).
- **해소는 API 계약 수준이다. 실제 모바일 앱은 R6에 도달하지 않는다**(§1-6 · `EOS-146`). 앱은 오답을 제출하지 않고 코치 정답 완료만 기록하며, 그 기록은 상태 머신을 돌리지 않는다. 3루프 하네스 동결 승격은 HTTP 계약(`POST /v1/me/attempts` → `GET /v1/me/next-problem`)에서의 해소이고, 앱 학생에게 일어나는 개선이 아니다.
- **해소 범위는 활성 오개념 가설이 0인 학생의 R6다**(§3 ⓔ · `EOS-138`). 활성 가설이 하나라도 있으면 원인 미상 오답도 R3로 분류된다.
- 이 판정은 **ⓐ만이 아니라 ⓑ도 새로 세운다.** §1-2의 실측이 ⓑ 역시 픽스처·요청 형태에 기대고 있었음을 보였다.

## §1. 실측 사실 (acceptance ①)

> 실행 환경: 컨테이너 · PostgreSQL 16.13 + pgvector · `alembic upgrade head` EXIT=0 · Python 3.12 venv(`pip install -e ".[dev]"` EXIT=0)

### 1-1. 기준선 — 태스크 문면 재현

main `bd87b30d` 그대로 `test_e2e_three_consecutive_loops.py` + `test_eos24_recommendation_follows_learning_state.py`를 실 PG로 돌렸다 — **41 passed · 1 xfailed · EXIT=0**. 프로브 판정은 태스크 문면과 같다.

> 「실측」 `DIAGNOSIS_PROBE :: 폐루프=PASS 선수지향=FAIL` · 선수 지향 프로브의 첫 추천 = `문항소속=side · action=diagnose · reason=unmeasured · target=side` · `THREE_LOOP_VERDICT[general] :: LOOP1=FAIL LOOP2=PASS LOOP3=PASS`

원인도 문면과 같다: 기본 경로의 1차 선택(`l2/next_problem_selection.py::candidate_pool_order_by` θ 근방 정렬 + 정보량 최대)은 선수 그래프를 보지 않는다. 오답 1회 뒤 θ는 하한 -4.0이고, 가장 쉬운 문항이 선수가 아닌 개념에 있으면 진단은 그쪽으로 간다.

### 1-2. 새 사실 — 기준 ⓑ도 구조적이지 않았다

EOS-139가 잰 폐루프(ⓑ)는 방해 개념 **없는** 배치에서, 하네스 기본 요청(`prioritize_weak_concepts=true`)으로만 쟀다. 스크래치 프로브(커밋하지 않음)로 방해 개념 배치에서 학습자가 **선수 문항을 틀린** 뒤의 추천을 두 요청 형태로 쟀다.

| 요청 형태 | 선수 문항 오답 뒤 추천 | ⓑ |
|---|---|---|
| `prioritize_weak_concepts=true` (3루프 하네스 기본값) | `pre · practice_prerequisite · served` | 성립 |
| 파라미터 미전송 (모바일 앱의 요청 형태) | `side · diagnose · direct` | **붕괴** |

첫 줄이 성립한 이유는 약점 가중이다 — 방금 틀린 선수(숙달 0.15)의 문항이 가중 1.85배를 받아 방해 개념(가중 1.0)의 정보량 우위를 이겼다. 둘째 줄은 가중이 없어 다시 가장 쉬운 문항(방해 개념)으로 간다.

**요청 형태로는 실제 앱이 둘째 줄이다.** `src/mobile/lib/features/problems/data/problems_api.dart::getNextProblem`의 `prioritizeWeakConcepts` 기본값이 `false`이고, 유일한 호출부 `problem_screen.dart`는 `load()`를 인자 없이 부른다(이 검색 방법 기준). 즉 EOS-139의 "폐루프 True"는 **방해 개념 부재 + 하네스 전용 요청 형태**라는 두 우연 위에 서 있었다. 사고 대장 `nondiscriminating-check` 계열의 재발이다(§7-3). 이 태스크가 ⓐ만 고치고 프로브의 ⓖ만 True로 올렸다면 `general` Loop 1 `보정`은 거짓 해소가 됐을 것이다. (단 **이벤트 원천** 축에서는 두 줄 모두 하네스 전용이다 — 앱은 이 경로에 도달하지 않는다. §1-6.)

### 1-3. 태스크 notes의 부수 관측은 현재 main에서 재현되지 않는다

notes는 "무관 개념 진단 문항까지 틀리면 `practice_prerequisite · prerequisite_gap · target=무관 개념`"을 적었다(main `81070ed5` 시점). 지금은 다르다.

> 「실측」 방해 개념 진단을 그대로 따라 틀린 뒤의 추천 = `side · practice_current · current_concept · intent unsupported` (두 요청 형태 동일)

EOS-124(#1317 · `cat_v2`)가 착지하며 선수 구간 의도가 그래프 근거를 요구하게 됐기 때문이다 — 무관 개념은 선수·후행 엣지가 없어 (다) 정직 강등으로 내려간다. 그래서 이 경로에서 "이름표가 거짓말을 하는" 경우는 지금 없다. `practice_prerequisite`는 EOS-124 (가)·(나)의 그래프 근거가 있을 때만 나온다.

### 1-4. 연속 판정은 국면으로 할 수 없다 — EOS-24 안전장치 ③ 모양이 옮겨 오지 않는다

EOS-24는 교정 고정을 "교정 국면(`REMEDIATING`)에서 제출한 응답이 다시 R3면 해제"로 풀었다(`LearningStateSnapshot.assessed_from`). R6에 같은 모양을 쓰면 "`PRACTICING`에서 제출한 R6"가 되는데, `PRACTICING`은 **R2의 도착 국면이기도 하다**. 그리고 확신도를 보내지 않는 클라이언트의 정답은 전부 R2다(`_is_high_confidence` · 미측정 = 낮음 — 모바일 앱의 `src/mobile/lib/features/problems/data/*.dart`에서 `confidence` 0건). 그러면 **정답 뒤의 모든 오답이 "연속 R6"로 읽혀** 첫 R6 탐침이 사실상 첫 응답에서만 돈다. 연속 판정은 국면이 아니라 **직전 정책 결정의 트리거**로 해야 한다.

### 1-5. `consecutive_failures`는 개념을 가리지 않는다

`V1_RULES` R5 설명은 "같은 개념에서 연속 오답"이라고 적지만 `l2/learning_state_evidence.py::_count_consecutive_failures`는 학생의 최근 응답을 개념과 무관하게 센다. 그래서 C 오답 → 선수 P 오답 → 셋째 오답이면 셋째에서 R5가 발화한다. §0의 "R6 개입은 최대 2문항"은 이 사실에 선다. 설명 문구와 구현의 불일치 자체는 이 태스크 범위 밖이다(`EOS-145`).

### 1-6. 실제 앱은 R6를 만들지 않는다 — 이 해소는 API 계약 수준이다 (독립 비판 발견 1 · 코드 대조)

§1-2의 "실제 앱"은 요청 형태 축에서만 맞다. 이벤트 원천 축에서 보면 두 줄 모두 하네스 전용이다.

- 모바일 앱은 `POST /v1/me/attempts`를 부르지 않는다. `src/mobile/test/e2e_loop_flow_test.dart`가 `callCount('/v1/me/attempts') == 0`을 두 곳(422·478행)에서 동결한다(`MOB-20` "배선 아님 — 계약상 금지").
- 앱 학생의 시도 기록은 코치 정답 완료뿐이다. `api/coach.py::_complete_problem`이 `ProblemAttempt(is_correct=True)`를 적재하고 숙달을 전파하지만 상태 머신(`advance_on_attempt`)은 부르지 않는다. `advance_on_attempt`의 호출부는 `api/me.py`의 시도 제출 1곳뿐이다(이 검색 방법 기준). 앱의 오답·포기는 어디에도 적재되지 않는다.
- 그래서 앱 학생의 원장은 전이 0건이고 스냅샷은 NEW다. R6 판독은 None이고 이 경로는 0회 돈다. EOS-24의 R3 집행도 같다.
- `EOS-134`(todo)는 코치 **정답** 완료만 상태 머신에 태운다. 착지해도 R6 원천(오답)은 생기지 않는다.

그러므로 3루프 동결 승격(§6)은 **API 계약 수준 해소 · 앱 도달 0**으로 읽어야 한다. 운영의 `learning_state_directive` R6 값은 앱 오답 원천이 생기기 전까지 0건이다 — 그것을 "학생들이 원인 미상 오답을 하지 않았다"로 읽으면 안 된다. 원천 부재는 `EOS-146`으로 등재했다(EOS-134와 별건). 승격 자체를 앱 원천이 생길 때까지 보류할지는 게이트 소유자(Kiki) 판단 사항이다. 이 태스크는 acceptance ⑤대로 승격하되, 해소 수준을 동결 테스트 문면·이 문서·PR 본문에 명기한다. 이 전제 오류는 판정문 초안에 있었고 머지 전 독립 비판이 잡았다 — 사고 대장에 같은 계열의 한 층 아래 재발로 기록했다(§7-3).

### 1-7. 범위 밖 부수 관측 — 정답만 있는 이력의 θ는 상한 4.0에 고정된다

θ 추정(`l2/irt.py::estimate_ability`)은 전부 정답이면 MLE 발산을 상한 4.0으로 돌려준다. 컨테이너 실측에서 첫 응답이 정답뿐인 학습자의 다음 추천은 `theta=4.0` · 난이도 4.8(재현 픽스처에서 가장 어려운 문항)이었다. 앱 학생은 시도 기록이 코치 정답 완료뿐이라(§1-6) 이 상태가 영구적이다(코드 경로 · 앱 실측 아님). 이 태스크 범위 밖이며 `EOS-147`로 등재했다(독립 비판의 범위 밖 부수 관측).

| — | 같은 개념 제한인데 그 개념에 미시도 문항 없음 | (제한 없음) | `no_candidate_in_concept` | 요청 목적 | 기본 경로 |

### 2-2. 채택 근거

1. **R6의 결정은 "같은 개념 연습"이고, Kiki가 인정한 것은 그 앞의 선수 확인 한 걸음이다.** EOS-24 판정의 원칙은 "추천은 상태 머신을 다시 판정하지 않고 집행한다"였다. 그러니 R6를 집행한다는 것은 기본적으로 같은 개념 연습이다. Kiki 결정 (가)는 그 앞에 한 걸음을 인정했다 — 원인을 모르는 오답이면 가장 가까운 구조적 원인(선수 결손)을 먼저 확인한다. 이 판정은 그 한 걸음을 **연속 오답의 첫 R6 · 오답 개념이 막혔을 때**에만 둔다. 막히지 않은 개념의 1회 실수는 선수 결손의 증거가 아니다. 경계는 계획서 §8 선수 구간 경계 0.4(`PREREQUISITE_MASTERY_CEILING`)를 그대로 쓴다 — 새 숫자는 없다. 입력은 최신 숙달 이력이라, 아래 기본 경로 이름표(EOS-124)가 앵커 구간을 판정하는 값과 같다(두 판정이 갈라지지 않는다).
2. **진단은 모르는 것을 잰다.** 측정된 약점은 다시 잴 것이 없으니 연습으로 잇고(아는 결손 우선), 미측정 선수만 탐침한다. 약점 경계는 EOS-124 (가)와 같은 입력(`learner_state.mastery`)·같은 선(< 0.7)이다 — 선이 다르면 "아는 결손이 있다"고 넘겼는데 (가)가 그 선수를 찾지 못하는 틈이 생긴다. 부수 효과: **탐침은 선수마다 최대 1회다.** 탐침에 한 번 응답하면 그 선수는 측정되어(정답 뒤 0.69 · 오답 뒤 0.15) 탐침 대상에서 빠진다 — C 단위 탐침 예산이 별도 카운터 없이 선다(§5 발견 3).
3. **ⓑ를 문면 집행이 세운다.** 탐침을 틀리면 학생은 두 번째 R6에 있고, 방금 틀린 개념은 선수 P다. R6 문면대로 P로 제한하면, P가 막힌 C의 직접 선수라는 사실을 EOS-124 (나)가 알아본다 — `practice_prerequisite`(목표 = P). 새 규칙 없이 기존 두 좌석(상태 머신 문면 · EOS-124 의도 해소)의 합성으로 ⓑ가 선다. §1-2의 붕괴는 1차 선택이 P를 앵커로 잡지 못해서 생겼으므로, 앵커를 P로 고정하면 방해 개념·요청 형태와 무관해진다. (나)의 전제("막힌 후행이 있다")는 첫 R6의 막힘 게이트가 보장한다 — 오답은 문항의 대표 개념만 갱신하므로 P 오답이 C 값을 바꾸지 않는다. 단 (나)의 근거 개념은 "P의 측정된 막힌 후행 중 가장 약한 것"이라 **C가 아닐 수 있다**(동률이면 UUID 순) — 이 판정은 근거 개념이 C임을 보장하지 않는다(§5 발견 2C · 서술 정정).
4. **새 근거 종류(ReasonType)를 만들지 않는다 — 후보 제한만 한다.** EOS-24는 `misconception_remediation`을 신설했다. 숙달 파생 근거가 전달 문항에 대해 **거짓**이 되기 때문이었다(C의 숙달 구간은 선수 하강을 말하는데 전달 문항은 C의 교정 확인이다). R6 경로에서는 전달 문항의 숙달 파생 이름표가 **참**이다 — 미측정 P를 진단하러 P 문항을 내면 `diagnose · unmeasured`가 사실이고, 막힌 C의 선수 P를 연습시키면 `practice_prerequisite`가 사실이다. 상태 머신이 한 일은 *후보 생성*이며, 그것은 `learning_state_directive`와 `policy_version`이 기록한다(EOS-124가 재선택을 `reason.type`이 아니라 `intent_resolution`에 기록한 것과 같은 자리 배분). 규칙으로 적는다: **상태 머신 근거 종류는 숙달 파생 근거가 전달 문항에 대해 거짓이 될 때만 신설한다.** 부수 효과로 행위 어휘가 그대로라 Kiki 결정 문면("`diagnose`를 보정으로 인정")과 3루프 하네스의 판정(`action == "diagnose"`)이 바뀌지 않는다.
5. **판정 위치는 `route_by_learning_state` 하나다**(acceptance ④). EOS-24 R3 집행과 같은 이음매에서 지시를 읽고 후보를 제한한다. 정책(`CatRecommendationPolicy`)은 제한된 후보로 같은 선택을 하고, 경로에 맞는 밴드를 고를 뿐이다.

### 2-3. 이 판정이 남기는 비대칭(정직 표기)

상태 머신의 R6 `next_action`은 언제나 `PRACTICE_SAME_CONCEPT`(오답 개념 C)다. 추천은 다음 세 경우에 다른 말을 한다.

- **첫 R6 탐침**: 추천은 `diagnose` P다.
- **아는 결손**: 후보는 C로 제한되지만 EOS-124 (가)가 약한 선수 P로 다시 골라 `practice_prerequisite` P가 나간다.
- **탐침을 맞힌 분기**: 최신 결정이 R2(정답)라 지시가 아니고(ⓓ), 기본 경로는 개념을 보지 않아 **C로 돌아가지 않는다.** R6가 C에 대해 말한 "C 연습"이 이 분기에서는 끝내 나가지 않는다(§5 발견 5).

게이트 `G-eos24-loop1-undiagnosed-wrong-criterion`의 evidence가 적은 "남는 부채"(API 수준에서 둘이 다른 말을 한다)는 이 판정으로 **줄어들 뿐 사라지지 않는다** — 연속 두 번째와 같은 개념 폴백에서는 둘이 같은 말을 한다. 결정자가 둘인 상태(EOS-24 판정문 §2 근거 1이 경계한 형태)가 위 세 경우에 남는다. 탐침 규칙을 상태 머신(`V1_RULES`)으로 올릴지, 탐침 정답 뒤 C로 한 번 복귀시킬지는 `EOS-144`가 판정한다(④에 탐침 정답 분기를 병기). 그 부채는 게이트 evidence가 "후속 태스크로 등재한다"고 적었으나 대장에 없었다(`grep PRACTICE_SAME_CONCEPT backlog/tasks` → EOS-139 1건 · 이 검색 방법 기준).

## §3. 설계 판정 ⓐ~ⓖ (acceptance ③)

### ⓐ 폴백 — 선수가 없거나 선수에 미시도 문항이 없을 때

**같은 개념 연습(R6 문면)으로 간다. 기본 경로로 가지 않는다.** 기본 경로는 θ 근방 최근접이라 오답 직후 무관한 가장 쉬운 문항으로 간다 — 그것이 바로 이 태스크가 고치는 결함이다. 탐침할 선수가 없다는 것은 원인 후보가 C 안에 있다는 뜻이거나(선수가 전부 숙달 — 반증), 우리 쪽 공백이다(엣지 없음 · 문항 없음 · 시간 초과 · 숙달 전파 공백). 어느 쪽이든 C를 이어 연습하는 것이 상태 머신이 말한 그대로다.

사유를 나누는 이유는 EOS-124 `IntentResolution`과 같다(모른다 ≠ 아니다) — 고칠 곳이 다르다.

| 지시값 | 뜻 | 고칠 곳 |
|---|---|---|
| `same_concept_not_blocked` | C가 막히지 않았다 — 정상 교수학 | (없음) |
| `same_concept_probe_refuted` | 직접 선수가 전부 측정 숙달 — 반증 | (없음) |
| `same_concept_probe_unsupported` | C에 선수 엣지가 없다 | 그래프 커버리지 |
| `same_concept_probe_unavailable` | 미측정 선수에 출제 가능 문항이 없다 | 콘텐츠 |
| `same_concept_graph_timeout` | 선수 조회가 시간 예산을 넘었다(예외 타입명 로그) | 성능 |
| `same_concept_anchor_unmeasured` | 오답 직후인데 C의 숙달 이력이 없다(경고 로그) | 숙달 전파 |

`known_prerequisite_deficit`은 폴백이 아니라 의도된 경로다(ⓑ). 같은 개념에도 미시도 문항이 없을 때만 기본 경로로 돌아가고 `no_candidate_in_concept`을 남긴다(EOS-24와 같은 값 재사용 — 뜻이 같다).

**이름표**: 폴백의 이름표는 EOS-124 의도 해소가 붙인다. 막힌 C가 앵커면 `_prerequisite_intent`가 돈다 — (가) C의 측정된 약한 선수(깊이 2까지)가 있으면 거기로 재선택, (나) C가 막힌 후행의 직접 선수면 근거를 그 후행으로, (다) 아니면 `practice_current`로 정직 강등. §1-3의 실측대로 무관 개념에 `practice_prerequisite`가 붙는 일은 없다. (가)가 깊이 2의 약한 선수로 재선택하면 전달 문항은 C 제한을 벗어난다 — 그 경우는 처치 기록에서 지시값과 `intent_resolution=served`의 조합으로 식별된다(§5 발견 7 · 지시값을 따로 두지 않는다).

### ⓑ 선수가 여럿일 때 — 직접 선수 · 측정 상태 셋 · 아는 결손 우선 · 미측정만 탐침

- **직접 선수(depth 1)만 본다.** 이유 셋: ① 원인 후보로 가장 가까운 것은 직접 선수다. ② `fetch_prerequisites`의 depth 2 행은 **경로를 싣지 않는다** — 숙달된 직접 선수 뒤에 있는 depth 2 선수(그 직접 선수가 이미 덮는 기초)와 약한 직접 선수 뒤에 있는 것을 구별할 수 없다. 구별 못 하는 것을 **탐침(측정)** 대상에 넣으면 숙달된 기초를 진단하는 문항이 나간다. ③ 더 깊은 하강은 측정이 이끈다 — 탐침을 틀리면 두 번째 R6에서 P가 앵커가 되고, P의 측정된 약한 선수가 있으면 EOS-124 (가)가 거기로 내려간다. (②는 *모르는 것을 잴 때*의 논거다. 측정된 약점으로 연습을 고르는 (가) 재선택은 depth 2 행도 측정값이라 경로 정보 없이 사실이다 — 그래서 (가)는 깊이 2까지 그대로 둔다.)
- **측정 상태를 셋으로 나눈다** — 미측정(코드 없음 포함) · 약점(< 0.7) · 숙달(≥ 0.7). 입력은 `learner_state.mastery`(개념코드 키)이고 EOS-124 (가)와 같은 입력·같은 경계(`WEAK_CONCEPT_MASTERY_CEILING`)다. 모른다 ≠ 숙달 · 모른다 ≠ 약점.
- **아는 결손이 먼저다.** 약점이 하나라도 있으면 탐침하지 않고 C로 제한해 (가)가 **가장 약한 선수부터** 잇게 한다(`known_prerequisite_deficit`). 측정된 결손(예: 0.35)을 두고 미측정 선수를 진단하러 가면, 그 진단이 맞았을 때 아는 결손은 이번 에피소드에서 다뤄지지 않는다(§5 발견 8).
- **약점이 없으면 미측정 선수만 탐침한다.** 숙달 선수는 원인 후보가 아니고, 약점 선수는 위에서 이미 걸렀다. 미측정 선수들 안의 선택은 기본 CAT 선택 연산(정보량 × 요청의 가중 축)에 맡긴다 — "선택 연산은 1차 선택과 같다"(EOS-124 재선택 원칙).
- 합친 후보는 기본 후보 풀과 같은 키(|b−θ| 오름차순 → `problem_id`)로 정렬하고 같은 크기로 자른다. 선택기(`select_weighted_item`)가 동률에서 낮은 인덱스를 고르므로, 같은 키여야 동률 처리가 기본 경로와 같아진다. 한 문항이 두 선수의 대표 문항으로 두 번 오면 한 번만 센다.

### ⓒ 고정 범위 — 탐침은 선수마다 1회 · 연속 오답 구간마다 1회 · 셋째는 R5로 인계

- **탐침은 연속 오답의 첫 R6에서만 나간다.** 연속 두 번째는 문면 연습이다.
- **같은 선수는 두 번 탐침되지 않는다.** 탐침에 응답하면 그 선수는 측정되어 미측정 목록에서 빠진다(§2-2 근거 2). 정답이면 0.69(약점 경계 아래)라, 다음에 C를 또 막힌 채 틀리면 그 선수는 아는 결손으로 **연습** 대상이 된다 — 진단 반복은 사라지고, 연습 반복은 EOS-124 (가) 규칙대로 남는다(정답 2회면 0.92로 숙달 · 빠진다).
- **연속 판정 = 직전 정책 결정의 트리거가 R3 또는 R6인가.** §1-4대로 국면(`assessed_from`)으로는 R2와 R6를 가를 수 없다. 원장에서 "결정 응답이 아닌 응답의 가장 늦은 정책 결정"의 트리거를 1건 읽는다(R6 경로에서만 · 조회 1건). **R3를 포함하는 이유**: R3(오개념 오답) 직후의 R6는 연속 두 번째 오답이다. 여기서 탐침하면 그 탐침을 틀리는 순간 셋째 오답(R5)이라, 탐침 결과를 쓸 하강이 구조적으로 없다(§5 발견 4B). 서빙 경로에서 연속 두 번째 오답의 직전 결정은 R3·R6뿐이다(R4 미배선 · R5는 셋째 이상에서만 발화).
- **셋째 연속 오답은 R5**(`REPEATED_FAILURE_THRESHOLD = 3`)라 R6가 아니다. R5는 집행하지 않으므로(EOS-24 판정문 §3) 추천은 기본 경로로 돌아간다 — 실제 앱 요청 형태에서 θ가 하한이면 가장 쉬운 무관 문항이다. **이것은 안전장치가 아니라 이 태스크 개선 범위의 끝이다.** EOS-24가 R5를 집행하지 않은 근거("θ가 내려가면 선수 문항이 나온다")가 §1-1에서 픽스처 의존으로 판명됐으므로 그 근거를 `EOS-148`이 재판정한다.
- **"연속"은 상태 머신의 정의를 따른다**(시간 창 없음). 어제 R6로 끝나고 오늘 첫 응답이 R6면 두 번째로 읽힌다. `consecutive_failures`도 시간 필터가 없다(§1-5). 시간 창은 상태 머신 소유 판정이라 `EOS-145`(연속 오답 범위 의도 판정)에 병기했다.
- **EOS-134 착지 전 한계**: 코치 정답 완료는 시도 기록은 남기지만 원장 결정은 남기지 않는다. 그래서 코치로 한 문항을 맞힌 뒤 다시 틀리면, 시도 기준 연속 오답은 1인데 원장 기준 직전 결정은 여전히 R6라 "연속 두 번째"로 읽힌다. 두 연속이 갈리는 것은 앱 코치 경로가 섞일 때만이고, 앱은 지금 R6에 도달하지 않는다(§1-6).

### ⓓ R2는 집행하지 않는다

판독 함수는 `state is PRACTICING` **이고** `trigger is POLICY_PRACTICE_UNDIAGNOSED`일 때만 지시를 낸다. 국면만 보면 R2의 PRACTICING을 오독하고(확신도 미보고 학생의 모든 정답이 지시가 된다 — EOS-24 판정문 §3), 트리거만 보면 R6 뒤에 생애주기 전이가 끼어도 지시가 살아 있는 것처럼 읽힌다(EOS-24 `read_remediation_directive`와 같은 이유). R2면 지시가 아니므로 조회 0건이다. 그 결과가 §2-3의 "탐침 정답 분기는 C로 돌아가지 않는다"다.

### ⓔ R3 경로(EOS-24)와의 합성

- **요청마다 지시는 하나다.** 판독은 원장 최신 결정 하나를 본다 — R3면 `REMEDIATING`, R6면 `PRACTICING`이라 동시에 성립하지 않는다. R3를 먼저 읽는다(기존 순서 유지).
- **R3 → R6**(오개념 오답 뒤 원인 미상 오답): 연속 두 번째로 판정한다 — 방금 틀린 개념을 연습한다(ⓒ). 초안은 "교정이 원인을 못 짚었으니 선수 확인"으로 탐침했으나, 그 탐침은 결과를 쓸 수 없다(셋째가 R5). HTTP로는 곧바로 만들 수 없는 합성이다 — R3는 학생 전체의 활성 가설을 읽어, 교정 문항을 매칭 없이 틀려도 가설이 살아 있는 한 R3가 다시 발화한다(`EOS-138`). 그래서 판정 트리 수준 단위 테스트로 잰다.
- **R6 → R3**(탐침 문항을 오개념 매칭으로 틀림): 최신 결정이 R3 → EOS-24 경로(안전장치 ①② — 이번 회차 가설 · 신뢰 하한 0.7 초과). 교정 대상은 탐침 문항의 개념 P다. 단 새 매칭의 신뢰가 매칭 하한 0.65 이상 · 집행 하한 0.7 이하이면 R3는 발화하되 집행되지 않아(`weak_misconception_evidence`) 기본 경로로 간다 — ⓑ가 서지 않는 사각대다(§5 발견 9B).
- **해소 범위 = 활성 가설 0인 학생의 R6.** 다른 개념의 옛 가설이 활성인 학생은 원인 미상 오답도 R3로 분류되고, EOS-24 안전장치 ①이 막아 기본 경로로 간다 — 이 학생에게는 EOS-26 탐침이 돌지 않는다(§5 발견 9A). R3 입력 범위를 좁히는 `EOS-138`에 두 합성을 반례로 병기했다.
- **R3 경로는 한 줄도 바뀌지 않는다.** 이름표(`misconception_remediation`) · 학습 밴드 · `cat_v1_state_remediation` · EOS-124 해소 생략이 그대로다. R6 경로는 반대로 EOS-124 해소를 **돌린다**(이름표가 숙달 파생이므로).

### ⓕ 그래프 예산 — depth ≤ 2 · nodes ≤ 20 · timeout

- **R6가 새로 읽는 것은 앵커 C 1개의 직접 선수뿐이다**(`fetch_prerequisites(C, max_depth=1)`). 전체 그래프 읽기는 없다. 막히지 않았거나 연속 두 번째면 이 읽기도 돌지 않는다.
- **예산은 정책이 소유한다.** `route_by_learning_state`는 예산을 건 읽기 함수를 **주입받는다**(정책의 `_read_prerequisites` — 깊이는 요청과 예산 천장 중 작은 쪽, `_within_budget` 시간 예산, `_apply_node_budget` visited·노드 20 상한). 이 모듈이 예산을 다시 정의하면 예산 정의가 두 곳이 된다 — 천장 상수(`_DEPTH_CEILING`·`_NODES_CEILING`)와 그 뮤테이션 하네스(`scripts/analysis/mutate_recommendation_policy_guards.py`)는 `recommendation_policy.py`를 가리킨다. 순환 import(정책 → 이 모듈 → 정책)도 이 주입으로 피한다.
- **시간 초과는 추천을 실패시키지 않는다** — 같은 개념 연습으로 내려가고(`same_concept_graph_timeout`) 예외 타입명을 로그에 남긴다(침묵 실패 금지).
- **예산은 읽기마다 걸리고 요청 전체 상한은 없다.** R6 경로의 최악은 C 선수 읽기 + EOS-124의 앵커 선수 읽기(depth 2) + 앵커 후행 읽기 = 읽기 3건 × 2.0초다(`ConceptGraphBudget.timeout_seconds` 기본값 — 합산은 추론). 요청 단위 마감은 EOS-124 예산 구조 전체의 변경이라 이 태스크 밖이다(§5 발견 13 · 정직 표기).
- depth 1은 천장 2 안이다. 탐침이 depth 2를 쓰지 않는 이유는 예산이 아니라 교수학이다(ⓑ).

### ⓖ 작동 비율 기록

- `StateDirectiveOutcome`에 9값을 더한다: `prerequisite_probe` · `same_concept_repeat` · `same_concept_not_blocked` · `same_concept_anchor_unmeasured` · `known_prerequisite_deficit` · `same_concept_probe_unsupported` · `same_concept_probe_refuted` · `same_concept_probe_unavailable` · `same_concept_graph_timeout`. 미해소·후보 0은 기존 `anchor_unresolved`·`no_candidate_in_concept`을 쓴다.
- 이 값은 기존 응답 필드(`GET /v1/me/next-problem`의 `learning_state_directive`)와 처치 기록 meta 키에 그대로 실린다 — 저장 좌석 신설 0.
- 후보 제한으로 나간 추천은 `policy_version=cat_v2_state_undiagnosed`로 적는다(후보 생성 규칙이 다르다 — REC-11 소급 평가가 섞지 않게). `v2`는 이름표·재선택을 `cat_v2`(EOS-124) 규칙으로 붙인다는 뜻이다. 제한하지 못한 R6(`anchor_unresolved`·`no_candidate_in_concept`)는 기본 경로와 같은 입력·같은 결과라 `cat_v2`를 유지한다.
- 작동 비율: `learning_state_directive`가 R6 값인 행 중 `prerequisite_probe` 비율이 "탐침이 실제로 나간 비율"이고, `known_prerequisite_deficit`이 "측정된 결손으로 바로 연습한 비율", `same_concept_*`가 탐침하지 않은 이유의 분포다. **앱 오답 원천이 생기기 전까지 운영 분포는 0건이다**(§1-6) — 0건을 "학생들이 원인 미상 오답을 하지 않았다"로 읽지 않는다.

### 부가 안전장치 — R6 경로에서는 전진하지 않는다(`state_withheld`)

R6 경로의 앵커가 전진 구간(> 0.7)이면 EOS-124 전진 재선택을 돌리지 않고 앵커 개념 연습으로 강등한다. 해소값은 새로 둔 `state_withheld`다 — 측정 반증(`refuted`)이 아니다. 오답은 이미 숙달에 반영됐고 반영된 숙달이 여전히 전진을 말한다. 막은 주체는 측정이 아니라 R6 결정("같은 개념 연습")이다(§5 발견 12). 닿는 경로는 막히지 않은 오답이다 — 사전 숙달 0.95인 학생은 오답 1회로 약 0.73까지만 내려간다(BKT 기본값). 탐침 경로에서는 미측정 선수만 후보라 정상 입력으로는 닿지 않는다.

## §4. 선택 축 — 제한은 WHERE를 덧붙일 뿐이다

- **탐침 후보**: `load_target_candidate_rows`(EOS-124 신설 — 노출 게이트 3축 · PRIMARY 매핑 · 미응답 · 형제 배제 · 개념별 θ 근방 상한)를 그대로 쓴다. 게이트를 다시 쓰지 않는다(REC-06 "한 곳에서만 정의").
- **같은 개념 후보**: EOS-24의 `build_concept_candidate_pool_stmt`(기본 후보 SELECT + PRIMARY = X)를 그대로 쓴다.
- **밴드는 경로가 정한다.** 연습 경로 8종(`same_concept_*` · `known_prerequisite_deficit`)은 요청 목적과 무관하게 **학습 밴드**(정답 확률 70~85% 지향 · REC-04)로 고른다 — EOS-24가 교정 경로에 학습 밴드를 강제한 것과 같은 규칙이다. REC-04 주석(`api/me.py`)은 정보량 최대를 "학생이 절반을 틀리도록 설계된 출제"로 적고, 학습 세션에 적용하면 교수학 금기라고 적었다. 오답 직후의 연습이 바로 그 자리다(§5 발견 6). **탐침만 측정 자체**라 요청 목적(기본 `diagnosis` · 정보량 최대) 그대로다. 초안은 "제한된 한 개념 안에서 θ -4.0이면 어느 쪽이든 가장 쉬운 문항"이라며 요청 목적을 유지했으나, 그 전제는 신규 학습자(하네스 픽스처)에서만 성립한다.
- **정렬 재선택도 1차 선택과 같은 요청 상황으로 고른다.** EOS-124 (가)·전진 재선택(`_select_aligned`)은 1차 선택이 쓴 밴드를 그대로 받는다 — 연습 경로가 학습 밴드를 강제했으면 선수로 내려가는 재선택도 학습 밴드다. 지시가 없는 요청은 원래 요청 그대로라 전환 전과 같다.
- **정렬 계약은 그대로 강제된다.** 전달 문항 = 제한 후보 중 하나(또는 EOS-124 재선택 결과), 이름표 = 그 문항의 개념에서 EOS-124가 해소 → `check_intent_alignment`가 `NextProblemOutcome` 생성 시점에 검증한다(R2 target = 전달 개념 · R3 관계 행위면 앵커 ≠ 목표 · R4 비관계면 목표 = 앵커).

비판이 "결정별 점검"에서 지적한 대로, 강화된 프로브도 "신규 학습자 · 단일 선수 · 활성 가설 0" 한 배치다. 그래서 막힘 문턱·아는 결손·숙달 선수 경로는 프로브가 아니라 R6 전용 통합 테스트(`tests/backend/api/test_eos26_r6_prerequisite_probe.py`)가 각각의 배치로 잰다(§6).

## §6. 해소 신호와 하네스 강화 (acceptance ⑤)

- **프로브를 강화했다.** EOS-139 프로브의 폐루프는 방해 개념 없이, 하네스 기본 요청으로만 쟀다(§1-2). 이 태스크 뒤의 프로브는 **방해 개념 배치에서, 두 요청 형태(`prioritize_weak_concepts` true · 미전송)로** 원인 미상 오답 → 첫 추천(ⓖ 선수 지향) → 그 추천도 틀림 → 다음 추천(ⓕ 폐루프)을 잰다. 두 형태 모두 성립해야 True다. 선수의 선수(`root → pre`)를 하나 더 심어, 연속 판정이 빠지면 ⓕ가 끊기게 했다(절을 밟는 픽스처).
- 변경 전 코드에서 강화된 프로브는 ⓖ·ⓕ 둘 다 False를 낸다(ⓕ의 전제인 "첫 추천이 선수 진단"부터 끊긴다). 변경 뒤 둘 다 True라 `_FROZEN_PROBE`와 `general` Loop 1 `보정` 동결이 해소 신호를 냈고, 둘을 True로 승격했다. §18 xfail 대상은 공집합이 됐다(`_s18_open_variants` 유도).
- **해소 수준 = API 계약.** 승격 문면(동결 주석)에 "실제 앱은 R6에 도달하지 않는다 · `EOS-146`"을 함께 적었다(§1-6). 승격을 앱 원천이 생길 때까지 미룰지는 Kiki 판단 사항이다.

- **R6 전용 통합 테스트**(실 PG · HTTP · `tests/backend/api/test_eos26_r6_prerequisite_probe.py` · 8건): 판정 트리의 갈래마다 한 여정이다.

### 7-3. 사고 기록

- **`nondiscriminating-check` 계열 — 요청 형태**(§1-2): EOS-139의 폐루프 True가 방해 개념 부재 + 하네스 전용 요청 형태에 기댔다. 대책은 코드(강화된 프로브 — 두 요청 형태 × 방해 개념 · R6 전용 통합 테스트)와 태스크(`PED-40`).

- **`verification-tree-mutation-during-check` 계열**: 이 세션에서 두 번, 오래 도는 검증(백엔드 잡 재현 · 커밋본 뮤테이션 하네스)이 도는 동안 작업 트리를 고쳤다. 두 실행 결과 모두 폐기하고 수정이 끝난 뒤 다시 돌렸다(§9). 대책 태스크는 기존 `HARN-126`(주입을 임시 worktree에서만)이다.

- 다섯 건 모두 사고 대장(`backlog/incidents.ndjson`)에 기록했다.

## §8. 이 판정이 하지 않은 것

- **상태 머신은 한 줄도 바꾸지 않는다**(`V1_RULES` · R6 `next_action`). `EOS-144`가 판정한다.
- **앱의 오답 원천을 만들지 않는다**(§1-6 · `EOS-146`). 이 해소는 API 계약 수준이다.
- **R5를 집행하지 않는다**(셋째 연속 오답은 기본 경로 — `EOS-148`).
- **depth 2 탐침은 하지 않는다**(ⓑ). (가) 재선택이 depth 2로 C 제한을 벗어나는 것은 막지 않는다(§5 발견 7).
- **탐침 문항을 "원인을 변별하는 문항"으로 좁히지 않는다.** 지금은 선수 개념의 문항이면 된다(EOS-24 §7-3과 같은 한계). 미측정 선수 사이의 우선순위(`edge_strength` · 학년 거리)도 두지 않는다(§5 발견 8).
- **탐침 정답 뒤 C로 복귀시키지 않는다**(§2-3 · `EOS-144` ④).
- **"연속"의 시간 창을 두지 않는다**(ⓒ · `EOS-145` ④). 상태 머신의 연속 정의와 다르게 만들면 두 좌석이 다른 연속을 말한다.
- **요청 단위 그래프 마감을 두지 않는다**(ⓕ · §5 발견 13).
- **처치 기록 meta에 앵커 C를 싣지 않는다**(§5 발견 11).
- **활성 가설 학생·R6→R3 사각대는 다루지 않는다**(§3 ⓔ · `EOS-138`). 해소 범위는 활성 가설 0인 학생의 R6다.
- **수능 정책**(§7-1).
- **실데이터의 폴백 빈도는 재지 않았다.** 컨테이너 DB는 마이그레이션만 적용한 빈 DB다. 원자 백본(2,683노드 · 2,210엣지)에서 선수가 있는 개념의 비율과 그 선수에 승인 문항이 있는 비율은 운영 DB의 `learning_state_directive` 분포가 말해 줄 것이다(ⓖ) — 단 앱 원천이 생긴 뒤다.
