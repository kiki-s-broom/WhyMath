# HARN-193 설계 판정 — 게이트를 붙이고 claim을 푼 태스크의 착수 공백

**판정 기준: origin/main `ebd7a159`** (2026-09-30 착수 시점). 아래 실측은 같은 시각 이 클론이 fetch로 받은 원격 ref 42개(`origin/HEAD` 포함)를 기준으로 한다. 미머지 근거가 섞이는 항목은 본문에서 따로 표시했다.

## 0. 결론

- **읽기측 스캔(후보 ⓑ)을 채택한다.** `next`·`start`·`brief`가 "미머지 브랜치가 이 태스크에 트렁크에 없는 게이트를 붙여 두었는가"를 보고, 있으면 후보에서 빼거나 착수를 거부한다.
- **쓰기측 홀드(후보 ⓐ)는 채택하지 않는다.** 그 자리가 남기는 잔여 위험(브랜치가 원격에 push되기 전의 창)은 후속 태스크 `HARN-207`로 분리했고, 관측이 없으면 2026-11-30에 cancel한다.
- 검증: 테스트 33건 통과, 뮤테이션 28종 전건 RED·생존 0, 실제 원격에서 사고 상태(`EOS-129`) 양성 검출.

## 1. 무엇이 비어 있었는가 (원인 축)

착수 차단은 세 겹이다.

| 겹 | 무엇을 보는가 | 어디에 실리는가 | 언제 보이는가 |
|---|---|---|---|
| ⑴ 원격 claim | 누가 지금 잡고 있는가 | `harness-claims` 브랜치 | push 즉시 |
| ⑵ 트렁크 사본 | `requires_gates`·`depends_on` | `origin/main`의 태스크 파일 | PR이 머지돼야 |
| ⑶ 미머지 done | 끝낸 브랜치가 있는가 | 브랜치의 태스크 파일(HARN-11 스캔) | 브랜치 push 뒤 |

표준 흐름 `start` → `gates add` → `amend --gate` → `unblock`에서 `unblock`은 ⑴을 즉시 걷는다. 그 자리를 대신할 ⑵는 **브랜치에만** 있어서 PR이 머지되기 전까지 어느 세션에도 보이지 않는다. ⑶은 "끝냈는가"만 보고 "게이트를 붙였는가"는 보지 않는다. 그래서 보호를 교대하는 순간에 공백이 생긴다.

이력(태스크 원문·사고 대장 기록): `EOS-129`가 하루에 세 세션에서 착수됐고, `EOS-137`과 `EOS-146`이 같은 형태로 노출됐다. 네 건 모두 게이트를 담은 브랜치가 **이미 push된 뒤**였다는 점이 아래 판정의 핵심 근거다.

## 2. 후보 판정

| | ⓐ 쓰기측 홀드 | ⓑ 읽기측 스캔 | ⓒ 둘 다 |
|---|---|---|---|
| 하는 일 | `unblock`이 트렁크에 없는 게이트를 가진 태스크의 claim을 걷지 않고 게이트 대기 홀드(`kind: block`)로 바꾼다 | `next`·`start`가 원격 브랜치 사본에서 트렁크에 없는 `requires_gates` 추가를 찾는다 | 둘 다 |
| 막는 범위 | push 전 창까지 | push된 브랜치 | 둘 다 |
| 원격 claim 쓰기가 막힌 환경 | **무력** (refs/claims push가 프록시에서 상시 403이던 이력 — HARN-07) | 작동 (원격 ref를 읽기만 한다) | 읽기측이 받친다 |
| 새로 생기는 상태 | 홀드 레코드 — 수명 관리 필요 | 없음 (순수 함수) | 홀드 레코드 |
| 트렁크에 착지한 뒤 | 홀드를 걷는 주체가 있어야 한다 | 자동 해소 | 홀드 정리 필요 |

**ⓑ를 채택한 근거 셋.**

1. **이력 네 건을 전부 막는다.** 네 건 모두 브랜치가 push된 상태였다. 사고 상태를 그대로 재현한 테스트가 통과하고(`test_start_refuses_and_names_branch_and_gate`), 실제 원격에서 2026-09-28의 `EOS-129` 상태가 지금도 검출된다(브랜치 `claude/magical-maxwell-hja5kh-eos129`의 게이트 `G-eos129-item-response-census` — 트렁크에는 정의 없음, 그 브랜치에서는 pending).
2. **쓰기측이 무력한 환경에서도 작동한다.** 태스크 원문이 요구한 판정 조건이다. 읽기측은 remote-tracking ref만 읽어서 claim 쓰기 채널의 가용성과 무관하다.
3. **홀드 수명이라는 미해결 문제를 만들지 않는다.** `unblock`은 blocked·in_progress에서 todo로 가는 전이 전용이라, 이미 todo인 게이트 대기 태스크에는 홀드를 걷는 경로가 없다. 흡수된 `HARN-191`(cancelled)이 이 문제를 풀려고 `claims reap`과 브리핑에 해제 판정을 새로 넣으려 했다. 읽기측은 상태가 없어서 트렁크에 착지하는 즉시 스스로 풀린다(`test_merged_but_undeleted_branch_is_not_reported`, `test_gate_already_on_trunk_is_handled_by_the_ordinary_check`).

**ⓐ 미채택의 대가(정직한 잔여 위험).** 게이트를 붙이고 claim을 푼 세션의 브랜치가 아직 원격에 없으면 이 스캔은 그것을 볼 수 없다. 이 창은 홀드로만 메워진다. 이력에서는 관측되지 않았으므로 관측 기반으로 추적한다 — `HARN-207`(착수 조건: 사고 대장에 그 원인의 사고가 등재될 것 · 재확인일 2026-11-30 · 홀드 수명 문제를 먼저 푸는 설계가 선행 조건).

## 3. 구현

- `remote_claims.scan_remote_gate_attachments` — `scan_remote_done`과 같은 `git cat-file --batch` 한 번으로 (트렁크 + 브랜치) × 태스크 사본을 읽는다. 브랜치 사본의 `requires_gates`에서 **트렁크 사본과 호출자 로컬 사본이 이미 아는 게이트를 뺀** 나머지가 "그 브랜치만 붙인" 게이트다.
- 그 중 트렁크 `gates.yaml`이 `cleared`·`waived`로 기록한 것은 제외한다(낡은 브랜치의 영구 오차단 방지). 트렁크에 정의가 없거나 `pending`이면 미통과로 센다 — 신규 항목의 부재는 안전 방향이 아니다. 브랜치 쪽 게이트 상태는 표시용이며 판정에 쓰지 않는다(미머지 브랜치의 clear는 트렁크의 clear가 아니다).
- 배선 세 곳: `next`(후보 제외 + 이유 stderr) · `start`(거부 + `--ignore-remote-claim` 우회 + 우회 이벤트 `start_ignored_unmerged_gate_attach`) · `brief`(제외 + 이유를 **stdout**에 싣는다 — 훅이 stderr를 버린다).
- `start`는 세션 자신의 브랜치를 제외한다(내 로컬 사본이 내가 push한 사본보다 최신이다).

**표시 정직성 (acceptance ⑤).**

| status | 뜻 | 표면 |
|---|---|---|
| `ok` | 정상 | 발견분만 표시 |
| `truncated` | 브랜치 수가 상한을 넘어 일부만 봤다 | 발견분은 유효, 빈 결과만 판정 불가 |
| `no_refs` | 캐시에 다른 브랜치가 없어 못 봤다 (shallow·단일 브랜치 클론) | 판정 불가 |
| `offline` · `error:<Type>` | 조회 실패 | 판정 불가, 예외 타입명 포함 |
| `error:BatchMisaligned` | `cat-file` 출력 정렬 어긋남 | 판정 불가 (엉뚱한 브랜치에 붙이지 않는다) |

`start`에서 fetch가 실패하면 기존 "미머지 done 탐지 불가" 경고에 묻지 않고 게이트 부착 판정 불가를 **따로** 낸다.

## 4. 검증 — 무엇을 돌렸고 무엇이 나왔는가

- `tests/harness/test_gate_attach_claim_gap.py` **33건 통과**(무작위 순서). 진짜 git 원격 픽스처를 쓴다(시임 금지). 세 상태를 모두 밟는다 — 게이트가 트렁크에 있음(정상 차단) / 원격 브랜치에만 있음(이번 사고) / 없음(대조군).
- `scripts/analysis/mutate_gate_attach_guards.py` — **28종 전건 RED · 생존 0** (앵커 1건 · 주입 실재 · 쓴 내용 재확인 · 원복 바이트 동일 · 대조군 선행 GREEN · 종료 시 소스 세 파일 sha256 일치). 축: 차집합 기준선(트렁크·로컬) · 트렁크 통과 면제 · 트렁크 정의 없음의 미통과 취급 · 자기 브랜치 제외 · 정렬 검사 · 상한 · 필드 오독 · start 거부 · 우회 이벤트 · next 제외/경고 · brief 제외/렌더/문구/배선 · `no_refs`.
- 실데이터(이 클론, 원격 42개 ref): 전체 태스크 950건 스캔 5.15초 · `next`가 실제로 넘기는 준비 후보 72건 0.80초(기존 미머지 done 스캔 0.74초와 같은 규모). 사고 상태 양성 대조 — `EOS-129` 검출.
- CI 잡 미러 결과는 PR 본문에 적는다(이 문서 작성 시점에는 커밋 전이라 미실행).

**중간에 틀린 것들 (기록으로 남긴다).**

1. 첫 뮤테이션 실행에서 M27·M28이 **생존**했다. "브랜치가 정말 없는 저장소" 대조군 테스트가 그 절에 닿지 않았다 — 트렁크 착지 과정의 `add`가 번호 예약용 `harness-claims` 브랜치를 만들어 "다른 브랜치가 있는" 상태였다. 픽스처가 부산물 브랜치를 지우고 남은 브랜치가 `main` 하나뿐임을 스스로 단언하도록 고친 뒤 전건 RED가 됐다.
2. M07(트렁크 ref 제외)을 처음엔 "동치라 생존이 정상"으로 표기했다. `no_refs` 판정을 추가한 뒤로는 트렁크 ref가 `wanted`에 남으면 "다른 브랜치 0개" 판정이 무너져서 실제 뮤테이션이 됐다. 하네스가 "동치로 표기했으나 검출됨"으로 정확히 지적했고 표기를 정정했다.
3. 첫 구현은 shallow 단일 브랜치 클론에서 `fetch=False`로 다른 브랜치를 **0개 훑고도 `ok`**를 반환했다(실측: `--depth 1` 클론의 캐시는 HEAD·main뿐). 측정 실패가 "부착 없음"으로 위장되는 형태라 `no_refs`를 신설했다.
4. `brief`는 shallow 클론에서도 사고를 잡는다 — `brief` 안에서 먼저 도는 문서 시리즈 중복 스캔(`scan_doc_series_duplicates`, 기본 `fetch=True`)이 전체 브랜치를 fetch하기 때문이다(실측: `next` 뒤 캐시는 그대로, `brief` 뒤에는 다른 브랜치 ref가 생긴다. 처음엔 stale-branch 스캔이 원인이라고 **추정**해 적었으나 그 스캔은 shallow 클론에서 fetch 앞에서 물러난다 — 문서 시리즈 스캔을 꺼 보는 대조 실험으로 정정했다). 이 순서는 우연한 부산물이라 **계약이 아니다**. 그 스캔이 빠지거나 실패하면 이 스캔이 `no_refs`로 정직하게 물러난다.

## 5. 알려진 한계 (정직 기술)

1. **push되지 않은 브랜치는 관측할 수 없다.** 위 ⓐ 미채택의 대가다 → `HARN-207`.
2. **낡은 브랜치가 트렁크에서 떼어 낸(amend --remove-gate) 게이트를 아직 들고 있으면**, 그 게이트가 트렁크에서 pending인 동안 과잉 차단한다. 메시지가 브랜치를 지목하고 `--ignore-remote-claim`으로 넘길 수 있다. 실제로 몇 번 일어나는지는 측정하지 않았다.
3. `next`·`brief`는 마지막 fetch 시점의 캐시 ref를 본다. 확정 지점은 `fetch=True`로 다시 보는 `start`다.
4. 태스크 파일 파서(`_top_level_list_field`)는 `store.dump_task`가 내는 형태만 읽는다. 손편집으로 형식이 어긋난 파일은 미탐이다(기존 스캔과 같은 한계).
5. **작동 비율은 측정하지 않는다.** 거부와 제외는 이벤트를 남기지 않는다 — 거부마다 이벤트를 쓰면 실패한 착수가 작업 트리를 더럽힌다. 우회만 이벤트로 남는다. 이 스캔이 실제 운영에서 몇 번 발화하는지는 아직 모르며 `HARN-207` ④가 측정 방법을 묻는다.
6. 운영 데이터로 재지 않았다. 검증은 합성 픽스처와 이 클론의 원격 스냅샷 한 장이다.
