# 02. 학생 UI 설계 계획 — 전 대상 + 영업

> **질문**: WhyMath는 초등~중등~고등(일반·진로·재수)·영재·대학의 넓은 학생을 대상으로 하고, 교사·부모·학원 영업까지 고려한다. UI 설계 계획을 마련하라.
>
> **한 줄 답**: **단일 Flutter 앱 + 적응형 셸(Adaptive Shell)**. 공유 메타인지 코어 하나 위에 **연령대 × 모드 × 역할**의 3축으로 분기한다. 3개 앱 분리는 반려(`06:170-184`). 교사만 별도 웹, 학원은 그 웹의 B2B 변형.

---

## §1. 전략 — 단일 앱, 적응형 셸

PRD의 "학생·교사·학부모 3개 별도 앱"은 **반려됐다**. 이유(`06:179-184`·`07:70-74`):

- 코어 상태(BKT·오개념·`MasteryState`)는 학생·교사·학부모가 *같은 데이터의 다른 뷰*를 보는 구조 — 앱을 나누면 동기화 비용만 는다.
- 4~5명 팀이 3개 앱을 동시 개발·유지하는 것은 범위 폭발("처음부터 풀 K-12"와 같은 리스크).

**대신**: 한 코드베이스가 **셸(chrome)만 바꿔** 초등생부터 대학생까지, 학생부터 학부모까지 커버한다. 교사 대시보드만 별도 웹(React/Next)으로 분리(시험지 빌더·SEO는 PC 웹 작업·Phase3+).

```
                    공유 메타인지 코어 (L1-L4, 서버)
                              │
        ┌─────────────────────┼─────────────────────┐
   [연령대 축]            [모드 축 L6]            [역할 축]
   초 / 중 / 고 / 대   6모드 + 커리큘럼 정렬   학생 / 학부모(인앱) / 교사(웹)
        └─────────────────────┼─────────────────────┘
                     단일 Flutter 앱 (셸만 분기)
```

## §2. 3개 분기 축

### 축 1 — 연령대(학교급): 초 / 중 / 고 / 대

같은 코어, **chrome만 조정**. 수학 로직·판정은 학년과 무관하게 서버가 한다(표현≠의미). 조정 대상:

| chrome 요소 | 초등 | 중등 | 고등 | 대학 |
|---|---|---|---|---|
| 타이포·정보 밀도 | 큼·낮음 | 중간 | 중간 | 조밀·형식적 |
| 탭 영역·조작 비중 | 최대(≥48dp·정본 하한)·시각/드래그↑ | 중간 | 손글씨·수식입력↑ | 밀도↑·키보드 |
| 언어 난이도(`SpeechSpec` 학년 프로파일) | 쉬운 낭독 | — | — | 형식 용어 | 
| 손글씨 비중 | 낮음 | 중간 | **높음(킬러)** | 중간 |
| 학습 특성(원본 [B]) | 큰 버튼·캐릭터·애니메이션 | 개념 중심·시각화 강화 | 빠른 이동·증명·다양한 풀이 | 정리(Theorem)·증명·응용·CAS·시뮬레이션 |

- **Math-to-Speech 학년 프로파일**은 이미 설계됨(`05:45-52`): 같은 수식 구조를 학년별로 다르게 낭독하는 프로파일 파라미터. 연령대 축의 언어 조정은 이 `SpeechSpec`을 재사용한다.
- **메뉴 구조는 학교급이 달라도 동일**(원본 [B]) — chrome(외피)만 갈아끼운다. 이것이 "적응형 셸"의 핵심.
- 접근성 기준(대비 4.5:1·탭 **48dp**·색맹 친화·TTS)은 전 연령 하한선(`05_interaction.md` §5). 탭 영역 정본 단일값은 48dp(실 게이트 `androidTapTargetGuideline` 기준 — `06_design_system.md` §7).
- **원본 [B]는 재수·영재도 이 축에 넣었으나**, WhyMath에선 재수=`retake`·영재=`gifted`로 **축2(모드)** 소관이다(콘텐츠 풀·교수 가중치가 바뀌는 것이지 학교급이 아니므로). 각 모드는 chrome 강조(재수=문제 중심·시간 관리·약점 분석 / 영재=탐구·증명·일반화·확장)를 덧입힌다.

> **⚠️ 충돌 교정 — 초등 "게임 요소"**: 원본 [B]는 초등 UI에 *게임 요소*를 제안한다. 그러나 WhyMath의 **반게임화**는 하드 제약(`05:31-34`·`CLAUDE.md` 교수학 금기)이다. 교정 원칙:
> - ✅ **허용**: 연령 적합 *시각적 재미* — 큰 버튼·캐릭터·부드러운 애니메이션·즉각적 시각 피드백(정답률과 무관).
> - ❌ **금지**: *중독성 게임화* — 정답률 랭킹·스트릭·카운트다운·보상 루프·경쟁. 학습 시간·정답률로 우열을 매기지 않는다.
> - 예외: 자유학기제 모드만 `gamification_level ≤ 3`(적정 수준·`06`). 초등이라는 이유로 이 상한을 넘기지 않는다.
> 즉 초등도 "재미있되 중독 설계는 없는" 원칙을 지킨다(의사결정 우선순위 #1 학생 웰빙 > #7 개발 편의).

### 축 2 — 모드(L6) + 자동 커리큘럼 정렬 (직교)

6모드는 진입점, 정렬은 그 위에서 개인 맞춤(`06:96-103` — 곱집합). 넓은 대상은 대부분 이 축으로 흡수된다:

- **일반**: 학교 진도·수능·내신 모드.
- **진로**: 고교학점제 진로별 과목 선택 추천(PRD 특성 #78·FR-017) — 학교 진도 모드의 콘텐츠 필터 변형.
- **재수(N수)**: `retake` 모드 🟢(검정고시 N수·자사고 N수 페르소나 C·B).
- **영재**: `gifted` 모드 🟢(게이팅 구현·코퍼스 대기, Phase3 프리미엄 월 49,900원).
- **대학**: 별도 코퍼스 존재(`data/corpus/concept_content_university_v1/`·성취기준 409·원자 513) — 진단·개념 콘텐츠는 준비됨. 전용 모드는 후속(PRD #70 v3.0).

### 축 3 — 역할 (6개 역할 UI 레이어)

원본 [B]가 제안한 **"한 플랫폼 위 6개 역할 UI 레이어"** 모델을 채택한다 — *UI만 다르고 내부 엔진(개념 그래프·DSL·AI Tutor)은 모두 동일*. 이는 WhyMath의 "단일 코어 + 역할 분기"와 정확히 같은 철학이다. 단, **전달 형태**는 WhyMath의 확정 결정(3앱 분리 반려·교사만 별도 웹)에 맞춘다.

| # | 역할 UI | 관심사(원본 [B]) | WhyMath 전달 형태 | Phase | 상태 |
|---|---|---|---|---|---|
| 1 | **학생** | 목표·학습·AI 질문·오답·성취도 | Flutter 앱(기본) | 1 | 🟢 |
| 2 | **교사** | 대시보드·AI 수업 생성·평가·숙제·학습 분석 | 별도 웹(React/Next) | 3+ | 🔴 |
| 3 | **학부모** | 오늘 학습·주간 리포트·취약 개념·AI 상담 | **인앱 역할 레이어** + 보고서 opt-in | 3 | 🔴 |
| 4 | **학원** | 원생·반·숙제·시험·성적·출결·상담 | 교사 웹의 **권한 변형**(다수 학생 그룹) | 3+ | 🔴 |
| 5 | **학교 관리자** | 학년/반/교사별 통계·교육과정 진도·AI 분석 | 교사 웹의 **권한 변형**(기관 단위) | 4+ | 🔴 |
| 6 | **콘텐츠 제작** | Concept·Objective·Pedagogy·Flow·Misconception·DSL·Preview·Publish | **내부 운영 콘솔**([03](03_admin_console_plan.md)·[04](04_admin_console_architecture.md)) | 2+ | 🔴 |

- **전달 형태 정합**: 학생·학부모=단일 Flutter 앱 안 역할 레이어 / 교사·학원·학교관리자=**같은 교사 웹의 RBAC 권한 변형**(별도 앱 신설 아님) / 콘텐츠 제작=운영 백오피스(DSL이 생성되는 곳). 즉 6개 "레이어"지만 물리 앱은 **①Flutter 학생앱 ②교사·학원·학교 웹 ③내부 운영 콘솔** 3벌로 흡수된다.
- **공통 네비게이션**(원본 [B]): 모든 역할 UI가 `홈 · 검색 · AI · 알림 · 내정보` 5개를 공유하고, 나머지만 역할별로 달라진다. 적응형 셸의 공통 chrome.

### 관통 원칙 — 목표 → 성취 → 다음 목표 (원본 [A]·[B])

원본이 반복 강조한 차별점: 기존 앱은 `학년 → 단원 → 문제` 중심이지만, WhyMath는 **`오늘 목표 → AI 생성 활동 → 성취 → 다음 목표`** 중심이다. 학생은 "문제를 푼다"가 아니라 "목표를 달성한다". → 학생 UI의 구체 흐름은 [01 §5 학습 여정](01_student_pipeline_to_menus.md) 참조.

> **동기 모델 정본 개정(2026-08-03·`gamification_module_gap_review.md` §3 D3)**: "성취"가 무엇으로
> 채워지는지가 이 문단까지는 미정의였다. 반게임화(랭킹·스트릭·보상 연출 금지) 반대편의 긍정 축을
> **"성장의 증거(evidence of growth)" 5원칙**으로 확정한다.
> 1. **보상이 아니라 증거** — 외재 보상(XP·배지·코인) 대신 *자기 행동이 만든 변화의 증거*를
>    보인다(도움 없이 간 거리·줄어든 도움·해소된 오개념·스스로 도달한 풀이).
> 2. **비교가 아니라 자기 대비** — 모든 지표는 본인 과거 대비로만(타 학생·평균·순위 파생 금지).
> 3. **즉시 피드백의 자리는 보정(calibration)이다** — 확신도×정오답 기반 메타인지 피드백이
>    정답 보상의 자리를 대신한다.
> 4. **연속성은 압박이 아니라 복귀 지원** — Streak의 핵심은 "돌아오기 쉽다"이지 "끊기면 잃는다"가
>    아니다. 연속 일수 카운터·Freeze·복구권은 미채택.
> 5. **정서 신호는 내부 결정 입력으로만** — 학생 대면 정서 라벨링 금지.
>
> 상세 설계·근거·acceptance는 `gamification_module_gap_review.md` §3 D3 참조.

## §3. 정보구조(IA)와 온보딩

### 학습 루프 IA
```
온보딩(3분 무마찰) → 진단(CAT) → 학습 루프(홈·학습·탐구·나) → 학습 경로 갱신
```
- 하단 탭 4개(홈/학습/탐구/나)는 [01 문서 §4](01_student_pipeline_to_menus.md) 참조. 🔴 미구현.
- 모드 스위처는 홈 상단 또는 "나" 탭. Phase1은 사고력·메타인지 2모드만.

### 온보딩 — 연령대별 분기 (`05:87-97`)
표준 흐름: `국가 → 학년 → 학교 → 교과서(출판사) → 진도 → 목표`. **3분 무마찰**(드롭다운·검색·탭 위주, 자유 입력 최소).

- **현재 구현**(🟡): 목표 4필드(목표 등급·표준점수·시험일·출생연도)만. 국가/학교/교과서 검색 단계는 🔴. 온보딩 노출 영속(shared_preferences)도 🔴 → 지금은 매 진입마다 노출.
- **연령대 확장 필요**: 초등은 "등급·표준점수" 개념이 없고, 대학은 교과서·시험 체계가 다르다. → `StudentProfile` 스키마를 학교급별로 분기(초등=단원 진도 중심, 대학=과목·학기 중심). L5는 수집·전달만, 판정은 서버.

## §5. 영업(GTM) 표면 — 교사·부모·학원

영업은 별도 앱이 아니라 **역할 축(축3)의 확장**으로 실현한다. 세 대상 모두 독립 코어 API를 소비.

### 학부모 (B2C 리텐션·재구매 지렛대)
- **인앱 학부모 모드** + **주간 보고서**(`07:23-28`): 주 1회 푸시(학생 *동의 시*), 약점·강점·메타인지 순간·5분 대화 주제. **비교·랭킹 금지**, L4 톤 필터(긍정·정직) 적용.
- **가족 결제**(페르소나 E·가족 월 5~10만) — 결제 주체가 학부모.
- 상태: 🔴 Phase3(`07:98-114` opt-in 60%+ 목표).

### 교사 (B2B PMF·학교 유입)
- **별도 교사 웹**(Phase3+·React/Next): 학급 학습 상태·숙제 출제(성취기준 코드 기반)·**단계별 자동 채점**(OCR→PRM, "어느 단계에서 막혔는지"까지·정답/오답 이분법 아님)·**수업 영사 모드**(개별 학생 식별정보 미표시)(`07:30-39`).
- **학교 무료 제공**으로 PMF 검증 → 유입.
- 관리 UI 관점은 [03 문서](03_admin_console_plan.md)·[04 문서](04_admin_console_architecture.md)에서 상술.

### 학원 (B2B 라이선스)
- 직접 "학원용 기능"은 없다 — 교사 웹을 **재사용**한 B2B 라이선스 + "월 200만원 학원 대체" 포지셔닝(`market_analysis`).
- 향후 **학원 관리자 역할**(다수 학생 그룹·복수 강사 관리)은 교사 대시보드의 변형(`SCHOOL_ADMIN` 역할·RBAC 매트릭스)으로 실현 — [04 문서 §2 RBAC](04_admin_console_architecture.md) 참조.

> **안전선**(`07:46-59`): 학생 이름·학교 미표시, 본인 풀이 전 타인 풀이 미노출, "최고 풀이" 랭킹 금지, 부모에게 불필요한 PII 금지. 영업 표면도 이 안전선을 벗어나지 않는다.

## §6. 디자인 시스템 기초 (🟡 착지 시작 — `lib/theme/` 신설)

**착지(MOB-09)**: `lib/theme/app_theme.dart`(`WhyMathTheme.light`/`dark`·`ColorScheme.fromSeed(indigo)`·다크모드·`ThemeMode.system`)와 `brand_colors.dart`(OAuth 브랜드색 분리)를 신설. **정서 안전 팔레트를 토큰에서 강제** — M3 `error` 롤을 **앰버(주의)로 재정의**해 빨강을 구조적으로 차단(`test/theme_test.dart` 회귀 게이트). 넓은 대상·역할을 지탱하려면 여기에 아래를 더 얹는다.

- **토큰**: 색(🟢)·간격(🟢 `AppSpacing`·`SizedBox`+`EdgeInsets` 전면 이관·MOB-10/11)·타이포(🟢 `textTheme` 롤 전면 채택·잔여 매직 `fontSize` 0·MOB-10/11). **정서 안전 팔레트**(빨강 ❌·앰버 ✅ `05:31-34`)를 토큰 레벨에서 강제(🟢). 후속: 오프리듬 값 리듬 정리·골든 테스트.
- **테마 = 모드별 `primary_color`(`ModeConfig`) + 연령대 프로파일**. 모드/연령대가 바뀌면 셸이 토큰 세트를 갈아끼운다.
- **핵심 컴포넌트**: 코치 대화 버블(소크라테스 카테고리 배지·`CoachSignalCard`·`CoachEmphasisText`) · Polya 스텝바(상시 노출) · 힌트 단계 표시("지금 1단계") · `SceneElement` 위젯 세트(01 §2) · 활성 문제 배너(`_ActiveProblemBanner`).
- **접근성 컴포넌트**: TTS 재생(코어 `SpeechSpec` 소비·클라는 합성만), 대비·탭영역 보장.

## §7. 로드맵 정합 + 구현 현황

| Phase | 학생앱 초점 | 대상 확장 | 영업 |
|---|---|---|---|
| **1** | 사고력·메타인지·고3 wedge(킬러 30번) | 고3 | — |
| **2** | 학교 진도·수능·**결제(토스)** | +중등 · 재수 | — |
| **3** | 영재 트랙 | +초등 · 대학 모드 | **학부모 보고서·교사 웹(B2B)** |

- K-12 확장 순서: **고3 → 중등 → 초등**(wedge 인접 확장). 대학은 코퍼스 이미 존재.
- 현황: 🟢 학생앱 6라우트·채팅·OCR·수식입력·장면 렌더·6모드 게이팅·**하단 탭 셸(MOB-08)**. 🟡 온보딩 목표 4필드·커리큘럼 정렬 깊이 축·**디자인 토큰/테마(MOB-09·색·다크모드 착지·타이포/간격 후속)**. 🔴 역할(학부모/교사)·결제.

### 역할 UI 롤아웃 — 원본 [B] Phase 1~6 정합

원본 [B]는 학생→교사→학부모→학원→관리자→콘텐츠스튜디오 순의 6단계를 제안한다. WhyMath Phase(위 표·`06`·`07`)와 정합하면:

| 원본 [B] 단계 | 역할 UI | WhyMath Phase | 비고 |
|---|---|---|---|
| Phase 1 | 학생 | Phase 1 | 일치 |
| Phase 2 | 교사 | **Phase 3+** | WhyMath는 Phase1~2 학생 경험 집중, 교사 웹은 Phase3(`07`) |
| Phase 3 | 학부모 | Phase 3 | 일치(보고서 opt-in) |
| Phase 4 | 학원 | Phase 3+ | 교사 웹 권한 변형 |
| Phase 5 | 학교 관리자 | Phase 4+ | 기관 단위 |
| Phase 6 | 콘텐츠 스튜디오 | **Phase 2+** | 예외: 학생 콘텐츠 저작·검수를 위해 *조기* 필요(내부 운영 콘솔·[03](03_admin_console_plan.md)) |

> **정합 판단**: 원본은 콘텐츠 스튜디오를 맨 마지막(Phase 6)에 두지만, WhyMath에선 학생에게 보여줄 콘텐츠(문항·풀이·장면)를 만들고 검수하는 곳이므로 **학생 UI 다음으로 빠르게** 필요하다(운영 백오피스 MVP). 교사·학원·학교 대시보드가 Phase 3+인 것과 구분된다.
