# PED-17 A1 마이그레이션 되돌리기

대상 리비전: `b1a4d7c92e05` (직전 `a8c4e1f7b3d9`) · 파일 `src/backend/alembic/versions/20261107_0900_b1a4d7c92e05_concept_lifecycle_state.py`

> 용어: **마이그레이션**은 DB 구조를 바꾸는 변경 묶음이고, **downgrade**는 그 변경을 취소하는 것입니다.
> **head**는 DB에 마지막으로 적용된 마이그레이션 번호입니다.

## 1. 한눈에 보기

이 마이그레이션이 한 일:

| 구분 | 내용 |
| --- | --- |
| 컬럼 2개 추가 | `concept_content.lifecycle_status`(초안·검증됨·공개됨·회수됨), `concept_content.content_origin`(사람 검수·AI 생성) |
| 테이블 2개 추가 | `concept_state_transition`(상태 변경 기록, 수정·삭제 불가), `concept_exposure_event`(학생 노출 기록) |
| 트리거 3종 추가 | 허용된 상태 전환 5쌍 밖의 변경 거부 · 상태 변경 기록 수정/삭제/비우기 거부 · 노출 기록 수정 거부 |
| 기존 행 상태 이월 | `review_status=reviewed` → 공개됨/사람 검수, `rejected` → 회수됨, 그 외 → 초안 (기존 행은 지우거나 덮어쓰지 않음) |

**되돌리면 사라지는 것**(되돌리기 전에 반드시 내보냅니다):

- `concept_state_transition`, `concept_exposure_event` 두 테이블과 그 안의 **모든 기록**
- `concept_content`의 두 컬럼 값. 이 값은 `review_status`로 다시 계산할 수 있는 이월 결과(사람 검수 이월 분)와, 이후 전환 함수로 바뀐 값(검증됨·AI 생성 공개 등)으로 나뉩니다. **뒤쪽은 `review_status`로 복원되지 않으므로** 기록 CSV가 유일한 사본입니다.

되돌려도 **그대로 남는 것**: `concept_content`의 기존 행과 `review_status` 등 기존 컬럼 전부.

## 2. 되돌리기 전에 알아야 할 것

1. **코드를 먼저 되돌립니다.** 새 코드(`ped17/A1` 브랜치)는 새 컬럼이 있어야 동작합니다. DB만 먼저 되돌리면 학생 화면 요청이 모두 오류가 납니다. 순서: ① 이전 코드 배포 → ② 이 문서의 절차로 DB 되돌림.
2. **기동 시 스키마 가드**(`db/schema_version.py`)가 코드가 기대하는 head와 DB head를 비교합니다. 새 코드는 `b1a4d7c92e05`를 기대하므로 순서가 정해져 있습니다. **적용할 때는 DB 먼저, 코드 나중**(새 코드가 먼저 뜨면 가드가 "DB가 뒤처짐"으로 판정해 위험 신호를 냅니다). **되돌릴 때는 반대로 코드 먼저, DB 나중**입니다.
3. **되돌린 뒤 학생 화면은 `review_status`만으로 결정**됩니다(옛 동작). 이 마이그레이션 이후 AI 생성 개념이 '공개됨'이 되었다면 되돌린 뒤 그 개념은 학생에게 보이지 않습니다(안전한 방향). A1 시점에는 그런 개념이 없습니다.
4. **내보내기가 검증되지 않으면 스크립트가 downgrade를 하지 않습니다.** 샌드박스 리허설에서 내보내기가 권한 오류로 실패했는데 다음 줄의 downgrade가 그대로 실행된 사례가 있어, 이를 막는 가드를 넣었습니다(아래 6절).

## 3. 되돌리기 절차

실행 환경: 리눅스 셸(bash), PostgreSQL 클라이언트(`psql`, `pg_dump`)와 파이썬 3.12 + 백엔드 의존성이 있는 곳. 작업 폴더는 저장소의 `src/backend`.

**운영 DB에 바로 적용하지 않습니다.** 먼저 복사본이나 스테이징 DB에서 같은 절차를 실행해 결과를 확인합니다.

접속 정보를 입력합니다(비밀번호는 화면에 표시되지 않고 파일에도 남지 않습니다).

```bash
# 실행 환경: bash · 작업 폴더: 저장소의 src/backend
read -r -p "DB 호스트: " PGHOST
read -r -p "DB 포트: " PGPORT
read -r -p "DB 사용자: " PGUSER
read -r -p "DB 이름: " PGDATABASE
read -r -s -p "DB 비밀번호(화면에 보이지 않음): " PGPASSWORD; echo
export PGHOST PGPORT PGUSER PGDATABASE PGPASSWORD
```

되돌리기 스크립트를 실행합니다. 파이썬이 `python3`가 아니라 가상환경에 있다면 먼저 `export PYTHON=가상환경의/bin/python` 으로 지정합니다.

```bash
# 실행 환경: bash · 작업 폴더: 저장소의 src/backend
bash ../../ped17/산출물/A1/rollback_a1.sh
```

스크립트가 하는 일(순서대로, 하나라도 실패하면 그 자리에서 멈춤):

1. 필수 환경변수 5개와 실행 위치(`alembic.ini` 존재)를 확인합니다.
2. 현재 head가 `b1a4d7c92e05`인지 확인합니다(아니면 되돌릴 대상이 아님).
3. 두 기록 테이블을 CSV로, `concept_content`를 `pg_dump` 파일로 내보냅니다. 내보내기 폴더는 `OUT_DIR`(기본 `$HOME/ped17_a1_rollback_날짜시각`).
4. CSV의 행 수가 DB의 행 수와 같은지 확인합니다.
5. 여기까지 통과해야만 `alembic downgrade a8c4e1f7b3d9`를 실행합니다.

## 4. 되돌린 뒤 확인

아래 네 질의의 기대값은 순서대로 `a8c4e1f7b3d9`, `0`, `0`, 그리고 **되돌리기 전과 같은 행 수**입니다.

```bash
# 실행 환경: bash · 3절에서 입력한 PG* 환경변수가 설정된 같은 셸
psql -At -c "select version_num from alembic_version"
psql -At -c "select count(*) from information_schema.columns where table_name='concept_content' and column_name in ('lifecycle_status','content_origin')"
psql -At -c "select count(*) from information_schema.tables where table_name in ('concept_state_transition','concept_exposure_event')"
psql -At -c "select count(*) from concept_content"
```

학생 경로가 변경 전과 같은지는 비교 스크립트로 확인합니다. 이전 코드를 배포한 뒤 `scripts/analysis/ped17_a1_compare_student_gate.py`를 실행해 `ped17/산출물/A1/비교/before.json`과 `diff`했을 때 차이가 없어야 합니다.

## 5. 다시 적용하기

```bash
# 실행 환경: bash · 작업 폴더: 저장소의 src/backend · 3절에서 입력한 PG* 환경변수가 설정된 같은 셸
export WHYMATH_DATABASE_URL=$(python3 -c 'import os,urllib.parse as u; e=os.environ; q=lambda k: u.quote(e[k], safe=""); print("postgresql+asyncpg://%s:%s@%s:%s/%s" % (q("PGUSER"), q("PGPASSWORD"), e["PGHOST"], e["PGPORT"], q("PGDATABASE")))')
python3 -m alembic upgrade head
```

다시 올리면 기존 `review_status`로 상태를 다시 이월하고 '최초 부여' 기록을 만듭니다. **내보낸 CSV의 기록은 자동으로 복원되지 않습니다.** 되돌리기 전에 전환 함수로 바뀐 상태(검증됨·AI 생성 공개 등)를 복원하려면 CSV를 `changed_at` 순서로 읽어 `transition_concept_state`로 재생하는 별도 작업이 필요하고, A1 범위 밖입니다.
