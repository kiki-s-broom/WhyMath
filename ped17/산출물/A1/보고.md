## 설계 요약 (초보자용)

- 이 저장소에는 이미 `concept_content.review_status`(사람 검수 라벨: ai_estimated / reviewed / rejected)가 있고 학생 경로가 이를 보고 있었다. 그래서 **새 축을 하나 더 둔다**: `lifecycle_status`(초안·검증됨·공개됨·회수됨)는 "학생에게 공개되는 생애", `review_status`는 "사람이 검수했는가"다.
- 학생에게 나가는 조건(`is_student_visible`): 생애가 '공개됨'이어야 하고, 출처가 '사람 검수'인 행은 `review_status == reviewed`도 유지돼야 하며, 출처가 'AI 생성'인 행은 사람이 `rejected`로 판정한 경우만 막는다. **더 엄격한 쪽이 이긴다.** 사람 검수 행에 `review_status` 조건을 남긴 이유: 코퍼스 재적재가 `review_status`를 되돌리는 경로(CONT-05 ③)가 이미 있어, 생애 컬럼만 보면 그 강등이 학생에게 닿지 않기 때문이다.
- 새 행의 기본값은 '초안'(fail-closed). 이 컬럼을 모르는 코퍼스 적재기가 만든 행은 학생에게 나가지 않는다.
- 상태를 바꾸는 코드는 `transition_concept_state` 한 곳뿐이다(AST 테스트가 동결). 허용 전환 5쌍과 각 전환의 허용 경로(B6 / D4·D5 / 킬스위치·회수·긴급 정지 / D2·D4·D6 / 재생성)는 `schema/concept_lifecycle.py`에 있다. 긴급 정지 경로는 Kiki만 쓸 수 있다.
- DB도 같은 규칙을 지킨다: 허용 5쌍 밖의 `UPDATE`는 트리거가 거부하고, 상태 변경 기록은 수정·삭제·비우기를 트리거가 거부한다.

## Kiki 판단이 필요한 것

1. **2027년 사람 검수가 재개될 때의 승격 경로가 비어 있다.** 지금 `concept_content_review_apply`가 행을 `reviewed`로 바꿔도 새 행의 생애는 '초안'이라 **학생에게 나가지 않는다**(옛 동작과 다름). 지시된 허용 전환 5쌍에는 초안→공개됨이 없고, A1은 6번째 전환을 임의로 만들지 않았다. 후보: ① 사람 검수 행도 B6을 거쳐 검증됨→공개됨으로 올린다 ② 검수 반영 경로에 별도 전환(예: 초안→공개됨, 경로 '사람 검수 승격')을 허용한다. 사람 검수는 2027년까지 보류라 당장 영향은 없다.
2. **`rejected`(사람이 거부) 행을 '회수됨'으로 이월했다.** "공개된 적 없지만 사람이 거부한 행"의 자리가 4상태에 없다. 회수됨으로 두면 재검증은 반드시 회수됨→초안(재생성)을 거친다. 초안으로 두면 거부된 콘텐츠가 재생성 없이 B6에 들어갈 수 있다. 현재 코퍼스에 `rejected`는 0건이라 영향 없음.
3. **노출 기록의 보존기한 파기·삭제 요청 배선이 없다.** 노출 기록은 가명 해시지만 학생 학습 기록이라 법령 유래 절차의 대상이다. 그래서 DELETE는 막지 않았으나(수정만 막음) 기존 `privacy/retention.py`·삭제 요청 경로에 이 테이블을 연결하는 작업이 별도로 필요하다.

## 미확인·가정한 것

- **운영 DB의 `reviewed` 행 수는 확인하지 못했다.** 저장소 코퍼스 846건은 전부 `ai_estimated`이고 검수 라벨 파일도 저장소에 없다. 즉 저장소 증거로는 지금 학생에게 나가는 개념이 0건이다. 완료 기준 2는 합성한 검수 완료 5건으로 비교했다. 운영 DB에서의 실측은 하지 않았다(지시: 운영 데이터에 바로 적용 금지).
- 작업 환경의 "저장소 위치" 칸이 비어 있어 질문했고 `kiki-s-broom/WhyMath`로 확정받았다.
- `/study` 전체 HTTP 경로를 실 DB로 한 번에 태우지는 않았다. 엔드포인트 테스트는 가짜 세션, 실 DB 검증은 학생 경로 관문(`resolve_concept_content`)·전환 함수·노출 writer를 각각 따로 수행했다. 사용자·교육과정 단원·학습자 상태가 얽힌 시드가 필요해 비용 대비 이득이 작다고 판단했다.
- 상태 변경 기록에 지시문에 없는 열 `via`(어느 작업·기능이 바꿨는가)를 더했다. 전환표가 경로까지 검사하므로 사후 감사에 필요하다. `from_state`는 NULL을 허용한다('최초 부여' 행: 마이그레이션이 기존 행에 상태를 처음 매길 때. 허용 전환에 없는 가짜 이력을 만들지 않으려는 것).
- 지시문의 "D6"가 무엇인지 저장소에서 찾지 못해 경로 이름을 `D6` 그대로 두었다.
- `ai_label_shown`은 현재 응답에 AI 라벨이 없으므로 항상 False로 기록한다(`api/study.py`의 `AI_LABEL_SHOWN_IN_RESPONSE`). 라벨 표시 기능이 들어오면 그 상수 한 곳을 바꾼다.
- `changed_by_kind='kiki'`는 호출자의 자기 신고라 **위조를 막지 못한다**. 전환 함수는 "긴급 정지 경로는 kiki만"으로 실수·에이전트 오용을 막을 뿐이다. 위조 방어는 호출 지점 코드 리뷰와 AST 테스트의 몫이다.
- 전환 함수는 호출자가 선언한 경로(예: B6 공개 관문)가 **실제로 그 합격 판정을 거쳤는지는 검증하지 못한다.** 그것은 B6·D4·D5 각 작업의 책임이고, 기록 테이블이 선언을 사후 감사 가능하게 남긴다.
- 가명 해시 키는 `jwt_secret_key`를 공유한다(도메인 프리픽스 분리). 키를 바꾸면 같은 학생이 둘로 세어진다.
- 리눅스 컨테이너에서만 검증했다. Kiki의 작업 PC(Windows PowerShell + docker) 용 명령 변환은 검증하지 않았다.
- PED-17 백로그 항목은 claim하지 않았고 수정하지 않았다(T0와 같음, 지시문 범위 밖).
- 선행 작업 T0의 `보고.md`는 "완료"로 확인했다. 그 PR(#1857)의 산출물은 이 저장소 main에 들어와 있었다.
- CI 25개 잡 중 닿지 않는 잡(data-pipeline·mobile·web·webapp·corpus-authoring·infra-shell·e2e/serial nightly·constraints-freshness)은 해당 경로를 바꾸지 않아 재현하지 않았다. `docker-build`는 이미지 빌드가 필요해 재현하지 않았다.

## 다음 작업이 알아야 할 것

- **배포 순서: DB(마이그레이션) 먼저, 코드 나중.** `EXPECTED_ALEMBIC_HEAD`가 `b1a4d7c92e05`로 올라가서 순서가 거꾸로면 기동 가드가 위험 신호를 낸다. 되돌릴 때는 반대(코드 먼저).
- **B6**: `transition_concept_state(session, concept_code=…, to_state=ConceptLifecycleState.VERIFIED, via=ConceptTransitionVia.B6_PUBLIC_GATE, changed_by_kind=…, changed_by_name=…, reason=…)`. 커밋은 호출자가 한다. 거부 시 `InvalidConceptTransitionError`.
- **D4·D5**: 검증됨→공개됨은 `D4_AI_CANARY` 또는 `D5_STAGED_ROLLOUT`만. **개념 단위의 단계적 공개(1% → 10% → 100%)는 A1에 없다** — 생애 상태는 '공개됨'이면 전체 공개다. 비율 공개 장치는 D5가 따로 만들어야 한다.
- **킬스위치·회수·긴급 정지**: 공개됨→회수됨 경로 3종. 회수는 DSL 캐시(24시간)가 남아 있어도 다음 요청부터 막힌다(판정이 캐시보다 먼저 DB 현재 상태로 일어남, 테스트로 동결).
- **상태를 쓰는 코드는 전환 함수 한 곳뿐**이다. 새 코드에서 `lifecycle_status`를 직접 `UPDATE`/대입하면 `tests/backend/l1/test_concept_lifecycle_governance.py`가 실패한다.
- **노출 기록**: 같은 학생의 여러 학습 세션이 한 가명으로 묶인다(세션 바인딩과 다른 해시). "개념을 본 서로 다른 학생 수"는 `concept_exposure_event`에서 `count(distinct student_pseudonym)`으로 센다.
- 사유 상수 `REASON_UNREVIEWED`는 이름 그대로지만 이제 "공개 상태가 아님" 전체(초안·검증됨·회수됨 포함)를 뜻한다. 학생에게는 모두 같은 404다. "준비 중" 안내로 바꾸는 것은 다른 작업.
- `l1/standards/phase3_coverage.py`는 아직 `review_status == reviewed`로 "학생 공급 가능"을 센다. 지금은 이월 규칙 덕에 같은 수지만, AI 생성 공개 개념이 생기면 그 집계는 실제 공급 수와 어긋난다.
- 코퍼스 적재기·`concept_content_review_apply`는 수정하지 않았다. 적재기가 만든 새 행은 '초안'/'AI 생성'이다.
- 이 작업이 대장에 등록한 곳(인벤토리·BASELINE·프로브·체인)을 후속 작업이 모듈을 더할 때도 같은 방식으로 갱신해야 `infra-contracts` 잡이 통과한다.
